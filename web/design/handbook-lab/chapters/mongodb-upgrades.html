Separate binary version from feature compatibility

The selected target is the vendor RHEL 9 x86_64 RPM 8.0.29-1.el9. A patch update within 8.0 is not a 7.0 → 8.0 major upgrade. featureCompatibilityVersion (FCV) gates persistent feature compatibility; changing it does not install a binary. Running 8.0 binaries at FCV 7.0 after a major upgrade is a deliberate burn-in phase, not evidence of an unfinished package install.[4][27][28]

Starting point Route
Supported earlier 8.0 patch Review intervening patch notes/advisories; rolling binary replacement in a healthy replica set; retain FCV
7.0 series, all members FCV 7.0 Rehearse documented 7.0 → 8.0 procedure; secondaries first; FCV last
6.0 or older Sequential major upgrades to 7.0 first; review each intermediate version’s own procedure
Standalone Backup, write outage, clean shutdown, replace/start/validate; no rolling HA
Sharded cluster Config servers, shard replica sets, then routers; coordinated FCV through mongos

Do not skip majors by pointing a new executable at an old dbPath. Do not interpret “FCV still 7.0” as permission for arbitrary binary downgrade: MongoDB’s 8.0 documentation states binary downgrade needs support assistance; Community binary downgrades are not supported. The independent recovery plan is a rehearsed pre-upgrade backup restore or compatible logical/application migration, with an explicit post-upgrade-write loss/reconciliation decision.[25][27][56]

Preflight and rehearsal

Use the administrative identity and connect to each member directly for node-local inspection, preserving TLS/auth. Record effective config, exact packages, drivers, operating system, FCV, replica configuration and backup recovery credentials.[27][29]

const admin = db.getSiblingDB("admin");
admin.runCommand({buildInfo: 1});
admin.runCommand({getParameter: 1, featureCompatibilityVersion: 1});
admin.runCommand({replSetGetStatus: 1});

Before a 7.0 → 8.0 upgrade:

  1. Bring all members to the required 7.0-series baseline and FCV 7.0; verify none are in ROLLBACK/RECOVERING or doing initial sync.
  2. Restore a recent backup into staging, exercise the exact upgrade and application workload, and measure startup/recovery/index behavior.
  3. Review driver compatibility, removed options/commands, query changes and feature compatibility. 8.0 deprecates server-side JavaScript features; do not conceal warnings by dropping code paths untested.
  4. Inspect invalid non-time-series system.buckets collections as the official guide requires. Preserve data before any rename/drop; do not paste a wildcard removal command.
  5. Confirm majority remains while each member is unavailable, disk/cache/connection headroom, an oplog window longer than maintenance, and working backups.
  6. Retain old artifacts/config for forensic/recovery use, but do not promise they can simply reopen upgraded files.[27][29][31]

On RHEL record rpm -q for server/router/shell/Tools, the installed SELinux policy revision and local fcontext/port mappings, systemctl cat/show including drop-ins and /etc/sysconfig/mongod, filesystem mounts and both firewalld configurations. Rehearse any OS-major migration separately; swapping an el8 RPM onto an el9 machine is not an OS migration procedure. Recheck current RHEL kernel/glibc errata and MongoDB advisories.[100][101][104]

Application acceptance should include authentication, representative queries/plans, transactions/retries, change stream consumers where used, backup tooling and operational monitoring. “Server started” is insufficient.

Upgrade one replica set

Service disruption; potential election. Three healthy data-bearing members are assumed. Use exact approved packages, not an unattended broad dnf upgrade. For a 7.0 → 8.0 migration, configure the 8.0 repository as in installation; leave shell/Tools versions separately controlled.[27][104]

  1. Pick a secondary; verify its role immediately before stopping. Stop only its mongod service.
  2. Delete only the server component’s version lock, install the exact target NEVRA, verify/relock it, then restart. Do not clear the whole lock list. A router package is upgraded on router hosts, not used as evidence that a data member changed.
  3. Wait until it is healthy SECONDARY, caught up and error-free; check the actual server version. Abort the rollout if it cannot rejoin.
  4. Repeat for the next secondary, never taking down a voting majority together.
  5. On the current primary, step down without forcing. Wait until another upgraded member is PRIMARY; only then stop/upgrade/restart the old primary.[27]
# On the chosen stopped member only; package versions must already be available.
sudo systemctl stop mongod
sudo dnf versionlock delete mongodb-org-server
sudo dnf install mongodb-org-server-8.0.29-1.el9.x86_64
rpm -q mongodb-org-server
sudo dnf versionlock add mongodb-org-server
sudo dnf versionlock list
sudo systemctl daemon-reload
sudo restorecon -v /usr/bin/mongod /usr/lib/systemd/system/mongod.service /etc/mongod.conf
sudo systemctl start mongod
sudo journalctl -u mongod -n 100 --no-pager

// Primary maintenance action, cluster administration privilege
rs.stepDown(60);
// Reconnect through the set URI, then inspect:
rs.status();

If package installation fails, do not continue the sequence or relock an assumed version: inspect rpm -q/DNF transaction state and keep the node stopped until resolved. Retain /etc/mongod.conf and review any .rpmnew/.rpmsave, unit and environment changes rather than overwriting security settings. Recheck mongod_t, labels, effective service limits and AVCs after the upgrade; rpm -V differences on an intentionally changed config require review, not blind reset.[100][101][110]

Connection interruption can be expected during stepdown. No eligible caught-up secondary or failure to elect is a stop condition, not a reason to add force: true. Repair health while preserving majority; application drivers must tolerate the election and resolve uncertain write outcomes.[27][30]

For an 8.0 patch update, follow the same healthy-member discipline but do not change FCV merely because the patch number changed. Observe release-specific instructions/advisories before treating that as universally sufficient.[4][28]

Upgrade a sharded topology

Inventory every config-server member, every shard member and every mongos. Confirm the whole cluster is at 7.0/FCV 7.0 before a major upgrade, and have a coordinated backup including config metadata. Direct shard checks require authorized shard-local maintenance identities; cluster users on mongos are not automatically shard-local users.[25]

  1. On mongos, save balancer state, call sh.stopBalancer(), and verify it stopped with no migration still running.
  2. Upgrade the config-server replica set secondary-by-secondary, then step down/upgrade its primary; wait for complete health.
  3. Upgrade each shard replica set, secondaries then stepped-down primary. Verify health before moving on.
  4. Upgrade/restart mongos routers individually, maintaining available client entry points. On each stopped router use the same DNF lock/delete/install/relock discipline for mongodb-org-mongos-8.0.29-1.el9.x86_64 and verify mongos --version. Preserve and revalidate the site-owned router unit and separate enforcing SELinux policy; the server policy does not cover mongos. Verify all clients have valid endpoints.
  5. Restore the prior balancer state, verify routing and application operations, then begin burn-in. Do not leave a disabled balancer undocumented.[25]

Do not raise FCV shard-by-shard. That is a cluster-wide action through mongos after all components are ready.[25][28]

Commit FCV and validate

After burn-in, no initial sync, compatible drivers, healthy replication and accepted rollback/recovery risk, run on the replica-set primary or on mongos for a sharded cluster:[25][27][28]

db.getSiblingDB("admin").runCommand({
  setFeatureCompatibilityVersion: "8.0", confirm: true
});
// Reconnect directly to an authenticated mongod member for this read.
// Do not issue getParameter/FCV on mongos.
db.getSiblingDB("admin").runCommand({
  getParameter: 1, featureCompatibilityVersion: 1
});

Check FCV directly on data/config members afterward, plus versions, member health, lag, balancer and logs. FCV transition performs internal writes and can wait for availability; an interrupted transition requires inspecting state and following documented retry behavior, not alternating target versions blindly.[28]

Acceptance includes application business checks, query-plan regressions, index/validator state, backup/restore drill under the new version and a fresh protected backup. If a severe issue appears, stop rollout/traffic as appropriate and invoke the rehearsed recovery plan. Restoring the pre-upgrade backup necessarily excludes later accepted writes unless separately reconciled. Keep that RPO decision explicit; a package downgrade is not rollback.[27][56]
