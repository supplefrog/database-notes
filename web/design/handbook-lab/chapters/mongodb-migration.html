Map behavior before moving bytes

A MongoDB migration is an application/data-model migration, not “restore a SQL dump.” Inventory source objects, joins, routines, constraints, collations, identifier generation, transactions and permission assumptions. For this worked model, customers remain referenced documents and bounded order lines embed under each order.[35]

Source contract Target decision
orders + order_lines join One bounded order aggregate, stable source ID
Customer foreign key customerId + tenant check; transaction/application policy and reconciliation
DECIMAL totals Decimal128 plus explicit currency/rounding rules
BIGINT keys String or BSON Long, consistent in references and filters
Auto-increment Preserve source identity during migration; choose future globally unique strategy
Case-insensitive uniqueness Deliberate collation/normalization/index policy, checked against duplicates
Triggers/procedures Application/service workflow; no automatic SQL translation
Relational permissions MongoDB roles on actual resources; no assumption of field/tenant row policy
Timestamp without timezone Document original timezone/DST resolution before conversion

Document each transformation, including NULL versus missing, empty strings, binary/UUID representation, decimal overflow and invalid dates. Reject/quarantine incompatible rows with source keys and reason; never silently coerce them merely to finish the import.[36][45]

Load one canonical Extended JSON order

Data mutation on a disposable staging database. The source extract must represent a consistent checkpoint across parent/child tables. The following file is authored fixture input, not exported production data. Canonical Extended JSON preserves Decimal128, BSON date and integer types; plain CSV/relaxed JSON can lose important distinctions.[45][46]

Create orders.ejson containing one JSON document per line (the single line below is one order):

{"_id":"o1001","tenantId":"t1","customerId":"c1","placedAt":{"$date":{"$numberLong":"1788253200000"}},"status":"new","total":{"$numberDecimal":"5.00"},"lines":[{"sku":"pencil","qty":{"$numberInt":"2"},"unitPrice":{"$numberDecimal":"2.50"}}]}

Prerequisite: the fixture shop.orders validator exists. As useradmin, grant the loader operator temporary readWrite and dbAdmin roles on shop_migration. Then, authenticated as operator, create a new empty target collection with the same validator and required index; inspect an existing target instead of overwriting it:[18][37][54]

const source = db.getSiblingDB("shop");
const stage = db.getSiblingDB("shop_migration");
const definition = source.getCollectionInfos({name: "orders"})[0];
if (!definition) throw new Error("fixture validator missing");
if (stage.getCollectionInfos({name: "orders"}).length) throw new Error("target already exists");
stage.createCollection("orders", {
  validator: definition.options.validator,
  validationLevel: "strict", validationAction: "error"
});
stage.orders.createIndex({tenantId: 1, placedAt: -1}, {name: "tenant_recent"});

Run the separately verified RHEL 9 x86_64 Database Tools RPM 100.17.0-1 from the OS shell on a trusted worker. It is not a mongod service: give the operator access to its input/output and CA files, not write access to dbPath. Preserve restrictive staging-file modes (umask 077) and review the worker’s actual SELinux domain; the vendor mongod policy does not cover Tools.[103][106] This loopback example matches the initial secured standalone; for the TLS replica/sharded deployment, use its TLS CA and topology URI instead. Keep the target database explicit.[45]

mongoimport --host 127.0.0.1 --port 27017 --username operator \
  --authenticationDatabase admin --db shop_migration --collection orders \
  --type=json --file=orders.ejson --mode=insert --stopOnError --maintainInsertionOrder

Require successful exit and inspect the inserted ID/types. --mode=insert intentionally rejects duplicates on a rerun. A failed import can leave earlier documents inserted: inspect/quarantine the partial staging batch, then reload a clean target or use an explicitly designed idempotent upsert strategy. --maintainInsertionOrder makes error stopping immediate; without it a small number of concurrent inserts can still finish after the error. These flags are also checked against the official 100.17.0 tagged option definitions, because the live import manual now describes 100.18.0.[45][67]

Option Use / caution
--type=json Extended JSON stream; not a SQL dump
--jsonArray Only if file is one JSON array; not needed for JSON-lines example
--mode=insert New documents; duplicate IDs expose accidental replay
--mode=upsert --upsertFields=... Replace matching document; omitted fields can disappear
--mode=merge Merge imported fields; may retain unwanted obsolete fields
--stopOnError Stop on error; no batch rollback
--drop Destructive collection replacement; omitted here to preserve validator/index design
CSV typed fields Requires explicit field-type policy; nested arrays/decimals are better represented by a driver/EJSON loader

mongoimport does not recreate the entire source database’s indexes, users, roles, views and validation rules. Create/review those separately. Use mongodump/mongorestore for MongoDB logical backup rather than declaring import/export equivalent.[2][45][46]

Validate shape, types and business invariants

const stage = db.getSiblingDB("shop_migration");
stage.orders.find({_id: "o1001"}).toArray();
stage.orders.aggregate([
  {$project: {_id: 1, totalType: {$type: "$total"}, dateType: {$type: "$placedAt"},
    quantities: {$map: {input: "$lines", as: "line", in: {$type: "$$line.qty"}}}}}
]).toArray();
stage.orders.aggregate([
  {$group: {_id: "$tenantId", orders: {$sum: 1}, amount: {$sum: "$total"}}},
  {$sort: {_id: 1}}
]).toArray();
stage.orders.aggregate([
  {$project: {_id: 1, total: 1, lineTotal: {$sum: {$map: {
    input: "$lines", as: "line",
    in: {$multiply: ["$$line.qty", "$$line.unitPrice"]}
  }}}}},
  {$match: {$expr: {$ne: ["$total", "$lineTotal"]}}}
]).toArray();

For this one-line fixture, acceptance is one o1001, decimal total, date placedAt, int quantities, correct tenant/customer IDs and no line-total mismatch. Real totals may include taxes/discounts/shipping: use the source’s actual business equation, not the simplified fixture equation. Compare count and exact decimal aggregates by tenant/currency/status to the same source checkpoint; retain exception reports.[35][45]

Also reconcile orphan references using the tenant-aware lookup, duplicate business keys, date ranges, delete/tombstone behavior and index/validator definitions. The lookup is database-local: for this staging exercise, prepare shop_migration.customers from the same checkpoint, and run the pipeline with db.getSiblingDB("shop_migration"); querying shop.orders would accidentally validate the original fixture instead. For the one-order fixture, staging customer {_id: "c1", tenantId: "t1", name: "Mira"} is sufficient. Inspect existing staging customers before inserting; do not replace a real customer dataset with that example. Byte checksums of a SQL export and BSON file will differ; if using row/document checksums, define deterministic canonical field order, decimal/date/null encoding and the same logical projection on both sides.

An inspection export can preserve BSON types in canonical EJSON, but remains data interchange, not a complete backup; --jsonFormat=canonical is present in the pinned 100.17.0 options:[46][68]

mongoexport --host 127.0.0.1 --port 27017 --username operator \
  --authenticationDatabase admin --db shop_migration --collection orders \
  --jsonFormat=canonical --out=orders-roundtrip.ejson

Reimport only into another isolated prepared target, then repeat type/business checks. Protect exports like the source database; they contain usable data.

Capture changes and cut over once

For a small migration, a source write outage through extract/load/reconciliation is the simplest complete consistency story. For a large one, use a source-specific CDC mechanism with a durable checkpoint, ordered transactions and delete handling. MongoDB change streams observe MongoDB changes, not a MySQL binlog; they do not solve source-side CDC automatically. Choose and validate the connector/application approach separately rather than inventing a universal command.[35][40]

A controlled CDC cutover has these gates:

  1. Take a consistent bulk snapshot with its exact source log/checkpoint position. Retain enough source history for the entire load and catch-up.
  2. Load deterministic document IDs; transform parent/child changes with a defined ordering and transaction policy. A late line deletion must not resurrect an old aggregate.
  3. Apply deltas idempotently and persist checkpoints only after acknowledged target effects. Track duplicates, dead letters, lag, schema changes and source-log expiration.
  4. Shadow-read and run application tests without letting the target become a second uncontrolled writer. Validate sort/collation, pagination, aggregates, authorization, transactions/retries and error behavior.
  5. Stop source writers and drain in-flight transactions. Record final source position; wait until target has applied it. Reconcile counts/totals/references at that stable boundary.
  6. Switch one controlled application configuration/traffic path to the target; verify reads and guarded writes with stable business request IDs. Fence old writers, retain old source read-only and monitor.
  7. Take a protected target backup and complete a restore drill before retiring source artifacts.

No-loss dual writes are not achieved by write(source); write(target);: one side can succeed while the other fails. Use a proven transactional-outbox/CDC design with reconciliation, or accept a write outage. Track who owns the authoritative copy at every stage.

Rollback is a data decision

Before target writes, rollback is usually to keep/re-enable the source and discard the isolated failed target after preserving evidence. After target writes, switching back to a stale source loses accepted work. Predefine reverse replication or a reviewed reconciliation/export process, the maximum tolerated divergence and the authority to approve it.

Do not overwrite source rows from an unverified MongoDB export or delete migration logs to make totals agree. Retain immutable source checkpoint extracts and transformation version/digests under retention policy. Revoke the loader’s elevated staging roles and remove temporary plaintext exports when acceptance and recovery retention permit. The application migration is done only when business behavior, recovery and access controls work—not when imported row counts look plausible.[18][45]
