Filesystems

RHEL 9’s usual local choices are XFS and ext4. Btrfs and OpenZFS below are cross-platform comparisons, not instructions to deploy unsupported RHEL filesystem packages. Features depend on format options, software version and storage layout.[23]

Filesystem Crash consistency Integrity checks Native snapshots Integrated multi-device/RAID Typical fit
ext4 Journaling, with mode-dependent data handling Metadata checksums when enabled; no general file-data checksum No; lower layers such as LVM can snapshot No; use a separate storage layer General-purpose Linux filesystems
Btrfs Copy-on-write Data and metadata checksums, with exceptions for configured modes such as NODATASUM Yes Yes; profiles have distinct limits and failure behavior Linux deployments needing subvolumes/snapshots and validated Btrfs support
XFS Metadata journaling Metadata checksums on modern formats; not general file-data checksums No native volume snapshots; reflink file clones are different No; use a separate storage layer Scalable general/server storage; RHEL 9 default.[133][140]
OpenZFS Copy-on-write transactional storage Data and metadata checksums; some data checksum properties are configurable Yes Yes, through pool/vdev layouts including mirrors and RAIDZ Storage deployments that support and deliberately operate OpenZFS

Btrfs checksum exceptions and OpenZFS pool/checksum properties must be read with their selected layout and property settings.[70][68][69]

A checksum detects corruption; repair also needs a sound redundant copy. Neither journaling nor copy-on-write guarantees that every unflushed application write survives a power loss. Choose by supported workload and recovery requirements, not “small files versus big files” alone.[59][24][44]

ext4 layout

A directory maps names to inode numbers. An inode describes a file’s metadata and data layout; regular-file data blocks hold its content. This is more precise than saying that every directory simply “points to data.” ext4 uses metadata checksums for supported structures; it does not generally checksum file contents.[59][67]

RAID

Redundant Array of Independent Disks describes families of layouts with different capacity, performance and failure tradeoffs. Hardware controllers, Linux software RAID and LVM RAID implement different management layers. RAID 0 stripes data without redundancy; other levels tolerate only specified failure patterns.[83][141]

RAID is not a backup. It does not independently protect against deletion, malicious changes, application corruption or loss of the whole host. A local snapshot is also not an independent backup. Keep restorable copies in a separate failure domain and verify recovery; after a disk failure, a rebuild is a period of additional risk, not proof the data is safe.[23][44]

Directory structure

The following is a systemd/Linux layout reference. RHEL 9 uses a merged /usr layout, so several traditional root directories are compatibility symlinks.[14]

Path Purpose
/ Root of the filesystem namespace
/boot Kernel/initramfs and boot-related files; the ESP may be mounted at /boot/efi
/dev Device nodes and related interfaces
/bin Traditional essential command path; commonly a symlink to /usr/bin
/sbin Traditional system-administration commands; commonly a symlink to /usr/sbin
/usr Installed userspace binaries, libraries and shareable data; not users’ home directories. Can be read-only in an appropriate deployment
/opt Optional/add-on application trees
/lib, /lib64 Traditional library paths, commonly linked into /usr; kernel modules conventionally under /lib/modules
/home Ordinary users’ home directories
/root Root user’s home
/etc Host-specific configuration
/var Variable persistent data such as logs, spool and application state; individual subpaths may have different retention
/tmp Temporary files; may be cleared on boot or by age-based cleanup. Not guaranteed to last a session or survive reboot
/var/tmp Temporary files normally retained across boots, but still subject to cleanup policy
/mnt Conventional temporary mount location
/proc Virtual process/kernel interface, including per-PID directories
/sys Virtual interface to devices and other kernel objects

Inspect and manage partitions

Inspection and creation are different operations. These examples target the RHEL 9 util-linux/e2fsprogs/GNU Parted tools; the first commands only inspect.[100][101][26]

lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS,MODEL,SERIAL
findmnt
sudo fdisk -l
sudo parted --list
Tool Role
parted Inspect/edit GPT or MBR partition tables; print is inspection, creating/deleting partitions writes metadata
fdisk Interactive partition-table editor supporting GPT and MBR, not only legacy MBR; -l lists tables
partprobe Requests that the kernel update its view of partition-table changes; busy devices can prevent a safe reread.[137]
mkfs.ext4 DEVICE or mke2fs -t ext4 DEVICE Create an ext4 filesystem, overwriting filesystem metadata on the selected device

Formatting destroys the selected filesystem. Use only an explicitly approved, expendable test partition or approved maintenance target with a verified backup. Identify it by capacity, serial/WWN and storage ownership—not by assuming /dev/sda1 is spare. Confirm it is neither mounted nor swap and is not a live RAID/LVM member; stop dependent workloads and obtain console access before changing a boot/storage device.[26][27][52]

Schematic alternatives—not a paste-ready device selection:

mkfs.ext4 /dev/disk/by-id/VERIFIED-TEST-PARTITION
# Equivalent filesystem choice, not a second required step:
mke2fs -t ext4 /dev/disk/by-id/VERIFIED-TEST-PARTITION

After an authorized change, inspect lsblk -f and the partition layout, mount only at an approved empty test mount point, and verify access/ownership before allowing workloads onto it. Do not force a partition reread on a busy production disk. Formatting has no general “undo”; restore from backup if the wrong data was destroyed. For basic mounting, see file commands.
