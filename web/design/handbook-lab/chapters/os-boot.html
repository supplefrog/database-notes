Boot process

This is an x86-64 PC overview, with RHEL 9, GRUB2 and systemd as the Linux example. Other architectures and firmware paths differ; BIOS versus UEFI is distinct from MBR versus GPT partitioning.

1. Power on

Power-on begins the platform firmware startup path. In a PI implementation, SEC is the initial code that takes control: it handles restart events, establishes temporary memory and passes control and platform information to PEI. The processor-specific details differ across architectures.[129]

2. Firmware

BIOS path

Legacy BIOS performs hardware initialization and power-on checks (POST), then selects a boot device. For a failed POST, consult the machine vendor’s diagnostics rather than assuming every reported error halts boot. In the conventional disk path, BIOS loads boot code from the first disk sector; that code continues the bootloader chain. It is not the only possible BIOS boot path.[10][119]

Conventional MBR region Purpose
Bytes 0–445 (0x0000–0x01BD) Bootstrap area, including fields such as the disk signature; not necessarily 446 bytes of executable code
Bytes 446–509 (0x01BE–0x01FD) Four 16-byte partition records. Traditional bootstrap code may select an active partition
Bytes 510–511 (0x01FE–0x01FF) Bytes 55 AA; little-endian 16-bit signature value 0xAA55

A GPT disk has a protective MBR at LBA 0, a primary GPT header at LBA 1, partition entries, and backup GPT structures near the end of the disk. GPT is not inherently incompatible with BIOS bootloaders: GRUB documents a BIOS Boot Partition on GPT.[10][119]

UEFI path

SEC (Security), PEI (Pre-EFI Initialization), DXE (Driver Execution Environment) and BDS (Boot Device Selection) describe common PI/EDK II firmware phases, not a requirement that every implementation expose identical steps to the user.[118][130]

The UEFI boot manager uses boot options/device paths to select an EFI application. On a conventional installed GPT disk, the EFI System Partition (ESP) is identified by its partition type GUID and contains a FAT filesystem (normally FAT32 on fixed disks) with .efi applications. Linux commonly mounts it at /boot/efi; that mount point is an OS convention, not where firmware finds it.[80][81]

When Secure Boot is enabled and configured, firmware verifies images against its authorized/revoked signature databases. “Any signed executable is allowed” is false, and merely using UEFI does not mean Secure Boot is enabled.[58]

3. Bootloader

GRUB2 on RHEL 9

GRUB presents a boot menu and selects the kernel, initial RAM filesystem and kernel command line. RHEL 9 uses /boot/grub2/grub.cfg as the main generated configuration and Boot Loader Specification entries under /boot/loader/entries/. On UEFI, /boot/efi/EFI/redhat/grub.cfg is a stub; do not replace it with a generated full configuration.[9]

The loader places the kernel image (commonly named vmlinuz-…) and initramfs-….img into memory and transfers control. vmlinuz is a conventional compressed-kernel image name, not a switch that enables virtual memory.[134]

systemd-boot: an alternative

systemd-boot is a UEFI-only boot manager, not RHEL 9’s default GRUB path. An x86-64 installation may place it at EFI/systemd/systemd-bootx64.efi on the ESP. It can select EFI-stub Linux kernels with associated initrds or unified kernel images; its menu and supported layout differ from GRUB.[13]

4. Kernel and initramfs

The conventional x86 compressed kernel image includes decompression/startup code. The kernel establishes CPU state, exception/interrupt handling, physical/virtual memory management and device support for controllers, network interfaces and other peripherals. Built-in drivers initialize as kernel code; loadable modules remain separate objects loaded when needed.[134][9]

The kernel unpacks the initramfs cpio archive into rootfs (ramfs or tmpfs-backed, depending on configuration) and runs its /init as the early userspace process. That environment locates and prepares the real root, potentially activating RAID/LVM, unlocking encrypted storage and loading additional modules. Early microcode loading is its own architecture-specific mechanism, not just another ordinary driver-module load.[11][135]

Early userspace mounts the installed root and uses a switch-root transition to hand control to the installed init system, normally systemd as PID 1 on RHEL 9. This is more than a plain chroot: the early root is replaced and the init process is handed off. Filesystem checking and read-only/read-write transitions depend on filesystem, initramfs and mount configuration; “mount, run fsck, remount” is not a universal sequence. Never repair an actively mounted filesystem by copying that shorthand.[11][9]

5. Init system

/etc/fstab is data consumed by mount tooling and generators, not an executable script. Its fields are Device Mount_point Filesystem Options Dump Pass. systemd translates appropriate entries into mount/swap units. Unit files commonly come from /usr/lib/systemd/system; administrator overrides belong under /etc/systemd/system. Dependencies and ordering constraints govern startup, with independent work able to run concurrently.[97][98][99]

SysV compatibility runlevel systemd target
0 poweroff.target
1 rescue.target — maintenance environment, not merely a getty
2, 3, 4 multi-user.target
5 graphical.target
6 reboot.target

Targets group units; several can be active simultaneously. The runlevel correspondence is a compatibility convention, not systemd’s full state model.[8][48]

Inspect or change the target

Task Command
List loaded active targets systemctl list-units --type=target
Show boot default systemctl get-default
Legacy compatibility view runlevel (where installed); does not enumerate all active targets
Switch this boot to text multi-user mode sudo systemctl isolate multi-user.target
Set text multi-user mode for future boots sudo systemctl set-default multi-user.target

Changing targets is authorized maintenance: isolate can stop services and terminate the current desktop/session. Save work, verify what depends on the current target, record the prior default, and retain console access. set-default changes future boot selection, not the current running target. Verify active units/default afterward; restore the recorded target/default if required. Do not substitute poweroff.target or reboot.target as a harmless exercise.[48]

Legacy init N compatibility requests a numbered runlevel; prefer the explicit systemd operation above on RHEL 9 rather than treating init # as literal syntax.

6. Login and session management

A getty/login path or a display manager handles user login. A successful login creates the user’s session. A command-line shell reads the startup files appropriate to its invocation; a graphical session manager initializes the desktop and may launch terminal shells later. A GUI is not simply a login shell.[128][17]
