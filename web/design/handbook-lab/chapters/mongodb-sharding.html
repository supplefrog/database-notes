A sharded cluster contains replica sets

application -> mongos router A / router B
                 | reads config metadata from cfgRS
                 +-> shard01 replica set (primary + secondaries)
                 +-> shard02 replica set (primary + secondaries)
config servers: cfgRS, three members, cluster metadata

A shard owns ranges of collection data. Each shard’s replica set provides redundancy for those ranges. Config servers hold placement/cluster metadata; routers cache that metadata and target requests. Lose a shard’s availability and requests needing its data fail even if other shards are healthy. Lose config-server majority and metadata operations/balancing become unavailable; do not treat router cache as a replacement backup.[34][73]

Applications connect to mongos, not directly to shards. Shard-local maintenance access is exceptional, separately authorized, and especially constrained in 8.0. Do not grant directShardOperations to application users or write around the router because a command is rejected.[25][34]

Choose a key from access patterns

For shop.orders, primary accesses are tenant + order ID and tenant + recent date. The worked starting key is {tenantId: 1, _id: 1}. Tenant alone has poor cardinality if there are few tenants, and one very large tenant can become a hotspot. The second field permits subdivisions within a tenant, but sequential IDs can still concentrate new inserts. The fixture is too small to demonstrate real distribution.[32]

Candidate Advantage Cost / reject when
{tenantId: 1} Tenant routing and zone affinity Few/hot tenants; identical-key range cannot split usefully
{placedAt: 1} Time-range locality Monotonically increasing ingest concentrates writes
{_id: "hashed"} Distributes many distinct IDs Tenant queries may scatter; hashing does not cure a single repeated hot value
{tenantId: 1, _id: 1} Tenant prefix and precise order routing Within-tenant monotonic insert pressure; date scans need their own index
{tenantId: 1, customerId: 1, _id: 1} Customer-specific routing/locality Tenant-only reads still span its ranges; changed write predicates required

Evaluate cardinality, value frequency, monotonicity, query targeting, write distribution, document growth and zone/residency rules. Use representative production-shaped data and sampled access patterns, not only the three-document exercise. An index can speed work inside a shard without improving router targeting.[20][32]

The shard key is not automatically a uniqueness constraint. Unique indexes on sharded collections must satisfy shard-key restrictions; _id may not enforce global uniqueness when it is not the shard key. Generate globally unique business/order IDs and include tenant context in application requests. Do not create an incompatible unique index and discover the conflict only during sharding.[36][39]

Assemble a secured lab topology

Use new isolated hosts and the pinned 8.0.29 packages. This procedure uses keyfile membership + TLS for a controlled self-managed lab; MongoDB’s production sharded-deployment guidance recommends x.509 security. Review internal-authentication requirements before promoting the lab to production.[13][34][58]

Set/process Hosts Explicit port Role
cfgRS cfg1, cfg2, cfg3.example.net 27019 configsvr
shard01 s1a, s1b, s1c.example.net 27018 shardsvr
shard02 s2a, s2b, s2c.example.net 27018 shardsvr
Router router1.example.net 27017 mongos

Names are examples, not resolvable infrastructure supplied by these notes. On distinct hosts each mongod may use the package /var/lib/mongo and log path; on shared lab hosts every instance needs a different path/service/socket/port and the custom SELinux integration. Never reuse the standalone restore instance’s 27018 on the same host.[6][34]

  1. Provision enforcing RHEL 9 hosts, the mongod policy, the private firewalld matrix, DNS, private reachability, clock synchronization, a CA bundle, unique node certificates with proper SAN/usage, and one shared cluster keyfile across all config/shard/router members. Protect files as in replica setup.
  2. On each config server use the replica-set TLS/security/data/log config, but set these role fields and its own private bindIp:
replication:
  replSetName: cfgRS
sharding:
  clusterRole: configsvr
net:
  port: 27019
  bindIp: 127.0.0.1,cfg1.example.net
  tls:
    mode: requireTLS
    certificateKeyFile: /etc/mongodb/tls/server.pem
    CAFile: /etc/mongodb/tls/ca.pem
    allowConnectionsWithoutCertificates: true
security:
  keyFile: /etc/mongodb/cluster.key
  authorization: enabled
  1. Verify mongod_port_t includes 27019 (do not re-add an existing port), label/secret access and then start the config-server mongod services. On one local TLS shell using localhost exception, initiate once:
rs.initiate({_id: "cfgRS", configsvr: true, members: [
  {_id: 0, host: "cfg1.example.net:27019"},
  {_id: 1, host: "cfg2.example.net:27019"},
  {_id: 2, host: "cfg3.example.net:27019"}
]});
  1. For each shard, use the same secure base, with sharding.clusterRole: shardsvr, port 27018 and replication.replSetName: shard01 or shard02. Verify mongod_port_t includes 27018 and all required scoped connections; start the package mongod service on each dedicated host, then initiate each set once with its corresponding three hostnames. For shard01:[13][34]
rs.initiate({_id: "shard01", members: [
  {_id: 0, host: "s1a.example.net:27018"},
  {_id: 1, host: "s1b.example.net:27018"},
  {_id: 2, host: "s1c.example.net:27018"}
]});

Repeat with _id: "shard02" and s2a/s2b/s2c. Wait for PRIMARY/SECONDARY health. On each shard primary, create a shard-local user administrator via localhost exception, then a narrowly controlled maintenance identity. This closes the individual shard’s bootstrap exception. It does not create application users for the cluster.[7][18]

  1. On a dedicated new RHEL 9 router host, configure the same signed vendor repository, but install mongodb-org-mongos-8.0.29-1.el9.x86_64 and the separately pinned shell. The mongos RPM supplies the router executable/manpage, not a service account, configuration or mongos.service. Do not install/start an unused mongod just to obtain a user.[100][106]
sudo dnf install mongodb-org-mongos-8.0.29-1.el9.x86_64 mongodb-mongosh-2.10.0-1.el8.x86_64
rpm -q mongodb-org-mongos mongodb-mongosh
sudo dnf versionlock add mongodb-org-mongos mongodb-mongosh
# Inspect existing identities first; the next two commands are for a NEW host.
getent passwd mongod
getent group mongod
sudo groupadd --system mongod
sudo useradd --system --gid mongod --no-create-home --home-dir /var/lib/mongo \
  --shell /sbin/nologin mongod
sudo install -d -o mongod -g mongod -m 750 /var/log/mongodb

If the identity already exists, verify its purpose/UID/group and reuse only when appropriate; do not run the creation commands or change an unrelated account. Install that router’s own TLS PEM/CA and the shared cluster.key with the documented ownership/modes. /etc/mongos.conf is root:mongod 0640 and has no storage.dbPath:[6][34]

systemLog:
  destination: file
  path: /var/log/mongodb/mongos.log
  logAppend: true
net:
  port: 27017
  bindIp: 127.0.0.1,router1.example.net
  tls:
    mode: requireTLS
    certificateKeyFile: /etc/mongodb/tls/server.pem
    CAFile: /etc/mongodb/tls/ca.pem
    allowConnectionsWithoutCertificates: true
security:
  keyFile: /etc/mongodb/cluster.key
sharding:
  configDB: cfgRS/cfg1.example.net:27019,cfg2.example.net:27019,cfg3.example.net:27019

Create a root-owned /etc/systemd/system/mongos.service (0644) with foreground supervision; no --fork or PID file. This is a site-owned unit, not a vendor-supplied mongos service:[100][101]

[Unit]
Description=MongoDB sharded cluster router
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=mongod
Group=mongod
Environment="GLIBC_TUNABLES=glibc.pthread.rseq=0"
ExecStart=/usr/bin/mongos --config /etc/mongos.conf
Restart=on-failure
RestartSec=5
LimitNOFILE=64000
LimitNPROC=64000
LimitMEMLOCK=infinity
LimitFSIZE=infinity
LimitCPU=infinity
LimitAS=infinity
TasksMax=infinity
TimeoutStopSec=infinity

[Install]
WantedBy=multi-user.target

Mandatory router confinement gate: MongoDB’s supplied SELinux policy explicitly excludes mongos. Do not relabel /usr/bin/mongos as mongod_exec_t and call it vendor support, nor accept an unconfined_service_t process as production confinement. Before starting, obtain a site-reviewed mongos policy for this exact RHEL build covering executable/domain transition, unit/config/TLS/key reads, log/socket writes, DNS and required outbound/inbound cluster ports. Install the approved policy and its persistent contexts under the platform security process, then verify them with matchpathcon, process context and AVC inspection. No universal policy blob is supplied here: its required access and support ownership depend on the deployment. Without that prerequisite, the router deployment is blocked, not an enforcing-ready production recipe.[103][104][110]

After that gate and the scoped firewall matrix are accepted:

sudo chown root:mongod /etc/mongos.conf
sudo chmod 640 /etc/mongos.conf
sudo restorecon -v /usr/bin/mongos /etc/mongos.conf /etc/systemd/system/mongos.service
sudo restorecon -Rv /etc/mongodb /var/log/mongodb
sudo systemd-analyze verify /etc/systemd/system/mongos.service
sudo systemctl daemon-reload
sudo systemctl start mongos
sudo systemctl status mongos --no-pager
sudo journalctl -u mongos -n 100 --no-pager
sudo ps -eZ | grep mongos
sudo ausearch -m AVC,USER_AVC -ts recent

Match the running domain to the approved router policy, verify logs/TLS/new internal connections and then enable boot start after full cluster acceptance. Keep shutdown supervised; an infinite stop timeout avoids an automatic timed SIGKILL but requires an operator escalation plan for a hung process. mongos membership authentication is enabled by keyFile; do not paste mongod-only options indiscriminately.[6]

  1. Start the router, connect locally over TLS, and use the cluster localhost exception to create useradmin on admin. Authenticate it, create operator with cluster administration and shop roles. This is the cluster user catalog maintained through mongos; do not first create a conflicting cluster user directly on config servers.[7][18]
  2. As authenticated cluster administrator through the router, add the shard replica sets and inspect topology:[34]
sh.addShard("shard01/s1a.example.net:27018,s1b.example.net:27018,s1c.example.net:27018");
sh.addShard("shard02/s2a.example.net:27018,s2b.example.net:27018,s2c.example.net:27018");
sh.status();
db.adminCommand({listShards: 1});

All intended members must be healthy and internally authenticated before admitting clients. If adding a shard fails, inspect set identity, DNS, TLS, keyfile agreement and duplicate databases. Never bypass authentication or hand-edit config metadata to force registration.

Shard and inspect the collection

Load the fixture through mongos in the isolated cluster, not directly into a shard. Use the administrator’s cluster-management privileges and approved index/DDL window:[32][34]

const shop = db.getSiblingDB("shop");
shop.orders.createIndex({tenantId: 1, _id: 1}, {name: "tenant_order_shard"});
sh.shardCollection("shop.orders", {tenantId: 1, _id: 1});
sh.status();
shop.orders.explain("queryPlanner").find({tenantId: "t1", _id: "o1001"});
shop.orders.explain("queryPlanner").find({status: "paid"});

The full-key lookup should be targetable; a status-only query lacks the shard key and may scatter to shards. Inspect the actual router explain output rather than assuming a particular shard count in a tiny dataset. Keep tenant_recent for tenant/date reads: the shard-key index does not replace that sorting access path.[20][24][32]

Chunks/ranges describe keyspace ownership, not fixed-size files. Balancing migrates ranges between shards; config metadata records ownership. A migration may create temporary copies/orphan cleanup work, which is why direct shard counts can mislead and backups must coordinate across the topology.[26][38]

Balance, zones and maintenance

sh.getBalancerState();
sh.isBalancerRunning();
sh.status();

The enabled setting and a currently active balancing round are different observations. Balancer decisions depend on data distribution/thresholds; adding a shard does not guarantee immediate even document counts. Repeated shard-key values can create unsplittable hot ranges. Investigate data/key design, shard disk, replication lag, migration errors and zone restrictions before manually moving ranges.[32][38]

Zones constrain key ranges to selected shards for placement/residency or hardware classes. They do not replace authorization or automatically ensure every copy/backup meets a residency policy. Design zone ranges and matching shard tags together; a missing eligible shard can stop useful balancing.[38]

For backup/upgrade windows, record prior state, stop the balancer, wait for active migrations to finish, perform the coordinated work, then restore prior state and validate. Link the same topology inventory to sharded backup and upgrade ordering; a per-shard “done” is not cluster completion.[25][26]

Reshard without pretending it is free

8.0 Community supports resharding. The example changes the key to {tenantId: 1, customerId: 1, _id: 1} only after a measured customer-locality benefit. It is not a fix required by this fixture. Read the 8.0 procedure in full: one collection at a time, majority journaling enabled, no incompatible unique indexes/index builds, sufficient recipient space and CPU/I/O/oplog headroom. The guide’s storage estimate per recipient is 2 × (collection storage + index storage) / shard count; skew and growth require additional margin.[39][64]

  1. Rehearse on a representative restored cluster; take a coordinated backup and agree latency/write-block budget. Update application query/identity assumptions for the new key.
  2. Save balancer state and stop it. Avoid concurrent DDL/topology changes.
  3. Through mongos, run as a role authorized for resharding:
db.adminCommand({
  reshardCollection: "shop.orders",
  key: {tenantId: 1, customerId: 1, _id: 1}
});
  1. Monitor from another connection with $currentOp on admin, filtering resharding descriptions, and watch per-member disk, lag and errors. The command builds required indexes during its index phase; it is write-intensive and has a write-blocking commit phase. A disconnected client is not proof of cancellation.[39]
  2. Before commit, an approved abort can use the command below. Once commit is reached, abort may be rejected; rollback then is another reviewed reshard/migration or restore, not toggling a setting.[63]
db.adminCommand({abortReshardCollection: "shop.orders"});
  1. After success, verify key/placement, counts and business totals, uniqueness assumptions and routing of actual queries/writes; restore the prior balancer state. Keep old-key query clients from becoming an unexpected scatter workload. In 8.0 the same-key forceRedistribution option also exists, but it is still a resharding operation with these resource/operational costs, not ordinary balancing.[39][64]
