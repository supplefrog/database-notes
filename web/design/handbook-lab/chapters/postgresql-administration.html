Separate ownership from application access

A role may own objects, receive privileges, belong to other roles and optionally log in. Do not make the application the database owner or a superuser simply to avoid grant errors. Ownership includes powers that ordinary grants cannot remove; a no-login owner plus narrow runtime roles gives a clearer boundary.[18][19][59]

Role in this example Login Allowed work
postgres Local OS peer administration Bootstrap, maintenance requiring superuser; never the application identity.
notes_owner No Own database/schema/objects; assumed only by authorized migrations.
notes_read No Read objects explicitly granted in notes.
notes_write No Read and modify rows plus use identity sequences; no schema creation.
notes_app Yes Inherits notes_write; cannot become the object owner.

Run the following once in a fresh cluster as postgres. Stop on errors/name collisions; do not repurpose existing roles without reviewing their memberships.

\set ON_ERROR_STOP on
CREATE ROLE notes_owner NOLOGIN;
CREATE ROLE notes_read NOLOGIN;
CREATE ROLE notes_write NOLOGIN;
CREATE ROLE notes_app LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION;
GRANT notes_write TO notes_app WITH INHERIT TRUE, SET FALSE;
CREATE DATABASE adminlab OWNER notes_owner;
REVOKE ALL ON DATABASE adminlab FROM PUBLIC;
GRANT CONNECT ON DATABASE adminlab TO notes_read, notes_write;

CREATE DATABASE cannot run inside a transaction block. Set a password interactively with psql \password notes_app after confirming SHOW password_encryption is scram-sha-256; never put a password in command history or these notes. The initial local peer policy requires the matching OS identity, so an app without that OS account connects by loopback TCP/SCRAM; remote access additionally requires TLS.[13][15]

\connect adminlab
REVOKE CREATE ON SCHEMA public FROM PUBLIC;
SET ROLE notes_owner;
CREATE SCHEMA notes AUTHORIZATION notes_owner;
GRANT USAGE ON SCHEMA notes TO notes_read, notes_write;
ALTER DEFAULT PRIVILEGES FOR ROLE notes_owner IN SCHEMA notes
  GRANT SELECT ON TABLES TO notes_read;
ALTER DEFAULT PRIVILEGES FOR ROLE notes_owner IN SCHEMA notes
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO notes_write;
ALTER DEFAULT PRIVILEGES FOR ROLE notes_owner IN SCHEMA notes
  GRANT USAGE, SELECT ON SEQUENCES TO notes_write;
ALTER DEFAULT PRIVILEGES FOR ROLE notes_owner
  REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC;
RESET ROLE;

Default privileges apply to future objects created by the specified role, not all future objects in a database and not existing objects. Migrations must SET ROLE notes_owner before creating tables; inherited membership alone does not make that role the creator. A schema-level default grant is additive to global defaults, which is why the function EXECUTE revocation above has no IN SCHEMA clause.[20]

Build one small administration fixture

Use only the new adminlab database. This fixture supports later plan, permission, backup and replication examples; it is not production schema advice. The deterministic generator inserts 2,000 rows. Existing joins teaching remains in the canonical joins lesson, not duplicated here.

\set ON_ERROR_STOP on
BEGIN;
SET LOCAL ROLE notes_owner;
CREATE TABLE notes.orders (
  order_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id integer NOT NULL CHECK (customer_id > 0),
  amount numeric(12,2) NOT NULL CHECK (amount >= 0),
  status text NOT NULL CHECK (status IN ('new','paid','cancelled')),
  created_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP
);
INSERT INTO notes.orders (customer_id, amount, status, created_at)
SELECT (g % 100) + 1, (g % 500)::numeric / 10,
       CASE WHEN g % 3 = 0 THEN 'paid' ELSE 'new' END,
       timestamptz '2026-01-01 00:00:00+00' + g * interval '1 minute'
FROM generate_series(1,2000) AS g;

CREATE VIEW notes.paid_orders AS
SELECT order_id, customer_id, amount FROM notes.orders WHERE status = 'paid';
CREATE FUNCTION notes.touch_order() RETURNS trigger
LANGUAGE plpgsql SECURITY INVOKER
SET search_path = pg_catalog
AS $$
BEGIN
  NEW.updated_at := CURRENT_TIMESTAMP;
  RETURN NEW;
END;
$$;
CREATE TRIGGER orders_touch BEFORE UPDATE ON notes.orders
FOR EACH ROW EXECUTE FUNCTION notes.touch_order();
COMMIT;
ANALYZE notes.orders;
SELECT count(*), min(order_id), max(order_id), sum(amount) FROM notes.orders;

A trigger function returns the row to store; SECURITY INVOKER uses the caller’s privileges instead of elevating to the owner. This timestamp trigger is not an audit trail: it records neither old values nor authenticated actor. A normal view is stored query text, not a physical copy; its owner’s access can matter, so review view security before using one to expose restricted data.[50][77]

Identity generates values through an implicit sequence; the primary key separately enforces uniqueness. Allocations can have gaps. A manual import of explicit IDs must resynchronize the sequence before writers resume; see migration.[48][60]

For existing objects that predate the defaults, apply grants explicitly as owner:

SET ROLE notes_owner;
GRANT SELECT ON ALL TABLES IN SCHEMA notes TO notes_read;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA notes TO notes_write;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA notes TO notes_write;
RESET ROLE;

Do not grant TRUNCATE, TRIGGER, ownership or CREATE just to support ordinary inserts. Extension installation is separate: first install its reviewed package for major 18, inspect pg_available_extensions, then CREATE EXTENSION in the intended database using required privileges. Some modules additionally require preloading and a restart.[19][54]

Verify permissions, including denials

\du+
\dn+
\dp notes.*
\ddp
SELECT has_database_privilege('notes_app','adminlab','CONNECT'),
       has_schema_privilege('notes_app','notes','USAGE'),
       has_table_privilege('notes_app','notes.orders','INSERT'),
       has_schema_privilege('notes_app','notes','CREATE');

Connect in a new session as notes_app using the approved endpoint. Do not trust only an inspection query executed as superuser. Use the bootstrap loopback SCRAM endpoint before hardening, or the verified TLS endpoint afterward.[14][18][19]

SELECT current_user, current_database();
SELECT order_id, amount FROM notes.orders ORDER BY order_id LIMIT 3;
BEGIN;
INSERT INTO notes.orders(customer_id, amount, status)
VALUES (42, 1.25, 'new') RETURNING order_id;
ROLLBACK;

The row insert must succeed and leave no row after rollback; its consumed identity value is not reclaimed.[60] Separately, in interactive psql (not in the setup script), run CREATE TABLE notes.denied_test(id integer); and SET ROLE notes_owner;. Both must fail with a permission error. If either succeeds, stop: review unexpected memberships/ownership before any application use. Do not silently drop an unexpectedly created object as though the test passed. Test readers separately because another inherited group can restore a revoked permission.

Change Command Limit
Block new logins ALTER ROLE notes_app NOLOGIN; Existing sessions remain; separately review termination.
Remove a membership REVOKE notes_write FROM notes_app; Direct/other inherited grants may still allow access.
Restore login ALTER ROLE notes_app LOGIN; HBA/password/database grants must also permit it.
Change password \password notes_app Rotation does not disconnect old sessions.
Remove a role DROP ROLE role_name First resolve ownership and dependencies in every database.

For decommissioning, inventory owned/shared objects, reassign ownership to the approved successor, and revoke remaining privileges in each database before dropping the role. DROP OWNED can delete objects; it is not a harmless grant cleanup when the role still owns data. Keep a dependency report and backup. HBA is a connection filter, not an alternative to object grants.[14][19]

Use psql for inspection and repeatable scripts

Command/option Purpose Scope/caution
\conninfo, \l+, \dn+ Connection, databases, schemas Check port/database before mutation.
\dt notes.*, \d+ notes.orders, \di notes.* Tables, table detail, indexes Pattern and search path affect what is shown.
\df+ notes.*, \dv notes.*, \dx Functions, views, installed extensions Inspect definitions/owners, not only names.
\x auto, \pset pager off, \timing on Expanded output, no pager, elapsed time Client presentation, not server settings.
\o /secure/report.txt, then \o Begin/end query-output capture Protect files; query results can contain secrets.
-f reviewed.sql -v ON_ERROR_STOP=1 -X Script with failure exit status, no startup file Wrap suitable SQL in a transaction if all-or-nothing is needed.
--single-transaction / -1 One transaction around -f/-c work Not for CREATE DATABASE, VACUUM, concurrent index creation.
\copy ... Client-side file import/export Server COPY '/path' reads server files and needs separate privileges.

These flags are psql behavior, not SQL executed by the server.[13]

# Local administrator, reviewed script; no password in arguments.
sudo -u postgres /usr/pgsql-18/bin/psql \
  -X -v ON_ERROR_STOP=1 -h /run/postgresql -p 5432 -d adminlab -f /secure/reviewed.sql

The OS account executing psql must be able to read/write its script/output paths. \copy (SELECT order_id, amount FROM notes.orders ORDER BY order_id) TO '/secure/orders.csv' WITH (FORMAT csv, HEADER true) writes on that client. Secure reports and delete them under the same retention policy as exported data.

Change settings at the right scope

There is no universal MySQL SET GLOBAL translation. Some parameters are session-settable, some superuser-only, some reloadable, and some startup-only. Query pg_settings.context, source, sourcefile and pending_restart before changing one.[12][58]

Mechanism Example Lifetime / reversal
Inspect SHOW work_mem; Current session’s effective value.
Transaction-local SET LOCAL statement_timeout = '10s'; Ends on commit/rollback; use inside BEGIN.
Session SET work_mem = '16MB'; Until reset/disconnect; RESET work_mem.
Database default ALTER DATABASE adminlab SET statement_timeout = '30s'; New sessions; ALTER DATABASE adminlab RESET statement_timeout.
Role/database default ALTER ROLE notes_app IN DATABASE adminlab SET lock_timeout = '2s'; New matching logins; same command with RESET lock_timeout.
Config file Edit postgresql.conf or controlled includes Reload or restart per context; restore recorded previous value.
Persistent SQL ALTER SYSTEM SET log_min_duration_statement = '500ms'; Writes postgresql.auto.conf; then reload. Undo with ALTER SYSTEM RESET ..., then reload.

postgresql.auto.conf overrides the main file; command-line settings can override files; role/database/session settings override applicable defaults. File includes and duplicate entries have order. Do not let automation and manual ALTER SYSTEM silently fight over the same parameter. ALTER SYSTEM cannot run in a transaction block.[12]

SELECT name, setting, unit, context, source, sourcefile, pending_restart
FROM pg_settings
WHERE name IN ('work_mem','shared_buffers','statement_timeout',
               'listen_addresses','log_min_duration_statement');
SELECT pg_reload_conf();
SELECT name, setting, pending_restart FROM pg_settings
WHERE pending_restart;

Reload returning true means a signal was sent, not that every setting parsed/applied. Check file errors, server logs and a fresh session’s value. Restart settings such as port/shared buffers require a scheduled service restart, not repeated reloads.

Inspect and stop a session deliberately

SELECT pid, usename, application_name, client_addr, state,
       xact_start, query_start, wait_event_type, wait_event,
       pg_blocking_pids(pid) AS blockers, left(query, 160) AS query
FROM pg_stat_activity
WHERE datname = 'adminlab' AND pid <> pg_backend_pid()
ORDER BY xact_start NULLS LAST;

Query text can contain sensitive values; monitoring privileges and captured reports must be restricted. Ordinary users see limited information about others; grant monitoring roles deliberately rather than superuser.[25]

Action Meaning Decision before use
SELECT pg_cancel_backend(&lt;confirmed_pid&gt;); Cancel the active query, keep session Confirm PID, user, query start and application; the transaction may still require rollback.
SELECT pg_terminate_backend(&lt;confirmed_pid&gt;, 5000); Disconnect session, abort active transaction; wait up to 5 seconds Coordinate app retry and possible external side effects; does not undo already committed work.

The angle-bracket PID is deliberately not runnable SQL. Re-query the exact target immediately before signaling to avoid PID reuse. Permissions depend on role membership/pg_signal_backend; only superusers may signal superuser backends. A true cancellation return is not proof a business action was reversed—read back activity and application state.[23]

For an idle-in-transaction blocker, cancelling a nonexistent running query is insufficient: ask its owner to commit/rollback, or terminate only after incident review. Continue with wait and performance analysis.
