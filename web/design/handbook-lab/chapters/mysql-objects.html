Database objects

Use a database name you are authorized to inspect. Definition visibility depends on privileges; SHOW output can expose definer accounts and routine source.

Object List objects Show definition
Procedure SHOW PROCEDURE STATUS WHERE Db='app'; SHOW CREATE PROCEDURE app.procedure_name\G
Function SHOW FUNCTION STATUS WHERE Db='app'; SHOW CREATE FUNCTION app.function_name\G
View SHOW FULL TABLES IN app WHERE Table_type='VIEW'; SHOW CREATE VIEW app.view_name\G
Trigger SHOW TRIGGERS FROM app; SHOW CREATE TRIGGER app.trigger_name\G; Information Schema exposes ACTION_STATEMENT too.
Event SHOW EVENTS FROM app; SHOW CREATE EVENT app.event_name\G

Names ending _name above are identifiers to substitute, not objects this chapter creates.

Sessions and server status

In the interactive mysql client, status or \s reports connection details and selected server status such as uptime, threads, open tables, slow queries and average query rate. It is a client command, not SQL usable through every connector. mysqladmin --user=operator --password status provides related server counters; processlist --sleep=2 polls sessions rather than status counters.

SHOW FULL PROCESSLIST;
SELECT * FROM sys.processlist;

These show connection IDs, account/host/database, command, elapsed state time and current state/query. Visibility into other users’ sessions requires additional privilege. The INFORMATION_SCHEMA.PROCESSLIST implementation is deprecated in 8.4; prefer the Performance Schema-based interfaces.

Cancel a query or disconnect a session

KILL QUERY connection_id cancels a statement; KILL CONNECTION connection_id terminates the connection. connection_id is a MySQL connection/thread identifier, not an OS PID. Confirm the current owner/query before acting because IDs can be reused. Cancellation can trigger expensive rollback; do not repeatedly kill a recovering operation. Account privileges govern which sessions you may kill.

Table Management

Tablespace growth

Source setting/operation Correct 8.4 interpretation
innodb_data_file_path=ibdata1:10M:autoextend:max:512M Startup system-tablespace layout example, not a live resize or shrink command. Do not apply a different initial size over an existing file. A small maximum can stop writes. Plan initialization/growth against actual files and backup/restore requirements.
innodb_autoextend_increment=64 Growth increment in MiB for the auto-extending system tablespace; not a universal size for every .ibd.
CREATE TABLESPACE ... INITIAL_SIZE=100M INITIAL_SIZE belongs to NDB syntax, not an InnoDB initial-allocation option. For InnoDB general tablespaces, AUTOEXTEND_SIZE controls extension increments (multiple of 4 MiB), not an arbitrary initial file size.

Auto-increment and temporary tables

ALTER TABLE table_name AUTO_INCREMENT=value is a schematic DDL operation: choose a permitted value above existing generated values. It does not renumber old rows or safely recycle identifiers. Concurrent inserts and engine rules affect the next value.

The examples in this section are independent of the later data generator. First select a deliberately created empty scratch schema with USE your_scratch_schema; (replace that identifier); app elsewhere means an existing application schema, not this fixture. A complete temporary-table example:

CREATE TEMPORARY TABLE customers (
  customer_id BIGINT PRIMARY KEY,
  name VARCHAR(100) NOT NULL
) ENGINE=InnoDB;

The table is session-local and disappears when that session ends. A same-named permanent table can be hidden in that session; explicitly identify scratch objects and do not assume temporary-table DDL follows ordinary rollback semantics.

General tablespaces

The following creates new objects and requires a scratch schema, suitable privileges, an unused datafile name and disk space:

CREATE TABLESPACE ts ADD DATAFILE 'ts.ibd' ENGINE=InnoDB;
CREATE TABLE t1 (
  id INT PRIMARY KEY,
  name VARCHAR(50)
) TABLESPACE ts ENGINE=InnoDB;

A relative datafile location is resolved under the applicable datadir rules. Do not copy/move the file manually while the server owns it. Dropping a table does not return a general tablespace’s allocated file size to the OS.

[21][25][26][129]

Change storage engine

Back up and rehearse before conversion. ALTER TABLE table_name ENGINE=InnoDB; can rebuild the table, change locking/storage behavior and consume substantial extra space. Check unsupported engine-specific features and dependent code; verify row counts, constraints and application behavior before accepting the conversion. Reverting the engine is not a substitute for a tested backup.

Generate bounded dummy data

The original procedure created successively numbered tables and generated one million SHA-256 values through a recursive CTE. Keep this as a load-generation task, not a production tuning command. A million-row run needs a deliberate resource budget; start with at most 1,000 rows in a disposable schema, never a shared schema named test whose ownership is unknown.

The procedure below preserves dynamic table creation, numeric suffix discovery, prepared statements, recursive CTE generation and hash values, but takes a bounded row count. It must run in the interactive mysql client (DELIMITER is not server SQL). The following CREATE DATABASE must succeed for a new scratch_mysql schema (stop if it already exists); do not reuse another exercise’s schema. Use that new empty schema and use a single session; concurrent calls can choose the same table number. The procedure deliberately leaves its created table for inspection. DDL is not rolled back if later insertion fails.

CREATE DATABASE scratch_mysql;
DELIMITER $$
CREATE PROCEDURE scratch_mysql.create_dummy_data(IN row_limit INT)
BEGIN
  DECLARE n INT;
  IF row_limit IS NULL OR row_limit < 1 OR row_limit > 1000 THEN
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT='row_limit must be 1..1000';
  END IF;
  IF @@session.cte_max_recursion_depth < row_limit THEN
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT='session recursion limit is too small';
  END IF;
  SELECT COALESCE(MAX(CAST(SUBSTRING(table_name,2) AS UNSIGNED)),0)+1 INTO n
    FROM information_schema.tables
    WHERE table_schema='scratch_mysql' AND table_name REGEXP '^t[0-9]+$';
  SET @dummy_table=CONCAT('scratch_mysql.t',n);
  SET @dummy_sql=CONCAT('CREATE TABLE ',@dummy_table,
    ' (id INT AUTO_INCREMENT PRIMARY KEY, hash CHAR(64)) ENGINE=InnoDB');
  PREPARE dummy_stmt FROM @dummy_sql;
  EXECUTE dummy_stmt;
  DEALLOCATE PREPARE dummy_stmt;
  SET @dummy_sql=CONCAT('INSERT INTO ',@dummy_table,' (hash) ',
    'WITH RECURSIVE cte(n) AS (SELECT 1 UNION ALL SELECT n+1 FROM cte WHERE n<',
    row_limit,') SELECT SHA2(n,256) FROM cte');
  PREPARE dummy_stmt FROM @dummy_sql;
  EXECUTE dummy_stmt;
  DEALLOCATE PREPARE dummy_stmt;
END$$
DELIMITER ;
CALL scratch_mysql.create_dummy_data(100);

Inspect the created table’s count and hashes and the actual resource use; no expected output is fabricated here. For a larger load, deliberately revise/test a generator in a disposable instance, choose batches or an appropriate nonrecursive data-generation method, and budget redo/binlog/disk/replication load. Do not just set cte_max_recursion_depth=1000000 in an unrelated session. Remove only the confirmed disposable objects when finished.
