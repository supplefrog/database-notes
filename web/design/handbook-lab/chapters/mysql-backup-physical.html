Backup and recovery

Applies to MySQL Server 8.4 LTS; the production baseline is RHEL 9 x86_64 with Oracle MySQL Community RPMs from the MySQL Yum repository. Separately licensed products and other platforms are identified explicitly.[1][72]

Choose a physical backup product first

Physical backups are server-format dependent. Percona XtraBackup 8.4 and MySQL Enterprise Backup 8.4 (mysqlbackup) are separate products with separate compatibility/support matrices, licensing and command dialects. Select an exact backup-tool build supported for the exact MySQL 8.4 server patch/edition and encryption/compression features. Do not bypass server-version checks or feed one tool’s backup into the other.

Percona XtraBackup 8.4

After provisioning the documented backup account/OS read access, use a new or empty private backup destination. Provision authentication in a restricted option file outside the backup, using the selected build’s documented option groups. Confirm its handling with that exact release; do not assume MySQL client password-prompt behavior applies to every backup tool. These Linux patterns show a full uncompressed, unencrypted-by-tool backup; tablespace encryption still needs supported keyring handling:

xtrabackup --defaults-file=/secure/xtrabackup.cnf --backup --target-dir=/backups/full
xtrabackup --prepare --target-dir=/backups/full

--defaults-file is first and names a pre-provisioned protected file containing the intended instance options and backup identity; /secure/xtrabackup.cnf is a site input, not a supplied credential file. Preparation modifies the backup; retain an immutable original if it must be reused in another recovery chain. Restore only with the target server stopped, the chosen datadir empty, compatible binaries/configuration/keyring available and a retained pre-restore backup:

xtrabackup --copy-back --target-dir=/backups/full --datadir=/srv/mysql-restore

Correct OS ownership, labels and access before starting. --datadir, not --data-dir, selects the target here; --incremental-dir does not belong on --copy-back.

For incrementals, take a base, then each --backup --incremental-basedir=/backups/previous --target-dir=/backups/next, with the same reviewed instance/authentication configuration. Verify LSN continuity. Prepare the base with --apply-log-only, then apply intermediate incrementals in order to that base with --prepare --target-dir=/backups/full --incremental-dir=/backups/next --apply-log-only. Apply the final incremental without --apply-log-only so that final rollback/preparation completes before copying the prepared base back. Follow the exact 8.4 guide’s sequence and never reuse an already merged incremental directory as if untouched.

--target-dir Backup directory, not SQL database or live datadir.

MySQL Enterprise Backup 8.4

Requires a licensed compatible Enterprise Backup build; the program is mysqlbackup, not mysqld. Full directory backup and prepare use action words, not XtraBackup’s flags:

mysqlbackup --user=backup --password --backup-dir=/backups/meb-full backup
mysqlbackup --backup-dir=/backups/meb-full apply-log

For a prepared directory restore to a stopped, empty target with reviewed target option files:

mysqlbackup --defaults-file=/etc/mysql-restore.cnf --backup-dir=/backups/meb-full copy-back

--defaults-file must be first among options and must describe the intended restore instance. copy-back-and-apply-log combines preparation/restoration where the product supports it; it is not an XtraBackup command.

Source option/task Enterprise Backup qualification
--backup-image with backup-to-image Single-file image backup plus a separate working --backup-dir; image restore/validation follows the image workflow, not an assumed directory copy.
--incremental, --incremental-base Select incremental backup and its base (dir: or supported history reference); preserve the entire ordered base/incremental chain. Use MEB incremental application commands, not XtraBackup --incremental-dir.
--include-tables, --exclude-tables Partial backup selection; review regex and restore restrictions.
GTID-related flags Do not copy the source’s --include-purge-gtids=off blindly. Decide GTID preservation from the exact MEB command/reference and intended replica/recovery workflow. A physical restore inherits server state.
--no-locking Not a default speed switch; can compromise consistency for mixed engines/DDL. Use only with documented external consistency guarantees.
--skip-binlog Affects captured logs, not the requirement for an archived PITR chain.
--encrypt, --compress Require the documented algorithms/key custody and restore handling for this product. Do not attach generic decrypt/uncompress flags borrowed from another tool.
--with-timestamp Optional directory organization; ensure the actual resulting directory is used for prepare/restore.
--process-threads, --read-threads, --write-threads Distinct processing/I/O parallelism controls; not XtraBackup’s --parallel.
validate Physical-backup validation, e.g. mysqlbackup --backup-dir=/backups/meb-full validate; it does not detect missing .ibd/.sdi files or every truncation, and directory validation is limited to InnoDB data files. Independently verify the backup inventory and start a restored server to verify data/application behavior.

For compressed/encrypted images or incrementals, choose the corresponding MEB 8.4 restore procedure from the manual before taking the backup. The simple full-directory examples above intentionally do not pretend to cover these mutually different formats. Test key access, complete application replay/PITR, accounts/replication state, RPO and RTO in an isolated restored instance.

Accept a restored RHEL instance, not just copied files

Use the configured target unit and its actual datadir for restore: a tool’s --datadir=/srv/mysql-restore alone does not change /etc/my.cnf, sockets, unit mount ordering, SELinux or application routing. Follow the relocation path/security checks for the restore directory, keep NO_INIT protection appropriate to an already restored datadir, and retain a recoverable pre-restore copy. Do not silently start an empty default directory instead of the restored tree.

Before first restored startup, isolate network access/outbound jobs, configure event_scheduler=OFF, and prevent automatic replication start (skip_replica_start=ON for asynchronous channels; Group Replication has its separate group_replication_start_on_boot=OFF). A physical copy can contain live accounts, channel credentials and the original auto.cnf; it must not accidentally join production under a duplicate server identity. Same-instance disaster recovery preserves its identity only after the lost host is fenced. A new replica/clone has its own documented UUID provisioning path; do not delete auto.cnf from the production source.

Acceptance records include backup inventory/checksums and tool exit status; successful prepare and intended unit startup; readable encrypted tables with recovered keys; complete objects/definers/accounts; independent keyed data reconciliation and business queries; exact binlog/GTID recovery boundary; and measured RPO/RTO. Confirm intended SELinux process/file contexts, a new verified-TLS session and rejected unapproved network access. A checksum, green service, zero lag, or backup utility’s validate output proves only its own limited property, not the entire recovery claim.

Transport an InnoDB file-per-table tablespace

This is a restricted table-transfer workflow, not a general full backup. Verify the documented source/target version, page size, row format, partition, encryption and foreign-key restrictions. Create the exact matching definition on the destination first and ensure its existing data is disposable/backed up. General/system tablespace tables cannot be treated as arbitrary standalone .ibd files.

  1. On the source, keep one session open with FLUSH TABLES app.table_name FOR EXPORT;. This is a SQL lock held by that session; do not disconnect before copying.
  2. While the lock is held, use an OS file-copy tool to copy the matching .ibd and export .cfg files to protected staging. For encrypted tables, follow the documented .cfp/key transfer requirements too. Verify the copy and only then UNLOCK TABLES; in the source session. cp is not SQL.
  3. On the destination, create the exact table definition, then ALTER TABLE app.table_name DISCARD TABLESPACE; only for the intended empty/disposable table. This discards its current tablespace; do not apply it to a populated production table.
  4. Copy the staged table files into the destination table’s actual schema path, apply correct MySQL ownership/permissions/SELinux context, and verify compatibility before ALTER TABLE app.table_name IMPORT TABLESPACE;.
  5. Read import warnings/errors, compare definition/row counts/data and relevant foreign-key relationships, then test application queries. Keep the source/export until validation is complete; do not delete production source data because import returned success.

The source’s missing destination file-copy step is essential. Quiesce related tables together when consistency spans relationships; independent exports are not an atomic multi-table backup.

Rotate text logs, not database recovery files

On EL9 use the package’s existing logrotate configuration as the starting point. Confirm whether the error log goes to a file, journald or a configured log component. FLUSH ERROR LOGS and FLUSH SLOW LOGS require suitable privileges and apply only to the matching file logging setup; logrotate does not restart arbitrary logging components.

Original directive Meaning and deployment check
/var/log/mysql/mysql_error.log /var/log/mysql/slow_query.log Example paths only; use actual configured paths. EL9 RPM error-log defaults often differ. Avoid duplicate stanzas managed by the package.
compress Compress rotated text files; consider delaycompress until the server has reopened the new file successfully.
create 660 mysql mysql Mode/owner/group of the new file. Prefer only the readers required by policy; 0640 may suffice. Verify service access and SELinux labels.
size 1G Rotate when size exceeds this threshold at a scheduled logrotate run; not a hard maximum enforced continuously.
dateext Date-based archive naming; frequent rotations may need adequate date granularity.
missingok, notifempty Tolerate absent/empty files; do not use these to hide missing required audit data.
sharedscripts Run the reopen action once for the grouped files.
postrotate / endscript Reopen logs via an authorized local MySQL connection; ensure the scheduled OS identity can access the intended restricted login path/socket. An operator’s personal login path is not automatically root’s or the service user’s.
rotate 30 Keep up to 30 rotated files, not necessarily 30 days; align with retention/security requirements.

Inspect logrotate’s dry-run/debug output with the real local configuration, then perform a controlled test: server must write to the new file and archives must remain readable by authorized operators. Do not place credentials in the stanza. Do not send binlogs, relay logs, redo, undo, .ibd or Enterprise Audit files through this generic text-log recipe; they have their own managed retention/rotation interfaces.
