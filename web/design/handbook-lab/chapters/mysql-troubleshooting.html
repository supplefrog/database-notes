Applies to MySQL Server 8.4 LTS; the production baseline is RHEL 9 x86_64 with Oracle MySQL Community RPMs from the MySQL Yum repository. Separately licensed products and other platforms are identified explicitly.[1][72]

Diagnose startup in order

For the selected EL9 RPM service:

systemctl status mysqld.service
journalctl -u mysqld.service -b
mysqld --verbose --help

Read the configured MySQL error log as well. Verify configuration syntax, port/socket conflicts, free space, mounted data/key directories, OS ownership and SELinux denials. sudo systemctl reset-failed mysqld.service clears the start-limit state after fixing the cause; it does not repair MySQL. Do not reinitialize a nonempty datadir to cure startup errors.

OS security

firewalld

Firewalld zones/rich rules can constrain traffic by source address, service, port and protocol. Inspect the active interface’s zone first; the default zone may not be the one serving MySQL.

firewall-cmd --get-active-zones
firewall-cmd --zone=public --list-all

Choose the actual zone and approved application/replica source CIDRs. Prefer a source-restricted rich rule to opening mysql to an entire untrusted zone. --add-service=mysql refers to the service definition’s ports; a custom port uses --add-port=3307/tcp. These are alternatives, not requirements to expose both ports. Test a runtime rule, preserve console access and existing SSH rules, then persist only the approved rule. --reload applies permanent configuration and can discard temporary rules; review before doing so. Do not expose X Protocol or replication-internal ports merely because a classic-protocol client needs 3306.

SELinux

Keep enforcement enabled. Inspect the installed policy and AVC denials; label the intended path/port, not every similarly named directory.

semanage port -l | grep mysqld
semanage fcontext -l | grep mysqld

For a deliberately selected new port 3307 that is not already assigned to another type, the policy operation is semanage port -a -t mysqld_port_t -p tcp 3307; an existing entry may need -m after inspection. Use -d only to remove a rule you intentionally own. For a moved standard datadir, follow the configuration chapter’s equivalence mapping and restorecon procedure; it preserves differentiated data/socket rules instead of labeling every object as database data. If an entry already exists, review/modification is required instead of repeating -a. Match log/socket/key paths to their appropriate policy types, and restore the previous mapping if rolling back. OS permissions and SELinux policy must both permit access.

Background processes are not service management

Mechanism What it actually does
processname & Runs asynchronously in the shell’s job context; TTY/session/hangup behavior depends on shell and process. The TTY is not the parent process.
nohup processname & Ignores SIGHUP and conditionally redirects terminal streams; does not create a complete supervised service.
setsid processname Starts a new session when possible; does not automatically close inherited descriptors, drop privileges, restart on failure or guarantee reparenting to PID 1.
systemd unit Supervises a service with explicit identity, environment, lifecycle and resource controls. Use this for the RPM MySQL instance.

Historical nohup mysqld --defaults-group-suffix=1 & / setsid mysqld ... examples demonstrated shell detachment, not a recommended way to bypass the installed unit. Starting a second server against the same datadir is unsafe. Use named units and unique datadirs/ports/sockets instead.

A source-restricted runtime rule with explicit acceptance

Use this only after authorizing the interface, zone, source network and listener. Here public and 192.0.2.0/24 are documentation inputs to replace, not a production recommendation. Inspect both runtime and permanent zone settings first: a broader existing mysql service/port/rich rule or trusted source can already admit traffic, and adding a narrow allow rule does not revoke that access.

sudo firewall-cmd --get-active-zones
sudo firewall-cmd --zone=public --list-all
sudo firewall-cmd --permanent --zone=public --list-all
sudo firewall-cmd --zone=public --add-rich-rule='rule family="ipv4" source address="192.0.2.0/24" port port="3306" protocol="tcp" accept' --timeout=300

Test a new identity-verified TLS connection from an allowed host, rejection from a disallowed host, and a new SSH management connection before the temporary rule expires. IPv6 needs its own deliberately restricted policy; an IPv4 allow test does not validate IPv6. Preserve console access. If accepted, add the same exact rule with --permanent (without --timeout) and as a non-timed runtime rule after removing the timed copy if still present. Query both copies with --query-rich-rule and test again. Avoid --runtime-to-permanent when unrelated transient rules are present. A later planned reload/reboot must retain only the approved access. Rollback removes only this exact rule from runtime and permanent configuration with --remove-rich-rule; do not flush the zone or stop firewalld.

A firewall opening cannot make an unbound or SELinux-denied listener work. For SELinux tooling on RHEL 9 install policycoreutils-python-utils through the approved Red Hat repositories if absent. Inspect getenforce, ls -lZ, matchpathcon, ps -eZ and sudo ausearch -m AVC,USER_AVC -ts recent to distinguish DAC/path labeling, port labeling and genuine policy needs. Repair the specific cause; do not use setenforce 0, disable SELinux, or blindly generate audit2allow policy as the operating solution.

Multiple instances versus multiple databases

Dimension Separate instances Multiple databases in one instance
Data integrity Separate dictionaries/storage; no cross-instance foreign-key enforcement. Never share one datadir between processes. Cross-schema relations can be supported within one server/engine.
Availability Independent restart boundaries, but same-host instances share host/storage failure. HA requires a designed topology and failure domains. A server outage affects all schemas.
Security Separate accounts/configs can reduce blast radius; same OS account/root access can defeat isolation. No automatic regulatory compliance guarantee. Grants/roles can restrict schemas, but share privileged administration and server resources.
Backup/maintenance/recovery Each instance needs its own jobs, monitoring and restore plan; selective maintenance can spare others. Fewer server jobs, but consistency and restore scope need attention.
Cost More operational/resource overhead; dedicated tenant instances may be justified. Simpler consolidation for workloads that can safely share limits.
Performance Separate buffer pools and processes, not reserved CPU/RAM/I/O unless OS/cgroup/storage controls allocate them. Sum all budgets. Workloads contend within the same server; schema separation is not a resource governor.
Scalability An instance can be moved/scaled independently after dependency review. Adding schemas is simple but does not remove instance limits.

For RPM templates use [mysqld@replica01] with the matching mysqld@replica01.service. Give each instance a unique datadir, socket, classic/X ports where enabled, PID/error/relay/binlog paths and replication identity. The instance appendix preserves and corrects the template. Never clone a datadir as a generic way to create independent server UUIDs.

Named instances on the RPM platform

Target: RHEL 9 x86-64 Oracle MySQL 8.4 RPMs. Use the package-provided mysqld@.service; the original template below is historical, not a portable service download. See the single-instance appendix for the common directive-by-directive review, including the incorrect EnvironmentFile assignment, notify/forking mismatch and deprecated identity control.

Instance expansion and path isolation

The source’s ExecStartPre=... %I passes the unescaped instance name to the RPM helper. --defaults-group-suffix=@%I makes instance replica01 read [mysqld@replica01] in addition to common groups. It does not read [mysqld1]. Verify the installed unit’s exact command rather than copying an ordering of --defaults-file and suffix options that the server will reject.

A per-instance option-file illustration, after its distinct directory/ownership/mount/SELinux plan is prepared:

[mysqld@replica01]
datadir=/var/lib/mysql-replica01
socket=/var/lib/mysql-replica01/mysql.sock
port=3307
log-error=/var/log/mysqld-replica01.log

This is not a complete replication configuration. Decide unique server IDs/UUIDs, binlog/relay-log locations, PID files and X Protocol listener/socket if enabled. A common inherited pid-file, mysqlx_port or log path can still collide even with separate classic ports. Sum memory budgets and use OS resource controls if resource isolation is required; shared-host instances do not provide host-failure HA.

  1. Inventory vendor/common settings and existing instances; ensure new paths are empty intentionally, not unmounted production data.
  2. Configure each unique suffix group, owned paths and security policy, then validate the selected configuration.
  3. Start the specific instance with systemctl start mysqld@replica01.service. Inspect that exact unit’s journal and error log; connect using its socket/port and verify @@datadir, @@port, server identity and intended objects.
  4. Only after verification, decide whether systemctl enable mysqld@replica01.service should make it start at boot. Test mount/order dependencies.
  5. On failure stop/repair only the intended instance. Keep prior config/data for rollback and do not run both units over the same datadir.

All original template fields are retained in the historical text. Their common meanings are unchanged from the single-instance review except for %I, @%I and the need to avoid shared runtime/storage resources.

Provision the named instance’s RHEL paths

Keep this second instance local initially: add bind_address=127.0.0.1, mysqlx=OFF (unless separately provisioned), pid-file=/run/mysqld/replica01.pid and a chosen unique nonzero server_id to [mysqld@replica01]. Retain the standard package-managed /run/mysqld runtime directory and verify the installed unit/tmpfiles setup recreates it at boot. Do not inherit the default instance’s PID/socket/log paths. The datadir below must be a deliberately new empty directory; creating it on top of missing storage is not acceptable.

After reviewing existing SELinux local rules and approving this path:

sudo install -d -o mysql -g mysql -m 0750 /var/lib/mysql-replica01
sudo semanage fcontext -a -e /var/lib/mysql /var/lib/mysql-replica01
sudo restorecon -Rv /var/lib/mysql-replica01
matchpathcon /var/lib/mysql-replica01/mysql.sock
matchpathcon /var/log/mysqld-replica01.log
semanage port -l | grep mysqld

Confirm the socket’s expected type is mysqld_var_run_t; verify/restore the named error log’s mysqld_log_t after creation and inspect the PID label. The Oracle RPM helper only assists automatic error-log creation for its documented /var/log/mysql*.log pattern; an arbitrary new log directory is your provisioning responsibility. Register port 3307 as mysqld_port_t only if needed after inspecting the actual policy; do not reassign a port owned by another service. No firewall opening is needed for this loopback-only initial instance.

Check all inherited groups and run /usr/sbin/mysqld --defaults-group-suffix=@replica01 --validate-config with appropriate config-read authority. If NO_INIT=true is already set for existing production units, do not turn it off globally just to create this one instance. After verifying the new empty paths/options, explicitly initialize only this instance using sudo /usr/sbin/mysqld --defaults-group-suffix=@replica01 --initialize --user=mysql; inspect its own protected error log for the temporary password. Otherwise the reviewed vendor helper may perform first initialization. These are alternative paths: never initialize twice or use --initialize-insecure to avoid credential handling.

Start mysqld@replica01.service, complete its interactive account hardening against its explicit socket, and verify it with mysql --protocol=SOCKET --socket=/var/lib/mysql-replica01/mysql.sock --user=root --password. Compare both instances’ datadir, server UUID, ports, PID and logs; verify stopping the new unit leaves the original instance healthy. Add per-instance mount dependencies where needed and test restart before boot enablement. Remote exposure then follows the TLS/SELinux/firewall procedure for 3307, not a copied 3306 service rule. All instances share one installed server binary/package update: separate units do not provide independent MySQL versions or rolling binary upgrades on one host.
