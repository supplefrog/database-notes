Choose the upgrade mechanism

A minor update (18.x to a later 18.x) replaces binaries without a major-format conversion. A major update (for example 17 to 18) requires pg_upgrade, logical dump/restore or a planned logical-replication migration. Never start an 18 binary on a 17 data directory. PostgreSQL does not require visiting every intervening major, but you must review their compatibility notes.[1][37]

Route Strength Main constraint
Minor package update Short restart, unchanged major format Read that minor’s release notes for extra actions; binaries/extensions must remain compatible.
pg_upgrade default copy Fast catalog conversion without logical row reload Both major binaries, compatible physical settings/extensions and extra disk space.
pg_upgrade --clone Copy-on-write speed with independent old cluster Supported OS/filesystem and same filesystem requirements; verify in rehearsal.
pg_upgrade --link Less copying/storage After new cluster starts, shared files make old cluster unsafe to restart.
Dump/restore Clean rebuild; portability and selected redesign Longer copy/index-build outage unless separately synchronized.
Logical replication Can reduce final write outage DDL, sequences, large objects and cutover consistency need separate handling.

PostgreSQL 18 also has swap/copy-file-range modes; this procedure deliberately uses default copy, not a space-saving mode with different rollback properties.[36]

Inventory and rehearse before the window

The bounded major procedure is PGDG PostgreSQL 17 to 18 on the same RHEL 9.7 x86_64 host, old unit postgresql-17 with /var/lib/pgsql/17/data, new unit postgresql-18-upgrade with /var/lib/pgsql/18/upgrade on 5544. Both package families must resolve against this maintained OS minor, including OpenSSL and all extension dependencies. It is not an AppStream stream-switch recipe or an instruction to downgrade the existing 18 learning cluster.[94][100]

SELECT version();
SHOW data_directory;
SHOW data_checksums;
SHOW server_encoding;
SHOW lc_collate;
SHOW lc_ctype;
SELECT datname, datlocprovider, datcollate, datctype, datcollversion
FROM pg_database ORDER BY datname;
SELECT extname, extversion FROM pg_extension ORDER BY extname;
SELECT spcname, pg_tablespace_location(oid) FROM pg_tablespace;
SELECT * FROM pg_prepared_xacts;

Collect extension inventory from every database, native library paths, replication topology/slots, publications/subscriptions, external integrations and package versions. Check drivers, SCRAM/TLS support, reserved words, query behavior and extension vendor upgrade instructions. A compatible binary package is not proof its SQL extension version was upgraded.[36][54]

PostgreSQL 18 enables checksums by default; pg_upgrade requires matching old/new checksum settings. For a no-checksum source, initialize the target with --no-data-checksums or follow an independently reviewed offline checksum-enablement plan. Match locale/provider/encoding and other checked physical settings; do not “fix” a check failure by editing control files.[4][11]

Use a restored production copy for rehearsal. Measure the entire outage through extension updates, stats, reindex work and application validation. Freeze schema changes before the final run, take a verified recoverable backup and retain source binaries/configuration. Confirm capacity for both copied data and later WAL/index work. Default-copy rollback still cannot recover writes accepted only by the new server.[36]

Apply a minor update

  1. Read the exact old-to-new 18.x release notes, check repository candidates and extension package updates, verify backup/recovery access, then drain applications.
  2. Inventory every unit using /usr/pgsql-18; drain and stop affected clusters cleanly. Review dnf --refresh list --showduplicates postgresql18 postgresql18-server postgresql18-contrib, then use sudo dnf upgrade postgresql18 postgresql18-server postgresql18-libs postgresql18-contrib with approved matching extension updates. Preview/review the whole transaction; retain gpgcheck=1. The inspected server RPM calls systemctl try-restart postgresql-18 on upgrade; a stopped service is not started by that action. Separately named local units are not updated/restarted for you. Compare copied units to the new vendor unit and inspect .rpmnew files.[99][100]
  3. Start postgresql-18.service (and each affected named instance in order), verify SQL SELECT version() and tool versions, inspect logs, connect as the actual application role and run representative reads/writes.
  4. Follow any release-specific reindex/extension tasks. Observe replication/archive health and new backup completion before closing the change.[1][100]

If startup fails, preserve logs and diagnose config/library mismatches. Binary rollback is a release-specific decision, not a universal safety guarantee; keep a restore path for changes that cannot be reversed by reinstalling an older package.

Run a copy-mode major upgrade

The OS account running pg_upgrade must own both clusters and a writable work directory. Use the new major’s utility. No applications may connect during conversion. Ensure the fresh target’s HBA permits local peer connections for postgres; do not enable network trust to make the tool work.[36]

  1. Install approved postgresql17, postgresql17-server and corresponding old extensions if not already retained, plus target postgresql18, postgresql18-server, postgresql18-contrib and all matching target extension libraries. Do not replace the old major or install extension SQL manually into the empty target. Register postgresql-18-upgrade.service using multiple instances, with PGDATA=/var/lib/pgsql/18/upgrade and mount ordering. Leave it disabled/stopped.
  2. Initialize that empty directory as postgres with /usr/pgsql-18/bin/initdb -D /var/lib/pgsql/18/upgrade, adding the source’s encoding/locale/provider/checksum choices and --auth-local=peer --auth-host=scram-sha-256; never use learning defaults blindly. Set target port 5544, listen_addresses = '', socket /run/postgresql, and local peer HBA. Create/label its owned log directory. Inspect the port inventory; if TCP will later be enabled on 5544, allocate postgresql_port_t after checking conflicts. No broad firewall opening is needed for this local upgrade.[11][102]
  3. Create /var/lib/pgsql/upgrade-work owned by postgres, mode 0700. Use direct new-major pg_upgrade in default copy mode: the inspected PGDG setup wrapper’s upgrade action uses --link and its check action rewrites HBA/has destructive failure cleanup, so it is not a harmless substitute for this workflow.[100] Both clusters must be cleanly stopped for the following rehearsal/final sequence. Prevent unattended package/service starts during conversion.
sudo systemctl stop postgresql-17.service
sudo systemctl stop postgresql-18-upgrade.service
sudo restorecon -Rv /var/lib/pgsql/18/upgrade /var/lib/pgsql/upgrade-work
sudo -u postgres -H bash
cd /var/lib/pgsql/upgrade-work
/usr/pgsql-18/bin/pg_upgrade \
  --old-bindir=/usr/pgsql-17/bin \
  --new-bindir=/usr/pgsql-18/bin \
  --old-datadir=/var/lib/pgsql/17/data \
  --new-datadir=/var/lib/pgsql/18/upgrade \
  --old-port=5432 --new-port=5544 \
  --socketdir=/var/lib/pgsql/upgrade-work --check

PGDG configs are inside these PGDATA paths, so no external --old-options/--new-options config-file override is needed. If discovery showed a nonstandard split layout, explicitly adapt and rehearse it. pg_upgrade starts temporary postmasters itself: do not also start their systemd units. Keep SELinux enforcing; diagnose path/domain/AVC failures instead of turning confinement off.[36][100][102]

--check reports incompatibilities, not successful application migration. Resolve every reported library/type/setting/prepared-transaction issue and rerun. Keep the generated logs. Before final execution, confirm backup and cutover authorization; run the same command without --check, still from the owned work directory. Do not add --link, --swap or --no-sync to save time.[36]

  1. Exit the OS postgres maintenance shell before host-administrator service commands. Follow pg_upgrade’s generated, version-specific completion instructions. Review and apply extension update SQL using the extension vendor’s supported path. Compare old/new configs; do not copy the old whole file over new defaults or unintentionally point target data_directory back at the source. After conversion, inspect/restore SELinux labels, verify target unit PGDATA and its private listener/log settings, then sudo systemctl start postgresql-18-upgrade.service on 5544 while applications remain drained. Test confined service startup and new-session authentication; do not use the temporary upgrade postmaster as production supervision.[100][102]
  2. PostgreSQL 18 transfers most, not all, optimizer statistics. Run the instructed missing-statistics and cumulative-statistics refresh, with correct connection parameters, running these clients as OS postgres for local peer authentication:[36]
/usr/pgsql-18/bin/vacuumdb -h /run/postgresql -p 5544 \
  -U postgres --all --analyze-in-stages --missing-stats-only
/usr/pgsql-18/bin/vacuumdb -h /run/postgresql -p 5544 \
  -U postgres --all --analyze-only
  1. Validate structure, counts, roles, plans and application behavior, plus release-note-specific changes. PostgreSQL 18’s collation/text-search behavior changes can require rebuilding affected full-text/pg_trgm indexes. After an OS/ICU collation change, identify and rebuild affected objects before refreshing recorded collation versions; updating metadata alone does not rebuild index order.[4][87]
  2. Rebuild/reconfigure standbys for the new major and validate archive namespaces/backup jobs. Do not let a 17 physical standby consume 18 WAL. Test logical subscriptions separately, including slot compatibility/failover settings. Route a controlled client cohort to 5544 or change the planned endpoint during a final stop/start; then monitor errors/latency and take a new base backup.[36][38]

Keep rollback honest

Point Copy-mode rollback What must not happen
Precheck failed Source remains the authority; restart it after inspection Do not promote/populate the target to bypass checks.
Conversion failed before target use Preserve logs, confirm source unchanged, restart source Do not reuse half-upgraded target without cleanup/reinitialization plan.
New target tested without accepted writes Stop target, restore routing/config to retained source Never run both writable behind the same endpoint.
New target accepted writes Reconcile/export those writes or restore under an agreed loss decision Old source is now stale; starting it is not lossless rollback.
Link/swap mode was used instead Follow that mode’s strict destructive boundary; restore backup when required Do not restart shared or moved source files after the unsafe boundary.

Keep old cluster data, packages, tablespaces and generated cleanup scripts through the agreed rollback period. Do not run delete_old_cluster.sh merely because the upgrade tool produced it. End the window only after new backups can be restored and the performance/application acceptance checks pass.[36]

For dump/restore migration, use the logical restore workflow with target-major clients. For a low-outage table migration, use logical replication and a separate sequence/DDL/cutover plan—not an assumed automatic upgrade of every database object.
