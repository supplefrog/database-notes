Device management

Kernel modules and drivers

Kernel functionality may be built into the kernel or supplied by loadable modules. A driver is not necessarily a loadable module.[94]

Drivers and interrupts

  • Hardware can signal an interrupt request (IRQ). Drivers register handlers with the kernel interrupt subsystem.
  • A hard-interrupt handler should do bounded, non-sleeping work; defer longer work to an appropriate threaded handler or other deferred-work mechanism.[132]
  • Interrupt controllers route and prioritize interrupts. On x86, APICs are part of this machinery. MSI/MSI-X are message-signalled interrupt mechanisms, not a generic component called an “MSI controller.”[93]
  • Device drivers handle hardware such as network adapters and storage controllers; CPU/platform support also lives in the kernel.
  • Filesystem implementations (for example ext4 or NTFS implementations) manage on-disk structures and filesystem operations through the kernel’s filesystem/I/O layers. Buffering and caching involve shared kernel facilities, not only the device driver.[3][43]

Pluggable Authentication Modules (PAM)

Linux-PAM is a userspace framework, not a Linux kernel module subsystem. PAM-aware applications use libraries and configured module stacks for authentication, account checks, password changes and session setup. A shared-library PAM module is different from a loadable kernel module.[7]

See password policy.

Network protocol support

The kernel implements networking protocols, including IP and the TCP and UDP transports. Depending on the build, networking features can be built in or modular. TCP and UDP both operate over IP; “TCP/IP” is not a peer of UDP in a clean protocol-layer taxonomy.[90]

Linux Security Modules (LSM)

LSM provides hooks for security decisions involving files, networking, process operations and other kernel objects. SELinux is one implementation that applies its security policy through these hooks. It is distinct from PAM’s userspace login/session decisions.[4][82]

Kernel services

Exceptions, hardware interrupts, and system calls are different entry paths into privileged kernel handling. Linux “softirqs” are a specific deferred-processing mechanism; the term is not a synonym for every system call or exception.[132][85]

Applications request kernel services through interfaces such as read(), write(), getpid(), pipe(), socket() and execve(). The exec*() family includes library wrappers; exec() is not one universal Linux syscall name. time() is a familiar time interface, but a library/vDSO implementation need not trap into the kernel on every call.[92][91]

A syscall enters kernel mode, validates the request and permissions, performs the operation where permitted, and returns a result or error; it does not grant the caller unrestricted privilege.[61]

Namespaces

Namespaces give groups of processes distinct views of resources such as process IDs, network stacks, mount points and user IDs. They are building blocks for containers and sandboxes, not by themselves a complete security boundary.[5]

Control groups (cgroups)

Cgroups organize processes for resource accounting and control: CPU, memory and I/O are important examples. Namespaces answer “which resources are visible?”; cgroups answer “how are resources accounted for and constrained?” Available controllers and delegation rules depend on the kernel and configuration.[6]

For service-level limits, see resource controls.
