Architecture, editions and tools

Choose the server, not just the name

These notes target community PostgreSQL 18, with server and bundled command-line tools 18.6 as the documentation-review baseline. The official support table lists major 18 through 14 November 2030. Install the maintained 18.x security/bug-fix release available from your approved repository, not an unqualified latest image; record its exact package revision before a change.[1]

Linux procedures use RHEL 9.7 x86_64, systemd, SELinux enforcing, PGDG PostgreSQL 18 RPMs. The inspected server/client build is 18.6-1PGDG.rhel9.7 and repository RPM 42.0-66.rhel9.7PGDG. PGDG’s last-two-minors policy is distinct from Red Hat’s RHEL/EUS lifecycle: revalidate the maintained minor and repository dependency match before deployment. These upstream packages are not Red Hat AppStream PostgreSQL or automatically covered by Red Hat database support.[93][94][97] Shell blocks are Bash on that server, not Windows commands. sudo denotes OS administration; sudo -u postgres switches to the database service account. SQL blocks run in psql against the named cluster. The default unit postgresql-18.service manages /var/lib/pgsql/18/data on port 5432; a separate restore drill uses 5543. Paths, addresses and capacity settings called out as examples must be changed for the actual host. Never point a restore drill at the live data directory.

Component What it provides Boundary
PostgreSQL core Server, SQL, roles, WAL, logical/physical backup and replication Open-source PostgreSQL License; no paid core edition is required for these tasks.[65]
PGDG packages Versioned binaries and integration with distro packaging Upstream RPMs, separate from Red Hat’s postgresql-server module/support contract; do not mix service/setup conventions.[97][100]
Extensions Additional SQL objects, modules or background workers Availability depends on packages, server major and privileges; CREATE EXTENSION does not download software.[54]
Commercial distributions/tools Vendor support or additional features Verify that vendor’s license, compatibility and recovery path; not assumed here.
Managed services Provider-operated machines, backups and failover OS access, superuser and supported extensions may differ; these self-hosted procedures are not cloud-console instructions.

Use the right utility

Call /usr/pgsql-18/bin/&lt;tool&gt; where more than one major is installed. PGDG versioned RPMs place binaries here; postgresql18 supplies clients and postgresql18-server supplies server/setup/unit. Avoid PATH/alternatives ambiguity, especially across majors. A source build commonly uses /usr/local/pgsql; inspect rather than mix trees.[100][105][53]

Utility Task Important limit
psql -X -v ON_ERROR_STOP=1 -d adminlab Run SQL or a reviewed script without user startup customizations Default interactive error handling is not a fail-fast migration runner.[13]
pg_isready -h /run/postgresql -p 5432 Check whether the endpoint accepts connections Readiness is not proof of application authentication, schema or recovery health.[73]
pg_dump, pg_restore, pg_dumpall Logical archives, restore and cluster globals A database dump excludes cluster-wide roles/tablespaces; logical dumps cannot be replayed with WAL.[29][31][33]
pg_basebackup, pg_verifybackup Copy a running cluster and check its manifest/WAL Validation is not a substitute for starting an isolated restore.[32][35]
pg_ctl, pg_controldata Control a directly managed server; inspect control metadata Do not run a second controller alongside the package service.[91][92]
pg_upgrade, pg_rewind Major-version conversion; rejoin a diverged physical copy Different operations, each with explicit prerequisites and rollback limits.[36][44]

Inspect versions with psql --version, /usr/pgsql-18/bin/pg_dump --version, and SQL SELECT version();. Client and server versions are separate facts. Check extension availability before scheduling a restart:

SELECT name, default_version, installed_version
FROM pg_available_extensions ORDER BY name;
SELECT extname, extversion FROM pg_extension ORDER BY extname;

An extension’s files must be installed for this major on every relevant host, then its SQL objects installed in each required database. Superuser is normally required unless the extension is marked trusted; native extension code runs inside the server’s trust boundary.[54]

Follow one connection

client / driver / psql
       | Unix socket OR TCP + TLS
       v
postgres supervisor (historically “postmaster”)
       | matching pg_hba rule + role/database authorization
       v
one backend per connection
       | parse -> rewrite -> plan -> execute
       v
shared buffers / heap and index pages / WAL

The supervisor accepts connections and creates a backend for each; each backend consumes resources, so connection counts need a host budget. The parser checks syntax, rewrite expands views/rules, the planner estimates alternative paths, and the executor reads/modifies rows. Estimates depend on statistics, not only available indexes.[5][62]

Authentication answers who connected; database CONNECT, schema USAGE, table/routine privileges and possibly row security determine what they can do. A successful TCP connection does not grant SQL access. pg_hba.conf selects the first matching rule with no fallback after authentication failure. TLS supplies transport security; the client must verify server identity, not merely ask for encryption.[14][16][19]

Process Responsibility First place to investigate
Backend Session SQL, locks, snapshots, private working memory pg_stat_activity, pg_locks
Checkpointer Establish recovery checkpoints and write dirty pages pg_stat_checkpointer, storage latency
Background writer / WAL writer Smooth page writes / WAL writes pg_stat_bgwriter, pg_stat_wal, durability settings
Autovacuum launcher/workers Schedule and perform vacuum/analyze Dead tuples, transaction age, maintenance progress
WAL sender / WAL receiver Stream changes to/from physical replicas pg_stat_replication, pg_stat_wal_receiver
Archiver Deliver completed WAL files to archive storage pg_stat_archiver, archive destination
Logical replication workers Copy/synchronize/apply published table changes pg_stat_subscription

These views expose different processes; one low CPU number does not establish health.[25]

Sessions and pooling

A session holds settings, prepared statements, temporary tables and possibly an open transaction. In transaction-pooling mode a proxy may assign the next transaction to a different backend: do not rely on session state surviving that boundary. Configure and test the chosen pooler separately; core PostgreSQL does not turn one backend into an automatic transaction pool. Limit connection counts against memory, parallel workers and workload, not a desired marketing concurrency number.[5][63]

SELECT current_database(), current_user, session_user, pg_backend_pid();
SELECT datname, usename, state, count(*)
FROM pg_stat_activity
GROUP BY datname, usename, state ORDER BY count(*) DESC;

current_user can change with SET ROLE; session_user records the original session identity. Inspect application errors as well as pool wait time: a pool saturated by idle transactions is not fixed by adding server connections. See session cancellation and memory pressure.

Continue with storage and transactions, or install a local-only instance.
