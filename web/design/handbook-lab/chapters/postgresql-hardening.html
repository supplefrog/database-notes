Keep the trust boundaries separate

Network reachability, TLS identity, login authentication and SQL authorization are different controls. A password does not close a public port; TLS does not grant table permissions; an HBA rule does not limit a superuser’s SQL powers. Start local-only and add the smallest required path.[14][16][19]

Method/control Use Avoid
Local peer OS service/admin identity over protected Unix socket Assuming a TCP password affects peer mapping.
scram-sha-256 Password authentication with modern clients Reusing MD5 hashes; PostgreSQL 18 deprecates MD5 password authentication.[15]
cert or clientcert=verify-full Client certificate identity, optionally alongside SCRAM Confusing client CN/role verification with server hostname verification.
trust No authentication at all Network or routine recovery configuration.
password Cleartext password exchange inside a separately secured transport Using without TLS; prefer SCRAM here.
Object grants / owner separation Bound what a logged-in role can do Application superuser/owner to “fix permissions.”

Keep the OS postgres account noninteractive for normal human use, control sudo access and protect its Unix socket directory. An authorized OS administrator can already act as the database owner; do not pretend the database password protects against host root. For a forgotten database password, retain controlled local peer administration and use psql \password role_name; do not start a public trust-auth server.[13][14][45]

Changing password_encryption affects newly set passwords, not existing hashes. For an MD5-to-SCRAM migration, first verify every driver/tool supports SCRAM, select SCRAM, rotate affected passwords securely, then change the relevant HBA rules and test new logins. Keep an authorized local session open until the tests pass.[15]

Require TLS and verify the server name

For the RHEL PGDG primary, obtain a certificate from the organization’s trusted CA with the real database DNS name in its subject alternative names. The examples use primary.example.test; replace it with the intended identity. Do not ship a sample private key, publicly trusted wildcard assumption or production self-signed bootstrap here. Obtain/manage CA trust through the organization’s certificate process.[16][69]

Place server chain and key at the following example paths, owned by postgres; private key mode 0600, parent directories accessible only as necessary. Alternatively a root-owned 0640 key may be group-readable by the server account, but do not mix that model accidentally. Public CA/certificate files can be readable without exposing the private key.[16]

For this RHEL layout, create /var/lib/pgsql/tls owned by postgres, mode 0700; provision the files through secret management. Inspect semanage fcontext -l and matchpathcon first. If a custom path lacks an appropriate existing mapping, add the narrow PostgreSQL-readable data type (postgresql_db_t) to that directory, then apply restorecon -Rv /var/lib/pgsql/tls and verify ls -lZ/AVCs. Preserve key mode 0600: a SELinux label does not grant Unix access. Do the same after atomic certificate replacement because a moved file can retain its old label. Do not enable permissive mode to work around a denied key read.[102][104]

# /var/lib/pgsql/18/data/postgresql.conf
listen_addresses = 'localhost,192.0.2.10'
ssl = on
ssl_cert_file = '/var/lib/pgsql/tls/server.crt'
ssl_key_file = '/var/lib/pgsql/tls/server.key'
ssl_min_protocol_version = 'TLSv1.2'
password_encryption = 'scram-sha-256'

192.0.2.10 is a documentation address, not a real interface to bind. The server certificate file must begin with the leaf matching the key, followed by any required intermediate chain. The client separately trusts the issuing root. Confirm package OpenSSL support and certificate/key readability before changing the listener.[16]

Use explicit, narrow HBA rules, adapting addresses for the actual private network:

# Keep local break-glass administration; peer still checks OS identity.
local   all          postgres                            peer
local   all          all                                 peer
local   replication  postgres                            peer

# Application host and physical standby, separately authorized.
hostssl adminlab     notes_app  198.51.100.10/32          scram-sha-256
hostssl replication  notes_repl 192.0.2.20/32             scram-sha-256

# Explicit rejections make accidental broad access visible.
host    all          all        0.0.0.0/0                reject
host    all          all        ::0/0                    reject
host    replication  all        0.0.0.0/0                reject
host    replication  all        ::0/0                    reject

HBA uses the first matching line and never falls through after failed authentication. host matches encrypted and unencrypted TCP; hostssl matches only TLS. Database all does not match physical replication, hence the separate rules. Add any loopback TCP app or logical-subscriber rule narrowly before rejects; keep it hostssl once this policy replaces bootstrap loopback access.[14]

The host/provider firewall must independently allow only the intended clients to the intended interface/5432. Use RHEL firewalld, keeping SELinux enforcing. Inspect firewall-cmd --get-active-zones, the actual interface’s zone, --zone=ZONE --list-all and --permanent --zone=ZONE --list-all first. An existing broad postgresql service, 5432 port, trusted zone, rich rule, direct rule or forwarding policy can defeat a new narrow rule; reconcile it under change control before proceeding. Do not remove unrelated management access.[103]

After verifying that public really is the intended restricted interface zone, substitute the actual client/standby addresses below. Add runtime rules first, test permitted and denied sources, then persist exactly those rules. No database port is needed on a socket-only drill or on a standby solely receiving outbound streaming connections.[103]

DB_ZONE=public  # replace only after checking interface/zone assignment
APP_RULE='rule family="ipv4" source address="198.51.100.10/32" port port="5432" protocol="tcp" accept'
REPL_RULE='rule family="ipv4" source address="192.0.2.20/32" port port="5432" protocol="tcp" accept'
sudo firewall-cmd --zone="$DB_ZONE" --add-rich-rule="$APP_RULE"
sudo firewall-cmd --zone="$DB_ZONE" --add-rich-rule="$REPL_RULE"
# Test actual allowed clients and an unauthorized host before persistence.
sudo firewall-cmd --permanent --zone="$DB_ZONE" --add-rich-rule="$APP_RULE"
sudo firewall-cmd --permanent --zone="$DB_ZONE" --add-rich-rule="$REPL_RULE"
sudo firewall-cmd --zone="$DB_ZONE" --list-rich-rules
sudo firewall-cmd --permanent --zone="$DB_ZONE" --list-rich-rules

If validation fails, remove these exact rules from both runtime and permanent configuration with --remove-rich-rule, retaining the prior policy; do not blindly --runtime-to-permanent unrelated changes. Reboot/reload persistence must be tested in the approved window. IPv6 needs a separate deliberate source rule or remains denied; provider ACLs require the same narrow policy. postgresql_port_t on 5432/any alternate TCP port permits SELinux binding but is not a firewall allowance. Inspect the installed port map rather than assuming an alternate port works.[102][103]

Do not open 0.0.0.0/0 as a diagnostic shortcut. In a maintenance window, restart for listen_addresses; reload for HBA/certificate changes where supported. Inspect pg_file_settings, pg_hba_file_rules, logs and pending_restart—sending a reload signal is not successful validation.[12][16][58]

Client example, with no secret in the connection string:

/usr/pgsql-18/bin/psql -X 'host=primary.example.test port=5432 dbname=adminlab user=notes_app sslmode=verify-full sslrootcert=/secure/ca.crt gssencmode=disable'

verify-full verifies both trust chain and hostname. sslmode=require does not promise hostname verification: with a root CA file it can also validate the chain for compatibility, but that is still not verify-full. Specify the intended verification mode explicitly. gssencmode=disable keeps this TLS-specific example from selecting a separately configured GSS encrypted path.[17][69]

SELECT current_user, current_database(), inet_server_addr(), inet_server_port();
SELECT ssl, version, cipher FROM pg_stat_ssl WHERE pid = pg_backend_pid();

Test a new valid connection, a wrong hostname/CA, a non-TLS attempt and an unauthorized role/address; the latter attempts must fail. pg_stat_ssl.ssl confirms transport, not that the client checked the hostname—only the client’s configured verification and negative tests establish that. Preserve the prior files and admin session so failed changes can be reverted locally without opening trust authentication.

Authenticate clients with certificates

When policy requires mutual TLS, set ssl_ca_file to the CA(s) trusted to issue client certificates. Add clientcert=verify-full to the narrow hostssl ... scram-sha-256 rule to require both a valid matching client certificate and password authentication. Without a configured mapping, the certificate common name must match the requested database role.[16]

hostssl adminlab notes_app 198.51.100.10/32 scram-sha-256 clientcert=verify-full

Client sslcert/sslkey supply its certificate and owner-only key; its sslrootcert still verifies the server. The cert authentication method instead uses certificate authentication without a second password. Review role mappings in pg_ident.conf if certificate names differ; do not grant every valid client certificate the same privileged role.[14][16][69]

Rotate certificates and credentials without lockout

  1. Inventory certificate expiry, hostname/SAN, chain, key algorithm, client trust stores, standby/backup clients and CA revocation requirements. Decide whether old/new trust must overlap.
  2. Stage a matching certificate/key pair under the intended ownership/modes and validate the chain/identity. Retain the old valid pair securely for rollback. Use an atomic replacement strategy so the server never reads a half-written pair.
  3. Reload the PostgreSQL TLS files on the RHEL target, inspect errors and test new connections from every client class. Existing sessions do not prove the new files work. Passphrase-protected keys have additional reload/startup constraints; unattended services need an approved passphrase retrieval mechanism, not a password embedded in a script.[16]
  4. Rotate client trust/certificates or SCRAM passwords through their secret channel, reconnect pools and replication/backup clients, then remove expired/revoked trust after the overlap window. Monitor connection failures and standby lag throughout.
  5. If validation fails, restore the still-valid pair/trust policy and reload; verify a fresh connection. If compromise is suspected, rollback to a compromised key is not acceptable—reissue/revoke and follow incident policy.

Use ssl_crl_file/ssl_crl_dir where certificate-revocation policy requires it. Revoking a certificate or changing a password does not itself disconnect an established database session; plan termination/reconnect separately if the incident demands it.[16]

Bound SQL and filesystem privileges

Use the role/ownership matrix. Runtime identities normally need database CONNECT, schema USAGE, precise table privileges and sequence USAGE, not CREATE in a schema, role administration or ownership. Keep migration credentials separate and revoke temporary elevated access after the change.[19]

Capability Why it is sensitive Control
Superuser / BYPASSRLS Bypasses ordinary authorization/row policy Dedicated break-glass use with independent recording.
CREATEROLE, powerful memberships Can delegate/escalate authority under their rules Review membership ADMIN, INHERIT and SET options.
Server file/program roles Read/write server files or execute commands as server OS account Never grant to ordinary import/report users; use client \copy.
Writable schema on search_path Untrusted objects can change name resolution Schema-qualify sensitive SQL; remove untrusted create privileges.
SECURITY DEFINER routine Executes with owner’s privileges Minimal owner, safe fixed search path, reviewed body and restricted EXECUTE.
Extension/native code Executes inside database server trust boundary Signed/trusted packaging, major compatibility, change review.

A hardened function is not achieved merely by adding SECURITY DEFINER. Prefer invoker security where possible; malicious shadow objects and overly broad public execute grants can defeat an otherwise narrow role model.[19][21][54]

Encrypt the storage and protect recovery material

Community PostgreSQL 18 does not provide a general core switch for transparent whole-cluster data-file encryption. Use OS/block/filesystem encryption and storage/provider controls for that boundary; verify that data, WAL, tablespaces, temporary files, swap and snapshots are all included. TLS protects traffic, not stored files.[45]

Storage encryption protects offline media, not a compromised running host: while the filesystem is mounted, the OS exposes plaintext to authorized processes and a sufficiently privileged attacker. Keep recovery keys available through separate protected custody rather than relying only on the host being recovered.[45]

pgcrypto provides field-level cryptographic functions; it is not transparent database encryption, and plaintext/key handling in server-side functions has a different trust model. Client-side encryption can keep plaintext away from the server but changes indexing/query/recovery design. Pick a threat model before selecting either; neither makes superuser-controlled application access safe by itself.[45]

Secret/data location Required handling
libpq passfile Owner-only mode 0600 on Unix; exact host/port/database/user matching; ignored when permissions are too broad.[55]
Connection URI/environment Avoid embedded passwords; arguments, logs, process inspection and error reports can leak them.
Logical globals dump May contain password hashes unless --no-role-passwords; preserve grants without casually exposing credentials.[31]
Base backups/WAL/snapshots Treat as the entire database; encrypt, access-control, separate delete rights and test recovery.
TLS/storage encryption keys Separate protected custody, rotation records and tested recovery access. A backup without its key is not recoverable.
Logs/exports/support bundles Redact/minimize secrets and personal data; bounded retention and authorized readers.

Verify the backup restore drill using the recovery team’s access rather than the original machine’s cached credentials. Revisit hardening after promotion or upgrade: a new primary must inherit an intentional security policy, not accidental defaults from a copied file.
