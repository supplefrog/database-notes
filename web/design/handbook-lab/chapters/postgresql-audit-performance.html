Choose observability, not unlimited logging

Server logs diagnose errors and slow statements; cumulative statistics summarize activity; a statement-audit extension records selected classes of action. None alone is an immutable record of every business event. Decide which actor, operation and retention evidence you need before enabling high-volume logging.[24][25][61]

Mechanism Good for Does not prove
Error/slow statement log Failed connections, errors, slow SQL, lock waits Every successful row change or tamper-resistant audit.
pg_stat_* views Rates, waits, maintenance and replication status Permanent event history; counters reset and queries may be hidden.
pg_stat_statements Aggregate cost/calls of normalized query shapes Every execution with every parameter.
pgAudit (separate extension) Detailed session/object audit using PostgreSQL logs Independent custody, regulatory compliance or protection from host superusers.
Application audit events Business actor/reason/correlation Server-wide changes made outside the application.

Example server configuration for a measured starting point. Merge with existing values; do not replace an established logging destination blindly.[24]

logging_collector = on
log_destination = 'jsonlog'
log_directory = 'log'
log_filename = 'postgresql-%Y-%m-%d_%H%M%S.log'
log_rotation_age = '1d'
log_rotation_size = '100MB'
log_min_duration_statement = '500ms'
log_lock_waits = on
log_statement = 'none'

Use the instance’s PGDATA/log created by PGDG setup (0700, owned by postgres), and restorecon -Rv after restoring/copying it.[100][102] For an external log path, use a persistent postgresql_log_t mapping and inspect actual policy/AVCs as in relocation. Restrict access before restarting for logging_collector; most subsequent log policy changes are reloadable. Check pg_settings.context, then SELECT pg_current_logfile(); and produce a known benign event in a fresh test session. Inspect both server log and remote collector receipt. Rotation creates new files; it is not retention deletion. Enforce bounded retention/off-host delivery outside the database.[24]

Statement text, errors and parameters can leak secrets even when password-setting commands are treated specially. Avoid blanket log_statement = 'all'; document who can read logs and exclude secret values from application SQL. Watch disk space, ingestion lag and logging overhead after changing policy. Roll back to recorded settings and reload/restart as required if throughput or disk headroom becomes unsafe.

Add audit only for a defined requirement

PGDG provides pgAudit as pgaudit_18; the inspected RPM is 18.0-1PGDG.rhel9. Review its dependency resolution against this RHEL minor; a filename suffix alone is not dependency validation. Use sudo dnf install pgaudit_18, verify rpm -q pgaudit_18 and rpm -ql pgaudit_18, and keep signature checking enabled.[106] pgAudit is open source, separate from core, with major-specific builds; use the 18.x extension line for PostgreSQL 18, not an arbitrary build from another major. Install its trusted package/binary on every host that may become primary. Check the installed extension version rather than assuming it ships with the server.[61]

  1. Preserve the existing shared_preload_libraries list and append pgaudit. Restart in a maintenance window; a missing library can prevent startup, so keep the prior config available.
  2. As administrator, CREATE EXTENSION pgaudit; in each database needing its DDL event-trigger support before setting pgaudit.log.
  3. For a narrow initial policy, set pgaudit.log = 'ddl,role' in the server configuration and reload. Include read/write only if required and volume-tested; object auditing can restrict relation coverage but must be maintained when new objects are added.
  4. Execute a harmless, approved fixture DDL change, then verify the exact event in server and external logs. Test denied actions and role changes against the requirement too.
  5. Record overhead, rotation/retention, collector outage behavior and who can alter policy. To remove the extension, first unset pgaudit.log; removing preload needs a restart.[61]

Do not copy the example policy into a compliance claim: it deliberately omits ordinary reads/writes, and server administrators can change both extension policy and local files.

Rank query shapes and refresh statistics

Install the approved postgresql18-contrib RPM on each relevant host before preloading pg_stat_statements; confirm /usr/pgsql-18/lib/pg_stat_statements.so and its control files with rpm -ql postgresql18-contrib. The inspected contrib RPM also supplies amcheck, pgcrypto and basic_archive; availability of files is separate from extension SQL installation.[101]

pg_stat_statements needs its major-18 module files, preloading and query-ID computation. Merge pg_stat_statements into shared_preload_libraries, retain other entries, keep compute_query_id = auto (or on), restart, then create its SQL extension in adminlab.[26]

CREATE EXTENSION pg_stat_statements;
SELECT queryid, calls, total_exec_time, mean_exec_time, rows,
       shared_blks_hit, shared_blks_read, temp_blks_written,
       left(query, 180) AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC LIMIT 10;

Use an authorized monitoring role; other users’ text/query IDs require superuser or pg_read_all_stats. Record the stats reset time and sample interval. A high mean time with one call is different from cheap SQL executed millions of times. Do not reset shared counters merely to make a chart look clean.[26]

View Read it for
pg_stat_database Transactions, temp bytes, deadlocks, cache/block activity by database.
pg_stat_user_tables, pg_stat_user_indexes Scans, writes, live/dead estimates, maintenance and index use.
pg_stat_activity, pg_locks Active/idle sessions, transaction age, waits and lock identity.
pg_stat_io I/O by backend/object/context; distinguish reads, writes and eviction pressure.
pg_stat_wal, pg_stat_checkpointer WAL generation and checkpoint behavior.
pg_stat_progress_* Progress of supported vacuum/index/backup operations.[89]

These are observation surfaces, not exact bloat gauges or end-to-end application timings.[25] After large imports, run ANALYZE and review estimates; for skewed columns consider a measured higher statistics target, then restore the previous target if extra planning/collection cost is not justified. See vacuum and analyze.

Compare a plan before and after one index

Use the exact 2,000-row fixture in adminlab, with no concurrent benchmark workload. The table owner can create/drop the test index. EXPLAIN plans the query; EXPLAIN ANALYZE executes it, including writes, triggers and function side effects. A transaction rollback cannot undo external effects or sequence allocation, so do not profile unknown DML this way.[27]

ANALYZE notes.orders;
EXPLAIN (COSTS, VERBOSE)
SELECT order_id, amount FROM notes.orders
WHERE customer_id = 42 AND status = 'new';

EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)
SELECT order_id, amount FROM notes.orders
WHERE customer_id = 42 AND status = 'new';

CREATE INDEX orders_customer_status_idx
ON notes.orders (customer_id, status) INCLUDE (amount, order_id);
ANALYZE notes.orders;

EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)
SELECT order_id, amount FROM notes.orders
WHERE customer_id = 42 AND status = 'new';
Plan item/option Interpretation
cost=start..total Planner cost units, not milliseconds.
Estimated rows versus actual rows Large mismatch suggests distribution/statistics/correlation issues.
Actual rows and loops Repeated nodes report per-loop values; interpret work across loops.
BUFFERS Shared hits/reads and temp activity; a shared hit is not an application-cache hit.
TIMING OFF Reduces per-node clock overhead while still executing/counting.
Rows removed by filter Work done for rows not returned; consider predicate/index fit.
Heap fetches in index-only scan Visibility checks may still visit heap pages; vacuum state matters.

On this small table a sequential scan may remain cheaper; that is not a failed index. Compare result equality, estimates, logical reads and repeated timings under a declared cache/load condition. No elapsed times or chosen plan are promised here. Keep the index only if it benefits the real read workload enough to pay for write/WAL/storage cost; otherwise DROP INDEX notes.orders_customer_status_idx; removes this exact fixture index.[27][28]

For a live table, normal index creation blocks writes. CREATE INDEX CONCURRENTLY reduces that blocking but performs extra work, waits for old transactions, cannot run inside a transaction block and may leave an invalid index after failure. Check pg_index.indisvalid, resolve the cause and follow documented drop/rebuild handling. A failed concurrent unique index can still affect writes; do not assume “invalid” means harmless.[28]

Do not force global planner switches as a permanent fix for one query. Compare alternatives in a bounded session, restore the setting and correct statistics/query/index design. Join semantics and datasets are in the existing joins lesson.

Identify blockers and resource pressure

SELECT pid, usename, application_name, state, wait_event_type, wait_event,
       clock_timestamp() - xact_start AS transaction_age,
       pg_blocking_pids(pid) AS blockers, left(query, 120) AS query
FROM pg_stat_activity
WHERE datname = 'adminlab' AND pid <> pg_backend_pid()
ORDER BY xact_start NULLS LAST;

SELECT l.pid, l.locktype, l.mode, l.granted,
       l.relation::regclass AS relation
FROM pg_locks AS l
WHERE NOT l.granted ORDER BY l.pid;

A wait event is not necessarily a lock: it may be I/O, client consumption, WAL flush or synchronous replication. Follow blocker PIDs to the oldest transaction, check application ownership, then ask it to finish. Use cancel versus terminate only after identifying the exact target. Killing the visible victim leaves the root blocker intact.[9][23][25]

Budget memory and connections together

Lever Why it matters Safer first move
work_mem Per sort/hash operation, multiplied by plan nodes/sessions/workers; hashes also use hash_mem_multiplier Set locally for a measured query, not one enormous global allocation.
shared_buffers Shared cache competing with OS and private memory Change only with a host budget and restart window.
maintenance_work_mem / autovacuum memory Maintenance and worker concurrency Sum concurrent operations before increasing.
Connection pool / max_connections Backend memory, contention, reserved admin access Remove idle transactions and cap pools before raising server capacity.
Temp-file activity Sort/hash spill or large intermediate results Check query shape and selective indexes before adding RAM.
Checkpoints/WAL/archive Bursty I/O or retained WAL Correlate with disk latency, slots and archiver health.

PostgreSQL memory is not a single buffer-pool cap.[63] Compare database views with host CPU, filesystem bytes/inodes, storage latency and memory/swap, taking matched time samples. A high buffer hit ratio can coexist with slow locking, CPU-heavy queries or WAL waits. Change one hypothesis at a time; record old values, workload, interval and result, then revert changes that do not improve the chosen objective.
