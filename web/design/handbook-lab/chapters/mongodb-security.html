Separate the controls

Control Question answered Baseline
Network ACL/firewall Which machines can reach the listener? Private interfaces; explicit application/member allowlist
TLS identity Is this the expected peer, and is transport encrypted? Trusted CA, matching DNS SAN, requireTLS
Authentication Which user/member is connecting? SCRAM-SHA-256 users; keyfile membership in the lab
Authorization Which actions on which resources? Explicit least-privilege roles
Storage encryption What can a stolen disk/snapshot reveal? Host/volume encryption for Community
Backup/secret controls Can recovery work without exposing credentials/data? Encrypted off-host copies, separated keys, restore drills

Bind selection is not an access-control list; loopback is a bootstrap boundary, not sufficient isolation against other local users. Keep authorization enabled, patch the OS/server/clients, use a dedicated unprivileged service account, and keep its data/log/key directories unavailable to unrelated users.[6][9][14]

Use custom collection roles, not root for an application. User administrators can elevate privileges and need strong custody. Check permissions from fresh allowed and denied sessions; an authenticated ping is not a least-privilege test.[18][85]

Scope firewalld before remote binding

RHEL 9 uses firewalld zones and separate runtime/permanent configuration. An allow rule is not a deny-all policy: existing broad ports/services, source-based zone selection, trusted/ACCEPT zones, forwarding or upstream ACLs can defeat the intended restriction. Inventory them first and keep an out-of-band administration path; do not move interfaces or remove SSH access blindly.[109][111]

sudo firewall-cmd --state
sudo firewall-cmd --get-active-zones
sudo firewall-cmd --list-all-zones
sudo firewall-cmd --permanent --list-all-zones

The worked rule assumes the database interface is already in an approved restrictive public zone and 192.0.2.40/32 is a documentation placeholder for one authorized client. Substitute the actual zone and host source address seen after NAT. Check that no existing rule admits everyone to 27017. Add/test one source-qualified rule at runtime, then persist that exact rule after acceptance; do not save unrelated runtime changes with --runtime-to-permanent.[109]

sudo firewall-cmd --zone=public \
  --add-rich-rule='rule family="ipv4" source address="192.0.2.40/32" port port="27017" protocol="tcp" accept'
sudo firewall-cmd --zone=public \
  --query-rich-rule='rule family="ipv4" source address="192.0.2.40/32" port port="27017" protocol="tcp" accept'
# Test a NEW TLS/authenticated connection from the allowed client and
# a NEW connection from an unapproved host; the latter must not reach the port.
sudo firewall-cmd --permanent --zone=public \
  --add-rich-rule='rule family="ipv4" source address="192.0.2.40/32" port port="27017" protocol="tcp" accept'
sudo firewall-cmd --check-config
sudo firewall-cmd --permanent --zone=public --list-rich-rules
sudo firewall-cmd --zone=public --list-rich-rules

Rollback removes that same exact rich rule with --remove-rich-rule in runtime and permanent configuration, followed by readback. A controlled firewall-cmd --reload later proves persistence but replaces runtime-only rules with permanent state; audit those differences before reloading. Test fresh connections after reload/reboot, not an already established session.[109]

Destination Approved sources only TCP
Standalone/replica member Actual application/backup/monitor hosts; every peer member for a replica set 27017
Router Approved application/admin/backup/monitor hosts 27017
Shard members Peer/internal cluster hosts and authorized maintenance/backup hosts, not general application clients 27018
Config members Peer/internal cluster hosts (including shards/routers) and approved maintenance hosts 27019
Local restore instance None remotely; retain loopback bind, no inbound opening 27018 locally

Build the complete private cluster communication matrix: all members need the documented inter-member connections, not just app-to-primary access. Repeat scoped rules for the actual member addresses/ports on each destination. If IPv6 is enabled/bound, implement equivalent family="ipv6" rules with approved /128 or reviewed CIDRs; IPv4 rules do not constrain IPv6. Review egress policy, DNS/CA reachability and upstream firewalls separately. mongod_port_t labels permit daemon use of ports; they do not grant remote hosts access.[103][109]

Require TLS and validate identity

Configuration mutation and restart. Before binding remotely, obtain certificates from the approved CA. Each server PEM contains its own private key, certificate and required intermediate chain. SANs must include the exact DNS names clients/members use; include localhost only where the local TLS bootstrap requires it. Check validity, chain, key match and permitted usage before deployment. For inter-member TLS the node certificate must support its server/client roles.[14][58]

Paths used consistently in these notes:

/etc/mongodb/tls/ca.pem      trust bundle, no private key
/etc/mongodb/tls/server.pem  this host's certificate + private key
/etc/mongodb/rs0.key         shared membership secret (replica lab)
/etc/mongodb/cluster.key     shared membership secret (sharding lab)

The service must read them, but other users must not read private material. Keep root ownership for policy/config where possible, with controlled group/read access for mongod. Example installation of already approved artifacts on the target host:[13][14]

sudo install -d -o root -g mongod -m 750 /etc/mongodb
sudo install -d -o root -g mongod -m 750 /etc/mongodb/tls
sudo install -o root -g mongod -m 640 approved-ca.pem /etc/mongodb/tls/ca.pem
sudo install -o mongod -g mongod -m 600 approved-node.pem /etc/mongodb/tls/server.pem
sudo restorecon -Rv /etc/mongodb
sudo ls -ldZ /etc/mongodb /etc/mongodb/tls
sudo ls -lZ /etc/mongodb/tls
sudo -u mongod test -r /etc/mongodb/tls/server.pem

Use the host policy’s expected /etc/certificate contexts (matchpathcon -V), not home-directory labels carried in by a move. The pinned mongod policy reads generic /etc files and certificate types; DAC still restricts the private key. Do not label secrets as writable database files to force access. test -r checks DAC only: verify actual mongod startup/new TLS connections in mongod_t and review AVCs under enforcing mode.[108][110]

Merge into existing /etc/mongod.conf; this example exposes only the chosen private interface plus loopback and allows SCRAM clients without client certificates:[6][14]

net:
  port: 27017
  bindIp: 127.0.0.1,db1.example.net
  tls:
    mode: requireTLS
    certificateKeyFile: /etc/mongodb/tls/server.pem
    CAFile: /etc/mongodb/tls/ca.pem
    allowConnectionsWithoutCertificates: true
    disabledProtocols: TLS1_0,TLS1_1
security:
  authorization: enabled

Retain any existing keyfile and replica settings; replacing the whole security block and losing keyFile breaks membership authentication. Configure firewall rules before remote start. Restart a standalone in a maintenance window; for existing TLS replica sets use rolling member maintenance and keep quorum. Migrating a live plaintext set requires the documented staged TLS modes and client transition, not switching one member blindly to requireTLS.[14]

mongosh --host db1.example.net --port 27017 --username operator \
  --authenticationDatabase admin --tls --tlsCAFile=/etc/mongodb/tls/ca.pem

Acceptance: trusted/hostname-matched connection and protected operation succeed; plaintext, wrong CA, wrong hostname and unauthorized identity fail as expected. Inspect logs without logging secrets. Do not use tlsInsecure, invalid-certificate or invalid-hostname flags to make these negative tests pass. If startup fails, correct certificate permissions/chain/config or restore the last secure known-good config while keeping exposure restricted.[14]

SCRAM, x.509 and internal authentication

SCRAM-SHA-256 authenticates username/password accounts in their authentication database. Use passwordPrompt()/client prompts; never a reusable password literal in a shell command. x.509 client authentication instead maps a certificate subject to an external user in $external; trust in the CA alone does not grant the client’s database role.[18][58]

For an approved client certificate, copy its exact RFC2253 subject from the certificate inspection result—do not guess or normalize its distinguished name. Create the corresponding external user as user administrator:[58]

// Replace the marked subject with the EXACT approved certificate subject.
const subject = "<EXACT_RFC2253_CLIENT_CERTIFICATE_SUBJECT>";
db.getSiblingDB("$external").createUser({
  user: subject,
  roles: [{role: "read", db: "shop"}]
});

mongosh --host db1.example.net --port 27017 --tls \
  --tlsCAFile=/etc/mongodb/tls/ca.pem --tlsCertificateKeyFile=/secure/client.pem \
  --authenticationMechanism=MONGODB-X509 --authenticationDatabase='$external'

Authorize only the intended subject/role; test another valid but unregistered client certificate is denied protected access. Do not reuse cluster-member certificates as client identities.[58]

Internal authentication is separate from application authentication. Keyfiles provide shared-secret membership and enable access control; all communicating replica/sharded members need compatible shared keys. File permissions must deny group/world access on Unix. Keyfiles do not encrypt transport; pair them with TLS.[13]

For production x.509 membership, use the official member-certificate requirements: trusted chain, required matching organization-related attributes or explicitly configured membership attributes, distinct client-versus-member subjects, and appropriate extended key usage. Configure security.clusterAuthMode: x509 and net.tls.clusterFile/CA options where separate member certificates are used. A conversion from keyfile is a staged rolling procedure (sendKeyFile/sendX509 transitions as documented), not a one-node instant switch. Plan it on a restored staging topology first.[88][91]

Rotate without breaking trust

TLS rotation and membership-key rotation are different operations. For TLS, retain trusted CA overlap across servers and clients, distribute valid new PEM/CA files at the same paths, preserve ownership/modes and restore/check expected SELinux contexts after replacement, then run on each process with the rotateCertificates privilege:[52]

db.getSiblingDB("admin").runCommand({
  rotateCertificates: 1, message: "scheduled certificate renewal"
});

The command reloads applicable certificate/CA/CRL files. If the private-key file is encrypted, its password must remain the configured password for online rotation; changing that secret requires a different reviewed procedure. Do not infer success for all members from one command. Test new client/member connections after each rotation; existing connections can hide a failed trust change. Keep the old valid files for rollback until acceptance and then remove obsolete trust after every dependent client/member has moved.[52]

For shared membership key rotation, use the documented keyfile multi-key rolling process: distribute a file accepting old/new keys to every member, roll while retaining majority, transition the sending/accepted key set, then remove the old key only after all members have converged. Replacing the shared key on one member with a disjoint secret partitions it. Certificate renewal does not rotate this secret. On replica sets the documented sequence is two rolling passes: first every keyfile accepts old and new; then every keyfile contains only the new key, with secondaries first and primary stepdown in each pass.[65][66]

At-rest encryption and recovery keys

MongoDB Enterprise’s encrypted storage engine and its key-management options are not available as a Community YAML switch. Do not publish security.enableEncryption/KMIP commands as Community instructions. For this baseline, provision OS/volume encryption under the platform’s supported process and verify mount/unlock/reboot/recovery behavior before placing the dbPath there.[11]

Boundary Still needs protection
Encrypted disk Running privileged processes can read data; logs/temp/swap may live elsewhere
TLS Plaintext on client/server endpoints and exported files
Backup encryption Keys, metadata, credentials, restore worker and offsite deletion authority
Client-side field encryption Driver/library/edition feature compatibility, key vault and application access patterns

Do not assume every client-side encryption feature, automatic encryption workflow or Queryable Encryption backup tool is available in every edition. The pinned Tools manuals explicitly exclude mongodump/mongorestore use for Queryable Encryption collections; those require a separately supported backup design.[2][3][11]

Escrow recovery keys separately from the only encrypted backup. Record key identifiers and rotation history, not secret bytes in an evidence report. Test restoring an older retained backup after rotation; deleting its last required key makes that backup unrecoverable.

Secret, log and incident discipline

Use interactive prompts for manual operations. For automated Tools jobs, a protected --config file can carry the documented sensitive fields; use restrictive permissions and a secret manager/rotation policy. Environment variables and command-line URIs can leak through process/environment dumps, shell history, CI logs and copied diagnostics.[2][3]

Never store keys/passwords in notes, source control or fixture JSON. Restrict profiler data, shell history/output and diagnostic logs, which can contain query/customer data. FTDC does not sample end-user collection/index data or include query contents; it does include hostnames, OS information and configuration metadata, so inspect its privacy boundary before sharing it.[96] Clear exposed artifacts through an incident process and rotate compromised secrets; simply deleting one history entry does not revoke a leaked credential.[23][43]

Lost administrative access is a controlled recovery incident. First use an independently secured administrator or restored access plan. Any exceptional auth-disabled recovery must be isolated at the OS/network level and follow a topology-specific official procedure; this manual intentionally provides no public-listener bypass recipe. Validate allowed/denied operations again after recovery.[7][9]
