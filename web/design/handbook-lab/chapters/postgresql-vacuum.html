Maintain the MVCC lifecycle

An update normally leaves an old row version behind. A delete marks a version dead; it does not immediately make its space reclaimable. Vacuum removes versions no snapshot can still need, updates free-space/visibility information and freezes old transaction identities. Analyze samples values for the planner. These are different jobs even when VACUUM (ANALYZE) requests both.[10]

Operation Changes Concurrency / disk behavior
VACUUM notes.orders Reclaims dead-version space for reuse, maintains visibility and freezing Normal reads/writes continue, but I/O and lock conflicts still matter; usually does not shrink the file.
ANALYZE notes.orders Updates estimated row counts/value distribution Run after bulk load or major distribution changes; not a dead-row cleanup.
VACUUM (ANALYZE, VERBOSE) notes.orders Both tasks, with diagnostic messages Run outside a transaction block.
VACUUM (FREEZE) notes.orders Aggressively freezes eligible tuples Extra work, not a reason to disable automatic freezing.
VACUUM (FULL, ANALYZE) notes.orders Rewrites a compact copy, returns space to OS ACCESS EXCLUSIVE lock and extra disk space; planned outage, not routine maintenance.
Autovacuum Schedules ordinary vacuum/analyze by thresholds and age Does not perform VACUUM FULL; keep enabled.

The command must be issued by an authorized owner/maintenance role; database ownership does not grant unrestricted maintenance of shared catalogs. PostgreSQL 18 offers MAINTAIN privileges and the predefined pg_maintain role, which is much broader than one-table access.[19][56][57]

Find the bottleneck before tuning

Start read-only in the affected database. Statistics are estimates, and counters can reset; compare samples taken over a known interval. Slot transaction horizons and maintenance progress answer different questions from dead-tuple estimates.[25][89][90]

SELECT relid::regclass AS relation, n_live_tup, n_dead_tup,
       n_mod_since_analyze, last_autovacuum, last_autoanalyze,
       vacuum_count, autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;

SELECT pid, usename, state, xact_start, backend_xmin,
       age(backend_xmin) AS xmin_age, wait_event_type, wait_event
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;

SELECT slot_name, slot_type, active, xmin, catalog_xmin,
       age(xmin) AS xmin_age, age(catalog_xmin) AS catalog_age
FROM pg_replication_slots;
SELECT gid, prepared, owner, database FROM pg_prepared_xacts;
SELECT pid, relid::regclass, phase FROM pg_stat_progress_vacuum;
Observation Likely next investigation
Dead tuples grow despite frequent vacuum Old snapshots, abandoned transactions, prepared transactions, slot xmin retention.
Vacuum rarely starts Per-table thresholds, worker capacity, disabled settings, repeated cancellation.
Vacuum active but little progress Lock wait, storage throughput, cost throttling, large indexes or retained tuples.
Plans stale after bulk load Analyze separately; waiting for a vacuum threshold is unnecessary.
Disk did not shrink after vacuum Reusable space inside the relation is expected, not failed cleanup.

Resolve long transactions with their application owner. A prepared transaction may represent an external coordinator’s decision; do not guess COMMIT PREPARED versus ROLLBACK PREPARED. A stale slot may be retaining required data for a real subscriber. Dropping it can force a rebuild. Do not terminate sessions or drop slots purely because an age column is large.[10]

Tune the table, then measure again

Thresholds combine a fixed component and a table-size component; large tables may need smaller scale factors to avoid a huge maintenance backlog. PostgreSQL 18 also has insert-triggered vacuum and a maximum vacuum threshold, so the old “updates plus deletes only” rule is incomplete. Inspect current settings instead of assuming every installation uses defaults.[10]

SELECT name, setting, unit, context
FROM pg_settings
WHERE name LIKE 'autovacuum%' ORDER BY name;
SELECT relname, reloptions FROM pg_class
WHERE oid = 'notes.orders'::regclass;

Example for a measured, high-churn table—not universal tuning values:

ALTER TABLE notes.orders SET (
  autovacuum_vacuum_scale_factor = 0.02,
  autovacuum_vacuum_threshold = 1000,
  autovacuum_analyze_scale_factor = 0.01,
  autovacuum_analyze_threshold = 500
);

Record the old reloptions, sample dead tuples and vacuum duration, then compare the next workload cycle. More aggressive scheduling can increase I/O contention. Worker count, maintenance memory and cost delay must fit the host across all databases, not just this table. Table storage-parameter changes need no server restart. Undo this example by restoring the recorded values, or remove these overrides to inherit cluster defaults:

ALTER TABLE notes.orders RESET (
  autovacuum_vacuum_scale_factor, autovacuum_vacuum_threshold,
  autovacuum_analyze_scale_factor, autovacuum_analyze_threshold
);

Autovacuum does not analyze partitioned parent tables automatically in the same way as ordinary leaf tables; explicitly analyze the parent after changes that affect its combined distribution. It also cannot work on a session’s temporary tables. PostgreSQL 18’s manual VACUUM/ANALYZE traversal of inheritance children changed; use ONLY when the intended target is strictly the named parent.[4][10]

Prevent transaction-ID exhaustion

Transaction IDs have a finite wraparound space. Freezing makes sufficiently old tuple versions safe regardless of later counter wraparound. Insert-only and nearly static tables still need it. The protective autovacuum activity for wraparound is not ordinary optional housekeeping; disabling normal autovacuum does not remove that requirement.[10]

SELECT datname, age(datfrozenxid) AS xid_age,
       mxid_age(datminmxid) AS multixact_age
FROM pg_database ORDER BY age(datfrozenxid) DESC;

SELECT oid::regclass AS relation, age(relfrozenxid) AS xid_age,
       mxid_age(relminmxid) AS multixact_age
FROM pg_class
WHERE relkind IN ('r','m') ORDER BY age(relfrozenxid) DESC LIMIT 20;

Alert well before configured freeze ages, using rate of age growth and measured maintenance duration to budget time. Include MultiXact age, not only XID age. When warnings occur: locate the oldest relations in each database, remove blocking old snapshots by an agreed application action, ensure disk/I/O capacity, and run ordinary targeted VACUUM as an authorized maintainer. Verify ages fall. Repeatedly cancelling an anti-wraparound worker or increasing limits only postpones the hazard. If the server reaches refusal thresholds, follow the official emergency procedure with a DBA rather than applying pg_resetwal as a fix.[10]

Distinguish bloat from necessary space

Bloat is allocated space that is persistently excessive for the live workload; free space for the next update cycle is often useful. n_dead_tup and file size alone do not measure exact reclaimable bytes. Investigate row growth, TOAST, indexes, long snapshots and maintenance history first.[10]

  1. Capture relation/index sizes and workload rates. Remove the retention cause before a rewrite.
  2. Run ordinary vacuum/analyze and observe reuse over a representative cycle.
  3. If the OS must recover space, estimate free disk for the rewritten relation/indexes, WAL/archive growth and replicas; book a maintenance window for VACUUM FULL.
  4. For an isolated bloated index, evaluate REINDEX INDEX CONCURRENTLY rather than rewriting the table. Concurrent rebuilds still consume space, can wait on transactions and have restrictions; read the target command reference before applying it.[68]
  5. Compare size, query plans, constraints and replication/archive health afterward. A rewrite is not transactionally “undone” after completion; restore or rebuild from a known-good source if validation fails.

Do not schedule VACUUM FULL nightly or disable autovacuum to reduce visible activity. That trades manageable background work for locks and future outages. Continue with measured plans and indexes.
