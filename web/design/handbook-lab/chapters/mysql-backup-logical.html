Backup and recovery

Applies to MySQL Server 8.4 LTS; the production baseline is RHEL 9 x86_64 with Oracle MySQL Community RPMs from the MySQL Yum repository. Separately licensed products and other platforms are identified explicitly.[1][72]

Backup and Restore

Term Meaning and caveat
Cold backup Server stopped cleanly while a consistent copy is taken; not merely a running database with locks.
Warm backup Some activity blocked, such as writes/table access, during copying; define the exact locks and engines involved.
Hot/online backup Server remains running; may still take brief locks or constrain DDL. “Hot” does not promise zero blocking.
Restore Reconstruct files/objects/data from a backup into a selected instance.
Recovery Apply the necessary redo/binlog or other recovery steps to reach a consistent state or chosen time; not only salvaging damaged files.

[43][45][78][137]

Disaster recovery

Choose a plan against explicit recovery-point (RPO) and recovery-time (RTO) objectives, failure domains, cost and operational complexity. Keep consistent full backups and supported incremental/log chains, protected off-host copies, recoverable keys, monitoring and a practiced incident runbook. Test isolated restores regularly and measure the achieved recovery point/time.

A replica or cluster can improve availability but can also replicate deletion or corruption. It is not an independent historical backup. Managed services (the source named Amazon Aurora MySQL) have their own engine versions, backup/restore and regional failover contracts; this self-managed MySQL 8.4 guide does not certify them or promise simplified recovery. Verify the chosen service’s official documentation separately.

Logical backups

Logical backups preserve object definitions and/or data in logical form. A SQL dump contains SQL statements; CSV or other delimited data files are not SQL and need their own schema, encoding, NULL/escaping and loader contract. Neither is a physical copy of all server state.

mysqldump

mysqldump option Meaning in the 8.4 client
-A, --all-databases Dumps selected server databases subject to tool exclusions/privileges; not a physical image of all server state or external keys/configuration.
-B, --databases db1 db2 Includes database-selection and creation statements for named databases.
-R, --routines Include stored procedures/functions; inspect definers and required target privileges.
-E, --events Include scheduled events; control event execution during restore validation.
--triggers Include triggers (enabled by default); target version/privileges still matter.
--single-transaction Starts a consistent transaction for transactional tables and disables --lock-tables; not consistent for changing MyISAM/MEMORY data. Avoid concurrent DDL such as ALTER/DROP/RENAME/TRUNCATE during the dump.
--lock-all-tables Holds a global read lock across the dump; conflicts with --single-transaction and blocks writes. Plan an outage/lock window.
--set-gtid-purged=OFF Omits the GTID-purged and related sql_log_bin manipulation. Whether restored changes receive GTIDs depends on target logging/GTID configuration; it does not simply “make a backup safe.”
--ignore-table=db1.tb1 Exclude exactly that qualified table; repeat the option for another table. No trailing comma or comma-separated list.
--add-drop-database Adds destructive DROP DATABASE before CREATE statements where applicable. Avoid for merges/production imports; not inherently a replication requirement.
--no-create-db Suppresses CREATE DATABASE statements normally added with --databases / --all-databases.
--no-create-info Data without CREATE TABLE statements; not a complete independently restorable dump.
--no-data Definitions without rows.
--source-data=1 / =2 Records source file/position as an active CHANGE REPLICATION SOURCE TO statement or a comment. Can require a brief global read lock even with --single-transaction. Replaces historical --master-data.
--compact Enables a set of reduced-output options, not just comment removal; inspect its effects on DROP/LOCK/charset statements.
Pipe through pv -trb Optional separate Unix utility reports elapsed time/rate/bytes, not database restore correctness.
Pipe through gzip Actually compresses the byte stream. A .gz filename alone does not compress it.
> file.sql Shell redirection overwrites a file. Use unique controlled filenames and restrictive permissions. A timestamp naming example should avoid colons when files cross platforms.

Example for an existing all-InnoDB app schema, a trusted TLS endpoint, no concurrent DDL, and a least-privilege dump account provisioned for the chosen flags. db.example.com, CA path and output path are site inputs. Bash/EL9 only:

umask 077
set -o pipefail
mysqldump --host=db.example.com --user=backup --password \
  --ssl-mode=VERIFY_IDENTITY --ssl-ca=/etc/mysql/trust/ca.pem \
  --single-transaction --routines --events --triggers \
  --set-gtid-purged=OFF --databases app \
  | gzip > "app-$(date +%Y%m%dT%H%M%S).sql.gz"

This example is for a logical application restore, not an automatic GTID replica seed. Record the command/options, server/client versions, object inventory, completion/exit status and checksums. A failed pipeline can leave a partial file; quarantine it. For replication/PITR, separately capture the matching snapshot coordinates/GTID set using the documented consistency procedure. Required privileges can include SELECT, SHOW VIEW, TRIGGER, EVENT, routine visibility, and others depending on tablespaces, locks and GTID options; do not grant ALL merely to suppress an error.

Historical mysqlpump

mysqlpump was removed in MySQL 8.4. The original mysqlpump -B db1 db2 > pump.sql and queue options are not 8.4 commands. --parallel-schemas=4:db1,db2 historically selected a schema queue; --default-parallelism=4 selected the default queue. Preserve that distinction when interpreting old jobs, but migrate them to a supported dump tool and retest restore format. Thread count should be benchmarked against source, network and destination capacity, not assumed equal to physical cores.

Validate a logical dump by restoring it

  1. Verify file integrity, decompression, manifest and successful dump completion. Encryption keys, config and routine/account dependencies need separate retention.
  2. Restore into an isolated disposable server, normally using original schema names. mysql --database=test < dump.sql does not redirect statements containing CREATE DATABASE, USE, fully-qualified names or DROP commands into test.
  3. Review the dump before import, isolate replication/events/outbound integrations, and authenticate with a prompted password and verified TLS where TCP is used. For a compressed SQL dump, decompress deliberately and check both decompressor and client exit statuses; use pipefail for pipelines.
  4. Check object definitions, definers, row counts/checksums where appropriate, constraints, routines and application business queries. mysqlcheck --user=operator --password --databases app checks supported table operations; it is not a proof of logical/business consistency.
  5. Record restore duration against RTO and recoverable point against RPO. Do not replace production until the rehearsed cutover is approved.

mysqlbackup ... validate validates an Enterprise Backup physical backup, not arbitrary SQL/CSV dumps. See the physical-backup chapter.

Point-in-time recovery with binary logs

Binlog format Meaning
STATEMENT Records SQL with replication context. Some statements are unsafe/nondeterministic; NOW() specifically has replication handling and is not by itself a valid blanket example of failure.
ROW Records row-change events; default in 8.4. Generally avoids statement nondeterminism but volume depends on workload/row-image settings.
MIXED Switches from statement to row events for cases classified unsafe; does not make arbitrary multi-source writes conflict-free.

Use SHOW BINARY LOGS; to inventory available logs and SHOW BINARY LOG STATUS; for current coordinates; neither guarantees a complete archived chain. A full backup plus every required binlog after its consistent boundary is needed. Archive securely off-host and retain source identity, checksums and encryption keys.

  1. Restore the base backup to an isolated target. Establish its exact snapshot coordinates/GTID state and which transactions already exist there.
  2. Inspect binlogs to identify the last complete transaction before the unwanted event. Time filters use the tool’s interpreted timestamps/timezone and are for locating events; pin validated event/transaction boundaries by file and position for final recovery.
  3. Generate a replay stream from all required files in original order. mysqlbinlog --start-position=... --stop-position=... applies the starting limit to the first file and the stopping limit to the last. Resolve these integers from actual logs; no universal numbers are supplied.
  4. Replay the normal executable output through mysql in a controlled session, checking both exit statuses and stopping on error. Test this exact boundary on the disposable target before production cutover. Do not add a database filter without understanding cross-database statements/row-event filtering.
  5. Reconcile resulting data, users/routines/events and application invariants, then plan cutover and retained rollback. Never replay the bad transaction merely to close a gap.
mysqlbinlog option/topic Correct use
--start-datetime, --stop-datetime Locate an interval; establish timezone and complete transaction boundaries before accepting a recovery point.
--start-position, --stop-position Byte/event positions, not transaction IDs; validate against named files.
--read-from-remote-server Retrieve logs through the server, including encrypted logs the server can decrypt. Use authorized credentials and identity-verified TLS.
--include-gtids, --exclude-gtids Filter GTID sets for applicable recovery/migration tasks, not “replication only.” Audit missing and duplicate transactions carefully. Existing GTID execution state influences replay.
-v, --verbose Adds decoded row commentary for inspection.
--base64-output=DECODE-ROWS Diagnostic pseudo-SQL comments, not a replay stream for row changes. Default AUTO retains executable BINLOG event payloads. NEVER also disables required row-event output.
/*! ... */ MySQL executable/version comments; do not strip them from a replay/dump assuming every comment is inert.

Retention is not reset

RESET BINARY LOGS AND GTIDS destroys binlog history and clears GTID execution state; it is not part of routine backup, replica setup or error repair. Do not run it on a source needed by replicas/PITR. If rebuilding a deliberately disposable instance, follow its complete provisioning procedure instead.

PURGE BINARY LOGS TO 'file' removes logs before the named file; BEFORE 'timestamp' removes logs older than a cutoff. These are destructive retention operations, not recovery commands. Before choosing a boundary, verify archived copies and restore tests, all connected/disconnected replica needs, delayed replicas, backup coordinates and the recovery-retention policy. NOW() is not a safe generic cutoff. Use server-managed expiry aligned with these dependencies; never delete binary logs using filesystem commands.

mydumper / myloader

These are third-party parallel logical tools, not Oracle mysqldump aliases. Their own project documentation/release notes govern compatibility. Before deployment pin the exact MyDumper release, read its matching help, authenticate through a restricted configuration or documented prompt mechanism, and test dump/load with that same release. A versionless password-on-command-line recipe is intentionally not provided.

Original option/task Review before using
-u, --user Authentication identity; provide only needed dump/load privileges.
-p, --password Tool-specific password handling; avoid literal command-line secrets and verify whether the selected version supports a prompt/config mechanism.
-t, --threads Parallel workers; budget source locks/snapshot consistency and target I/O.
mydumper -B, --database Database selection; the original -d as database was wrong for current MyDumper.
mydumper -o, --outputdir New protected dump output directory.
myloader -d, --directory Input dump directory; not a database-selection flag.

Select snapshot/locking behavior for all table engines; a fast multi-threaded dump is not automatically a consistent one. Preserve metadata files and check both tools’ completion status, then restore/reconcile in isolation. See the project documentation rather than borrowing Shell or mysqlpump queue syntax.

MySQL Shell 8.4 utilities

MySQL Shell is a separately installed tool; these calls use its JavaScript mode (\js), not SQL in mysql. The pinned Oracle-hosted 8.4 manual is used because the public /mysql-shell/8.4/ URLs now redirect to a newer manual. Use an 8.4 Shell maintenance build compatible with the source and destination and record its actual version.

Task JavaScript call pattern
Instance dump util.dumpInstance('/backup/instance', {threads:4, consistent:true})
Schema dump util.dumpSchemas(['app'], '/backup/app', {threads:4, consistent:true})
Table dump util.dumpTables('app', ['customers','orders'], '/backup/tables')
HeatWave-targeted dump util.dumpInstance('/backup/heatwave', {threads:4, ocimds:true, consistent:true}) after checking HeatWave’s current migration requirements.
Load Shell dump util.loadDump('/backup/app') against the deliberately selected isolated destination. This does not load a mysqldump SQL file.

Use new/empty writable output directories and a properly authenticated Shell session. Do not put connection passwords in JS source. The loader creates objects and inserts data; establish target privileges, free space, existing-object/GTID policy and restore isolation first.

Option Meaning
ocimds Real 8.4 option for HeatWave compatibility checks/adjustments. Not required for ordinary MySQL-to-MySQL backup and not a generic “safer” switch.
threads Total parallel worker connections (default 4); not mysqlpump’s per-schema queues.
consistent Default true. Establishes synchronized consistent snapshots under initial read/table locks and uses a backup lock where available; does not normally hold all tables read-locked throughout the data copy. Engine/DDL/privilege restrictions still apply; false can create inconsistent dumps.

Inspect documented required privileges and consistency-check failures. Avoid ignoreVersion or compatibility transformations as unexplained workarounds; record every transformation and test the loaded result.
