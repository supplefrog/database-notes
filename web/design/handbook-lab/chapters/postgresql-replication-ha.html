Replicate the right unit

                       physical WAL (whole cluster)
applications -> primary ----------------------------> standby
                    |                                      |
                    | WAL archive + base backups           | read-only queries
                    v                                      v
             independent recovery storage             promotion only after fencing

publisher database -- publication/table changes --> subscriber database
                  logical replication; separate schema/sequence policy
Mechanism Replicates Does not supply
Physical streaming WAL for the entire cluster, same major and compatible platform Selective table filtering, cross-major upgrade or automatic leader election.
Logical publication/subscription Selected tables’ data changes plus optional initial copy DDL, sequences, large objects, all extension state or a transparent HA copy.
WAL archive Durable retained segments for recovery/standby catch-up Live failure detection/routing.
External HA controller Failure decision, fencing, routing and rejoin policy A replacement for PostgreSQL backups or tested consistency settings.

Core PostgreSQL provides replication and promotion primitives, not the software that decides a primary has failed and fences it. A heartbeat alone cannot distinguish failure from network partition.[38][41][64]

Build an asynchronous physical standby

Two separate RHEL/PGDG hosts, both major 18 with compatible extensions, checksums/platform and maintained minor versions. Primary postgresql-18 is already running; standby has no running cluster at its target path. This bounded setup uses no external tablespaces. With tablespaces, stop and plan all target mappings. Require verified TLS, time/DNS, private routing and a restore-tested backup first.[32][38]

Example names/addresses are reserved documentation values: primary primary.example.test at 192.0.2.10, standby at 192.0.2.20. Replace them with actual private addresses and certificate identities. On the primary as administrator:

CREATE ROLE notes_repl LOGIN REPLICATION NOSUPERUSER NOCREATEDB NOCREATEROLE;
\password notes_repl

Set the password through the prompt with SCRAM selected, not in SQL history. Allow only the standby’s address, and only replication connections, before any broad reject rules:

hostssl replication notes_repl 192.0.2.20/32 scram-sha-256

Review settings on the primary. The following capacities are examples, not a formula for every topology:

wal_level = replica
max_wal_senders = 10
max_replication_slots = 10
max_slot_wal_keep_size = '10GB'

Changing wal_level, senders or slot capacity needs a restart; HBA and retention changes are reloadable according to pg_settings.context. Keep at least two sender connections free for a streaming base backup. The retention cap limits slot-induced growth at checkpoints but can invalidate a lagging consumer; it is not a guarantee of uninterrupted catch-up.[32][39]

On the separate RHEL 9.7 standby host install the same approved PGDG major-18 server/client/contrib and extension RPMs as the primary. Do not initialize its target: RPM installation alone does not create a writable database. Leave postgresql-18.service stopped/disabled and verify /var/lib/pgsql/18/data is empty, owned by postgres, mode 0700, with no process using it. If it contains data, stop and preserve/inventory it; do not delete it to make this recipe fit.[100]

Provision the primary CA at /var/lib/pgsql/tls/ca.crt and a passfile /var/lib/pgsql/.pgpass owned by postgres mode 0600 through secret management. Its matching database field is replication, with primary hostname/port and notes_repl. Use the TLS file-label checks; do not store credentials in primary_conninfo. Check primary firewalld allows only this standby source; the receiving standby needs outbound primary access, not a broadly opened inbound database port.[55][102][103]

As OS postgres on the standby:

/usr/pgsql-18/bin/pg_basebackup \
  --dbname='host=primary.example.test port=5432 user=notes_repl sslmode=verify-full sslrootcert=/var/lib/pgsql/tls/ca.crt gssencmode=disable passfile=/var/lib/pgsql/.pgpass application_name=standby1' \
  --pgdata=/var/lib/pgsql/18/data --format=plain --wal-method=stream \
  --write-recovery-conf --create-slot --slot=standby1 --progress
/usr/pgsql-18/bin/pg_verifybackup /var/lib/pgsql/18/data

-R creates standby.signal and connection/slot settings in postgresql.auto.conf; do not remove them. --create-slot fails if the named slot exists; inspect and determine ownership rather than dropping an unknown slot. If backup fails after creating a slot, review/remove the unused slot or it can keep retaining WAL.[32]

PGDG primary configuration lives inside PGDATA and is copied by this base backup. Save and replace/review it with standby-local postgresql.conf and pg_hba.conf; do not inherit the primary’s listener, TLS server identity, external includes, archive destination or local paths.[100] Review inherited postgresql.auto.conf for unrelated source overrides, retaining the intended primary_conninfo and primary_slot_name; never inherit a source data_directory, port or archive destination unchecked.

data_directory = '/var/lib/pgsql/18/data'
hba_file = '/var/lib/pgsql/18/data/pg_hba.conf'
listen_addresses = 'localhost'
port = 5432
unix_socket_directories = '/run/postgresql'
hot_standby = on
archive_mode = off

Set standby max_connections, max_worker_processes, max_wal_senders, max_prepared_transactions and max_locks_per_transaction no lower than required source values; install required libraries. For this admin-only standby, HBA can contain just local all postgres peer; enable any reporting TCP access separately with TLS/least privilege. On this second host 5432 must be free.[74] Before streaming or a logical subscription starts, inspect getsebool -a, the installed postgresql_selinux(8) policy documentation and AVC denials for server-originated outbound connections. If policy requires a PostgreSQL database-network boolean, enable only the verified installed boolean after a security review and record its prior value; do not enable all network booleans or generate broad allow rules. A successful unconfined pg_basebackup client is not proof that the confined WAL receiver/subscription worker can connect.[102]

sudo systemd-tmpfiles --create /usr/lib/tmpfiles.d/postgresql-18.conf
sudo restorecon -Rv /var/lib/pgsql/18/data /run/postgresql
sudo systemctl start postgresql-18.service
sudo -u postgres /usr/pgsql-18/bin/psql -X -h /run/postgresql -p 5432 -d postgres \
  -c 'SELECT pg_is_in_recovery();'

This is the default PGDG service on the second host, not a second controller for the primary. Configure its own PGDATA/log, check ps -eZ/AVCs and journal/collector output, then verify SHOW data_directory, system identifier, pg_is_in_recovery(), primary streaming state and a new fixture commit becoming visible. Rehearse clean stop/start and boot recovery before sudo systemctl enable postgresql-18.service; keep applications away until read-only state and security policy are proved. For nondefault paths use the PGDATA/drop-in/SELinux/mount relocation procedure, not a detached pg_ctl daemon.[100][102]

Monitor lag, slots and durability

On the primary, using an authorized monitoring role; slot restart_lsn is a retention boundary, not proof that the subscriber has applied every transaction:[25][90]

SELECT application_name, client_addr, state, sync_state,
       sent_lsn, write_lsn, flush_lsn, replay_lsn,
       write_lag, flush_lag, replay_lag
FROM pg_stat_replication;
SELECT slot_name, slot_type, active, restart_lsn, wal_status,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
FROM pg_replication_slots;

On a physical standby:

SELECT status, sender_host, sender_port, slot_name FROM pg_stat_wal_receiver;
SELECT pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn(),
       pg_last_xact_replay_timestamp();

Lag intervals are not guaranteed forecasts of catch-up time; an idle source can have an old replay timestamp without a backlog. Compare LSN positions, generation rate, receiver/apply state and storage throughput. A disconnected slot can fill primary disk; a cap can instead force a new base backup. Never delete pg_wal files or drop a consumer’s active slot to hide an alarm.[25][39]

Failure Response
TLS/authentication failure Inspect certificate hostname/CA, passfile ownership, HBA and SCRAM role; do not relax to trust.
Required WAL removed Retrieve from a valid archive if configured/available, otherwise rebuild from a new base.
Receive advances but replay stalls Check replay pause, conflicts with standby queries, resource settings and I/O.
Long standby queries conflict with recovery Choose delay versus cancellation consciously; hot_standby_feedback can reduce cleanup conflicts but retain bloat on primary.
Abandoned slot Confirm consumer retirement and rebuild consequence, then pg_drop_replication_slot for that exact inactive slot.

A production standby can add an authenticated restore_command for archive catch-up; access must be read-only and point to the same cluster/timeline history. Streaming alone cannot fetch WAL the primary has already recycled.[38]

Synchronous is a commit policy, not automatic HA

Asynchronous replication can lose acknowledged transactions if the primary fails before the standby durably receives them. To wait for this particular standby, set synchronous_standby_names = 'FIRST 1 (standby1)', where the name matches its application_name; reload and verify sync_state on the primary.[38][39]

synchronous_commit Wait condition (with a selected synchronous standby)
on Local durable WAL plus synchronous standby durable WAL.
remote_apply Also waits for standby replay/visibility; increases latency.
remote_write Standby OS has written WAL but may not have durably flushed it.
local Local flush only, not a standby acknowledgment.
off Does not wait for local durable commit; acknowledged recent work can be lost.

With no qualifying synchronous standby, commits can wait indefinitely. Changing the policy to resume writes is an explicit durability tradeoff, not an invisible health fix. Test loss of a standby, network partition and recovery while measuring both latency and data loss. Keep synchronous nodes in meaningful failure domains, and verify clients are not overriding the commit policy.[34][38]

Publish a bounded set of tables

Logical replication is useful for a selected-table copy or major migration, not an automatic full-cluster standby. For this example use adminlab on the publisher and a new adminlab_sub on a separate subscriber, with no application writes to the destination. A table’s primary key normally supplies replica identity for updates/deletes; REPLICA IDENTITY FULL is a fallback with performance/type limitations, not a default recommendation.[40][41]

  1. On the publisher set wal_level = logical, budget replication slots/senders, restart as required and retain the physical replication configuration if also used. Give notes_repl CONNECT on adminlab, USAGE on notes and SELECT on notes.orders for initial copy. Add a separate narrow TLS HBA rule for database adminlab from the subscriber; the special replication rule does not match logical database connections.[14][88]
  2. Copy the reviewed schema, not rows, to an empty destination. For the fixture, export only notes and exclude topology definitions so an existing publication/subscription is not recreated accidentally:[29][41]
# Publisher, as OS postgres; /secure must be owned/protected appropriately.
/usr/pgsql-18/bin/pg_dump -h /run/postgresql -p 5432 \
  -U postgres -d adminlab --schema-only --schema=notes --no-owner --no-acl \
  --no-publications --no-subscriptions --file=/secure/notes-schema.sql

Transfer the file through an approved secure channel and inspect it. On a separate subscriber cluster, create a no-login notes_owner and fresh adminlab_sub owned by it; if either already exists, stop and review, not overwrite. Revoke public database access. Install any required extensions first, then restore the fixture schema with correct ownership:[18][29]

# Subscriber, as OS postgres, after checking its identity/path/port.
/usr/pgsql-18/bin/psql -X -v ON_ERROR_STOP=1 \
  -h /run/postgresql -p 5432 -d adminlab_sub \
  -c 'SET ROLE notes_owner' -f /secure/notes-schema.sql

Do not create the fixture’s 2,000 rows there; initial synchronization will copy them. Review owners/grants independently because --no-acl intentionally omits source grants. A filtered schema dump can omit external dependencies; this bounded fixture has none, but a real schema needs an explicit dependency inventory. 3. As the table owner or appropriate administrator on the publisher:

CREATE PUBLICATION notes_pub FOR TABLE notes.orders;
  1. On the subscriber as a trusted superuser subscription owner for this bounded example, use a protected server-side passfile (matching database adminlab) and verified CA. This avoids embedding a secret in SQL/catalog connection text; non-superuser ownership has additional password/security restrictions that must not be bypassed casually.[42]
CREATE SUBSCRIPTION notes_sub
CONNECTION 'host=primary.example.test port=5432 dbname=adminlab user=notes_repl sslmode=verify-full sslrootcert=/var/lib/pgsql/tls/ca.crt gssencmode=disable passfile=/var/lib/pgsql/.pgpass'
PUBLICATION notes_pub
WITH (copy_data = true, create_slot = true, enabled = true, run_as_owner = false);

Do not run slot-creating subscription setup inside a transaction block. Default run_as_owner = false uses table-owner permissions for apply. Restrict who can alter subscriber table definitions/ownership; replication is a trust boundary, not merely a connection string.[42]

  1. Inspect pg_stat_subscription and pg_subscription_rel, wait for all subscribed tables to finish synchronization, and compare a quiet-source count plus keyed checks. Commit an approved fixture change on the source and verify it arrives. Watch the publisher slot and subscriber logs for conflicts/schema errors.
  2. Apply DDL deliberately to both sides (often additive subscriber changes first). Before subscriber cutover, stop source writes, prove all final changes applied, copy/update sequences and validate application state. Logical replication does not replicate sequences, schema changes or large objects.[41]

To abandon this copy, disable notes_sub, then drop it while the publisher is reachable so its slot is cleaned up. If the publisher is unavailable, follow the documented disassociation/slot-removal procedure and track the orphan explicitly; disabling alone keeps retention. Do not skip conflicting transactions to make replication appear green without reconciling missing data.

Promote only after fencing

  1. Establish whether the primary is truly failed or merely unreachable from one observer. Stop/reroute clients under the HA incident procedure; identify the best eligible standby and accepted RPO.
  2. Fence the former primary using a verified power/storage/network mechanism that prevents it accepting writes. Merely removing a DNS record or failing a health check is not fencing. If exclusive write authority cannot be established, do not promote into split brain.[64]
  3. Inspect replay/receive positions, pause state and required logical-slot readiness. For a planned switchover, stop writes and wait for the final committed position to replay. For an unplanned failure, explicitly record the possible data-loss window.
  4. On the chosen standby, run SELECT pg_promote(true, 60); as an authorized administrator. Verify pg_is_in_recovery() becomes false, perform a controlled write and readback, check the new timeline, then update the application endpoint/pool and confirm reconnect behavior.[23][64]
  5. Preserve old-primary files/logs for reconciliation. Reconfigure backups/archives for the new primary, create/rejoin a standby and test the degraded-period alert. Promotion does not automatically recreate redundancy.

Rejoin without creating a second primary

Safest general path: keep the old primary fenced, preserve any divergent data needed for reconciliation, replace its cluster with a fresh base backup from the new primary and start it as a standby using the physical procedure. This discards divergence only after an explicit decision.

pg_rewind can be faster for a compatible diverged cluster with common history. It needs target checksums or wal_log_hints enabled before divergence, full_page_writes = on, the required old WAL and a cleanly stopped target. Run --dry-run first with correct source/target and credentials; review exact official prerequisites before the write. A failed rewind can leave the target unusable—rebuild from base backup, not repeated improvisation.[44]

Rewind can copy source configuration. On RHEL, stop the exact target systemd unit before rewind and keep its boot/restart path fenced; restore file contexts with restorecon and inspect unit/drop-ins before allowing systemd to start it.[100][102] Before restart, correct local paths/ports/archive identity, create/verify standby recovery settings, and test pg_is_in_recovery(); starting it without standby configuration can diverge again. Restore client routing only after lag and consistency checks. Keep failover/rejoin drills, fencing evidence and measured RPO/RTO alongside the backup restore report.
