Choose the server, not the hosting product

These notes use self-managed MongoDB Community 8.0, WiredTiger, RHEL 9 x86_64, SELinux enforcing and systemd, using MongoDB vendor RPMs (not Red Hat AppStream). The concrete package baseline is 8.0.29; shell mongosh 2.10.0; Database Tools 100.17.0. Tools and shell have their own release numbers: neither is “MongoDB Tools 8.0.” Examples below are independent snippets, not one script to paste end-to-end. Use a fresh shell or a local block when repeating snippets that declare const bindings. These are pinned documentation targets, not a promise that a mutable repository still retains every package. Check package availability before changing a host.[4][5][48]

8.0 is a major release supported for on-premises use. The published Server lifecycle lists October 31, 2029 as 8.0 end-of-life under Enterprise Advanced; that date is not an entitlement to commercial support for a Community installation. RHEL 9 x86_64 is explicitly in the Community 8.0 installation matrix. Review advisories and supported OS/kernel combinations before adopting any pinned patch.[4][104][50]

Choice What it supplies What not to assume
Community Self-managed server, replication, sharding, transactions, authorization, TLS No Enterprise audit or encrypted storage engine
Enterprise Advanced Commercial distribution and subscription features Installation alone does not configure backup, auditing or key custody
Atlas Managed service, tier-dependent backup/security features Not the procedure or free substitute used here
Community SSPL Source available under Server Side Public License Not an OSI-approved open-source license; offering it as a service requires license review

Feature and license boundaries matter more than the download label. Community logs/profiling are not a security audit trail. Community can use host/volume encryption, but it has no security.enableEncryption equivalent to Enterprise’s encrypted storage engine.[11][15][47]

Executables and clients

Program Runs where Job
mongod Each data-bearing host Stores documents/indexes; runs replication and query execution
mongos Router host(s) Routes requests to shards; no application dbPath
mongosh Administrator workstation or DB host JavaScript/BSON shell; separately packaged
Driver Application Authentication, server discovery, pooling, read preference, retries
mongodump / mongorestore Backup worker BSON logical dump/restore, metadata and index definitions
mongoexport / mongoimport Migration worker JSON/CSV interchange; not a complete backup
mongostat / mongotop Monitor Server activity and collection time samples
bsondump Operator workstation Inspect BSON offline; can expose sensitive contents

The vendor RPM repository and Red Hat OS repositories have separate provenance/support responsibilities. mongodb-org-server, mongodb-org-mongos, mongodb-mongosh and mongodb-database-tools have different contents; a tarball does not create the package’s service user/configuration.[105][104]

Follow a request

application -> driver pool -> TLS handshake -> authentication
                                      -> authorization per operation
  standalone: mongod -> plan/execution -> WiredTiger
  replica set: driver discovers rs0 -> primary (writes)
                                  -> eligible member (reads)
  sharded: driver -> mongos -> config metadata/routing cache
                           -> shard replica-set primary/eligible reader
                           -> merge results -> client

Authentication establishes the user and authentication database; authorization checks roles against the target database/collection. TLS protects and authenticates the transport peer, not the user’s object privileges. A session is not a new authenticated socket for every operation: drivers pool connections and carry session identifiers across operations.[18][40][95]

The server matches a query shape to candidate access plans. Index scans may still fetch full documents; a collection scan is not automatically a bug on a tiny collection. explain distinguishes planning from measured execution, while the profiler records completed work. See measure an access path.[24]

A replica set keeps copies of the same dataset and elects a primary. Sharding partitions data across replica sets; mongos uses the shard key and routing metadata to target requests. Adding secondaries does not distribute writes to one unsharded collection. Adding shards does not rescue a poor shard key.[30][32][34]

Files are not collections you can copy independently

RPM defaults for this target are established by the versioned package specification, configuration and unit, not generic installation-page defaults:[100][101][102]

/usr/bin/                    mongod, mongos; separately packaged clients
/etc/mongod.conf             YAML startup configuration
/usr/lib/systemd/system/mongod.service  vendor unit
/etc/sysconfig/mongod        optional unit environment overrides
/run/mongodb/               vendor unit runtime directory
/var/log/mongodb/mongod.log   diagnostic log
/var/lib/mongo/            storage.dbPath
  WiredTiger*                engine metadata and supporting files
  _mdb_catalog.wt            catalog metadata (implementation detail)
  collection-*.wt            collection storage
  index-*.wt                 index storage
  WiredTigerHS.wt            history store
  journal/                   WiredTiger write-ahead journal
  diagnostic.data/           diagnostic samples
  mongod.lock                process/storage locking information

Names are illustrative, not an API or recovery recipe. Do not rename, remove or mix .wt files. A secondary index is a separate structure; ordinary _id indexing does not mean every collection is physically clustered like InnoDB. Back up the coherent instance, not selected engine files.[10][21]

Logical database Purpose
admin Administrative commands and users commonly authenticated against admin
local Node-local replication data, including replica configuration/oplog; not ordinary replicated app data
config Internal metadata, especially sharded cluster placement; never hand-edit routing records
shop Dataset used throughout these notes: orders, later customers and inventory

The RPM service runs as mongod:mongod, not a login/application user. Give the service user exclusive write access to its data/log directories. Separate databases inside one mongod still share storage, cache, CPU and failure domain. Use isolated instances when independent process/configuration boundaries are required; use separate hosts for real failure-domain separation.[6][31]

Configuration and identity

The service’s ExecStart determines which config file is read. Explicit command-line values override corresponding YAML values (for example --bind_ip overrides net.bindIp).[86][89] Inspect the unit and parsed options rather than trusting the file’s name. Most startup configuration edits need a restart; setParameter changes only documented dynamic parameters and is not a persistent settings file.[6][16]

// mongosh; clusterMonitor or another role allowing these inspections
const admin = db.getSiblingDB("admin");
admin.runCommand({getCmdLineOpts: 1});
admin.runCommand({buildInfo: 1});
admin.runCommand({hello: 1});
// FCV is inspected on a mongod, not on mongos:
if (admin.runCommand({hello: 1}).msg !== "isdbgrid") {
  admin.runCommand({getParameter: 1, featureCompatibilityVersion: 1});
}

Record binary version, FCV, dbPath, listener, replica-set name and host list before disruptive work. hello identifies a replica-set primary/secondary or mongos (msg: "isdbgrid"); connecting to the wrong endpoint can otherwise make a valid command dangerously wrong.[6][28][34]
