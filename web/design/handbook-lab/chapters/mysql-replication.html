Source-replica topology

MySQL asynchronous replication transfers binlog events from a source to one or more replicas. Circular/two-source (A↔B) and chained/ring (A→B→C→A) layouts are possible but not automatic conflict resolution or HA. Prefer a single-writer design unless conflict handling, failover/fencing and recovery have been explicitly engineered. Auto-increment offsets only reduce one class of generated-key collision; they do not resolve conflicting updates, deletes or explicit keys.

Prepare the source

  1. Inventory all members and choose unique nonzero server_id values and unique server UUIDs. Binary logging must be enabled; retain enough history to seed and catch up replicas. For 8.4 GTID replication, all participating servers must be in an appropriate compatible GTID state.
  2. For a new topology, configure gtid_mode=ON and enforce_gtid_consistency=ON before workload starts. For an existing OFF topology use the coordinated online-transition procedure, not a direct jump or reset.
  3. Provision a dedicated source account restricted to the actual replica host(s), with REPLICATION SLAVE and TLS requirements. Use a securely generated/provisioned credential; the source example’s literal secret is not retained as a usable password.
  4. Take a consistent seed backup and record its matching GTID set or binlog file/position using the selected backup tool’s documented procedure. Securely transfer/restore it to an isolated replica; preserve data and correct replication metadata.

Example account creation, replacing the documentation address with the approved replica host; capture the generated secret securely without session transcript logging:

CREATE USER 'replica'@'192.0.2.20' IDENTIFIED BY RANDOM PASSWORD REQUIRE SSL;
GRANT REPLICATION SLAVE ON *.* TO 'replica'@'192.0.2.20';
SHOW BINARY LOG STATUS;

SHOW BINARY LOG STATUS is the 8.4 statement; older notes use SHOW MASTER STATUS. Neither requires a reset beforehand. Historical RESET MASTER and 8.4 RESET BINARY LOGS AND GTIDS erase history and are not provisioning prerequisites.

For intentionally coordinated circular writers, the old auto_increment_increment=2 / offsets 1 and 2 illustrate distinct sequences. Choose values for the actual number of writers, test application assumptions and still implement conflict prevention. Do not enable circular writes merely by uncommenting these settings.

Configure a seeded replica

Use unique server_id, a stable relay-log basename and independent datadir/socket paths. For example, relay_log=/var/lib/mysql/relaylog belongs to that instance, not a shared directory. Set read_only=ON and normally super_read_only=ON to deter local writes; the replication applier can still apply events. Privileged operators can alter these settings, so they are not a security boundary by themselves.

Use named channels for multi-source designs. Current MySQL stores replication metadata in tables; old master_info_repository/relay_log_info_repository variables are not an 8.4 setup recipe. Do not import MariaDB metadata names into MySQL procedures.

GTID versus file/position

After verifying the seed, stop the relevant channel and choose one positioning method:

  • GTID: SOURCE_AUTO_POSITION=1 requests the transactions missing from the replica’s recorded GTID state. The seed’s data and GTID history must match; never clear history to hide errant transactions.
  • File/position: set SOURCE_AUTO_POSITION=0, the backup’s exact SOURCE_LOG_FILE and SOURCE_LOG_POS. Do not invent coordinates or combine them with auto-position. Account for purged logs before starting.

The following is a complete statement template for a GTID channel. Replace every site input, including the conspicuous secret placeholder, through your secure provisioning workflow; it is not a runnable universal recipe. Disable client history/transcripts around secrets. Paths are on the replica server, not the machine running the client.

STOP REPLICA FOR CHANNEL 'app';
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='source.example.com',
  SOURCE_PORT=3306,
  SOURCE_USER='replica',
  SOURCE_PASSWORD='<SUPPLY_SECURELY_AT_DEPLOYMENT>',
  SOURCE_AUTO_POSITION=1,
  SOURCE_SSL=1,
  SOURCE_SSL_CA='/var/lib/mysql/tls/ca.pem',
  SOURCE_SSL_VERIFY_SERVER_CERT=1
FOR CHANNEL 'app';
START REPLICA FOR CHANNEL 'app';
SHOW REPLICA STATUS FOR CHANNEL 'app'\G

For a new channel, the initial STOP can be omitted if no channel exists; do not suppress an unexpected error without checking identity/state. If the source account requires client certificates, add SOURCE_SSL_CERT and SOURCE_SSL_KEY to that same statement before FOR CHANNEL, with the private key readable only by the required service identity. There is no semicolon between its option lines and no trailing comma before FOR CHANNEL.

With verified TLS, GET_SOURCE_PUBLIC_KEY=1 is unnecessary. RSA password-exchange public keys are not TLS certificates or SSH keys. Do not weaken transport verification to cure an authentication error.

Filters and connection failover

CHANGE REPLICATION FILTER and option-file filters must be designed for the channel/binlog format and tested with cross-schema/routine behavior. Filtering can create intentional partial replicas that are unsuitable as full failover targets.

SOURCE_CONNECTION_AUTO_FAILOVER=1 requires GTID auto-positioning (SOURCE_AUTO_POSITION=1) and is optional after populating and validating alternative sources with the failover functions. For example, asynchronous_connection_failover_add_source('app','source2.example.com',3306,'',100) adds a source with a priority weight; use the documented delete function to remove stale entries. Inspect performance_schema.replication_asynchronous_connection_failover. Every listed source must serve the same intended history, support the account/TLS policy and retain needed GTIDs. Review SOURCE_RETRY_COUNT and SOURCE_CONNECT_RETRY: their default retry window can delay switching substantially. This changes connection source selection, not application-writer election/fencing.

Verify receiver/applier state, error fields and worker status as well as lag, GTID convergence and actual data. Seconds_Behind_Source=0 alone is not proof of consistency. RESET REPLICA discards connection/relay state according to its options; ALL also affects stored connection information. Neither is a routine “start clean” step, and neither substitutes for reseeding mismatched data.

Planned single-writer switchover acceptance

A channel’s source-connection failover does not promote an application writer. For an approved planned GTID switchover between equivalent unfiltered instances, rehearse this sequence with compatible versions, routing and rollback ownership:

  1. Fence application writes and scheduled jobs on the old source; set/verify its read-only protections, drain active write transactions, and retain an administrative session. Infrastructure fencing must prevent the old writer returning unexpectedly; SQL read-only flags alone do not supply that guarantee.
  2. Record the old source’s final @@GLOBAL.gtid_executed. On the intended candidate, check receiver/applier errors and wait for that exact set with WAIT_FOR_EXECUTED_GTID_SET(captured_gtid_set, approved_timeout_seconds). These are explicit SQL inputs supplied from the captured evidence. 0 means the wait succeeded; 1 is timeout; an error is failure. Stop on any failure, errant history or unresolved data discrepancy. A successful GTID wait alone does not compare rows or prove that a prior skipped transaction had its effects applied.
  3. After data/application checks and positive old-writer fencing, stop only the candidate’s intended channel, preserve its metadata, deliberately remove candidate read-only restrictions and redirect the approved writer endpoint. Verify one writable primary, new client TLS identity, writes/reads and replica progress. Do not reset binlogs/GTIDs as part of promotion.
  4. Repoint/reseed remaining replicas from the new authority only with compatible history and retained logs. Keep the old source fenced until it is reconciled and reintroduced safely. Once the new writer accepts changes, reverting a router entry is not rollback: catch up/reconcile the old instance or use the rehearsed restore path.

For unplanned loss, that final old-source boundary may be unavailable. Establish the most complete trusted survivor, quantify any loss against RPO, fence the failed writer and follow the incident runbook; never label a zero-lag counter as proof of zero data loss. Group Replication has separate quorum/outage-recovery rules and must not use this asynchronous promotion sequence blindly.

Recover from an applier error without hiding divergence

  1. Stop the affected channel, record full error/worker status, failing transaction identity and source/replica data. Preserve backup/logs before changing anything.
  2. Diagnose the cause: schema mismatch, duplicate/missing row, unauthorized local write, missing source logs, privilege error or storage failure. Correct configuration/permissions only if doing so does not alter transaction meaning.
  3. Prefer restoring/reseeding a replica from a consistent source when history or data cannot be proved equivalent. Do not reset GTIDs to make the error disappear.
  4. Only after explicit reconciliation and approval consider skipping a transaction. With GTIDs enabled, the documented method identifies and marks the exact GTID using the prescribed empty-transaction process; this permanently records it as executed without its original effects. It can propagate if logged. Audit and validate all affected rows and downstream replicas first.
  5. sql_replica_skip_counter is for the documented non-GTID mode cases, not a generic GTID cure. It counts events/event groups rather than intuitively “N bad SQL statements”; transaction boundaries matter. No blind SET ...=N recovery recipe is recommended here.
  6. Restart the intended channel only after resolving the cause; verify both applier/receiver and independent data reconciliation. Document any intentionally skipped history.

Crash recovery

MySQL 8.4 uses transactional replication metadata (including mysql.slave_relay_log_info and mysql.slave_worker_info) and GTID execution state where enabled. The source’s mysql.gtid_replica_pos is not the MySQL 8.4 metadata model.

relay_log_recovery=ON is a startup, not dynamic, setting. It reconstructs receiver progress from applier/transaction state and may fetch events again from the source; the source must retain required binlogs. Configure the documented durable relay/applier settings before failure, retain purging behavior compatible with recovery, and rehearse crash recovery. Do not try SET GLOBAL relay_log_recovery=ON after a crash or manually erase relay files as a universal repair.

Semisynchronous replication

Semisync waits for acknowledgments that the configured number of replicas have received and flushed the events to relay log; it does not mean their SQL appliers have committed those changes. rpl_semi_sync_source_wait_point determines the wait point, and timeout can fall back to asynchronous operation. Monitor whether semisync is actually active and acknowledge the durability/failover implications of each wait point.

For compatible 8.4 builds, choose source/replica plugins deliberately:

Side Installation/loading and enabling
Source Runtime INSTALL PLUGIN rpl_semi_sync_source SONAME 'semisync_source.so';, then enable rpl_semi_sync_source_enabled; or the corresponding plugin_load_add startup configuration.
Replica Runtime INSTALL PLUGIN rpl_semi_sync_replica SONAME 'semisync_replica.so';, then enable rpl_semi_sync_replica_enabled; or equivalent startup settings.

Check for an already installed plugin before issuing INSTALL. Runtime enablement alone is not restart persistence. A replica receiver thread that was already running needs the documented stop/start of its IO_THREAD (and intended channel) to advertise semisync capability. Test source status, acknowledgments, timeout/fallback, lag and failover before relying on the setup; installing the library is not verification.
