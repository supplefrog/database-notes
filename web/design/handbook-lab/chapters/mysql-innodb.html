Storage Engines

Engine Use and limits
NDB / NDBCLUSTER Distributed, highly available storage engine in the separate MySQL NDB Cluster product; not InnoDB Group Replication.
MEMORY RAM-resident table data; definitions persist but rows do not survive a server restart. Not all optimizer temporary tables use this engine.
CSV Stores table rows in CSV files; no indexes, with CSV-specific constraints. Useful for bounded interchange, not a transactional replacement.
BLACKHOLE Discards written data; specialized replication/logging experiments need binlog-format analysis.
ARCHIVE Compressed archival storage with restricted operations/index support; not a backup format.
MyISAM Nontransactional engine with table-level locking. Some workloads may favor it; “smaller and faster” is not a general rule. Prefer InnoDB when transactions, foreign keys and crash recovery are required.

[16]

InnoDB

ACID property InnoDB MyISAM
Atomicity Transaction rollback uses undo; application must handle statement errors, deadlocks and rollback scope. DDL commonly causes implicit commits. No transactional rollback.
Consistency Enforces supported constraints including foreign keys; application/business invariants remain the application’s responsibility. Supports some constraints such as unique indexes, but not InnoDB-style foreign keys.
Isolation MVCC plus record/gap locks and selectable isolation levels. Table-level locking coordinates statements but does not provide multi-statement transactional isolation.
Durability Redo, recovery, doublewrite and correctly configured flushing/storage. Not independent of settings or hardware. No transactional crash recovery; table repair is not committed-transaction recovery.

InnoDB is the default engine in 8.4 (historically the default since 5.5). Official architecture diagram is linked rather than republished.

In-Memory Data

The buffer pool, log buffer and internal structures use RAM; some cached structures have durable on-disk backing.

Buffer pool

  • Caches clean and dirty table/index pages. Default configuration starts small (128 MiB); size to the measured working set and total memory budget, including connections, other engines and the OS. “80% of RAM” is not universal, especially on shared or container-limited hosts.
  • The LRU diagram below shows the usual old/new midpoint policy. The old portion defaults to 3/8; flushing dirty pages and evicting pages are different operations.

Change buffer

  • Buffers eligible changes to secondary-index pages absent from the buffer pool, then merges them when needed or in the background. It has in-memory and persistent parts.
  • In 8.4 innodb_change_buffering=none by default. When enabled, innodb_change_buffer_max_size defaults to 25% of the pool, with maximum 50%; this is a limit, not a permanent reservation.

Adaptive hash index

  • Built by InnoDB from hot B-tree search patterns when enabled. It points to buffered index pages and can speed suitable lookups, but can also add contention.
  • Disabled by default in 8.4. Benchmark before enabling; it is not a user-created secondary index or optimizer hint.

Log buffer

  • Holds redo records describing changes, not a catalog of dirty pages. Writes/flushes are affected by commits, capacity and periodic flushing.
  • innodb_flush_log_at_trx_commit=1 and sync_binlog=1 are the usual strongest server settings for durable InnoDB/binlog commits; storage must honor flushes.

[8][9][10][21][129][90]

On-Disk Data

Redo Logs

  • Write-ahead logging

    • Persistent log of changes, before applied to on-disk pages

  • Changes can be reapplied to data pages if system crashes before/during writing

  • Durability depends on redo/binlog flush settings and storage guarantees; committed data can be lost with relaxed settings or faulty storage.

[10][21]

  • Temporary redo logs (#ib_redoXXX_tmp) - internal, pre-created spare files to handle log resizing and rotation

Tablespaces

  • System tablespace (ibdata1): stores the change buffer and may hold table/index data when not using file-per-table or general tablespaces. The 8.4 dictionary lives in mysql.ibd; default undo and doublewrite storage are separate. Old diagrams putting all of them in ibdata1 describe historical layouts.
  • General tablespace (.ibd): shared InnoDB container for multiple tables. Moving/dropping tables does not automatically shrink the file.
  • File-per-table (.ibd): one table’s data/index storage (or separate files for partitions). Availability of transportable tablespaces depends on table features and import restrictions.
  • Session temporary tablespaces (#innodb_temp/*.ibt): a pool starts with ten files. A session can receive two: one for user temporary tables and one for internal on-disk temporary tables. They are truncated/reused on release. Inspect INNODB_SESSION_TEMP_TABLESPACES; not all internal temp work reaches disk.
  • Global temporary tablespace (ibtmp1): remains supported in 8.4, not deprecated simply because session files exist. Stores rollback segments for user-created temporary tables. Default is auto-extending, initially slightly over 12 MiB. innodb_temp_data_file_path, for example ibtmp1:12M:autoextend:max:1G, bounds growth but can cause statements to fail at the limit. It is recreated on restart. Never delete it while the server is running; a normal controlled restart reclaims it without a manual deletion recipe.
  • Undo tablespaces: hold undo records for transaction rollback and consistent reads. They are not a network-delivery rollback mechanism. Long-running snapshots can delay purge and grow undo storage.
  • Doublewrite files: protect against torn page writes; normally separate .dblwr files in 8.4, not the old fixed system-tablespace location.

Glossary

InnoDB data changes run in transactions. With the usual autocommit=1, each statement forms its own transaction unless an explicit transaction is active. Use START TRANSACTION for a deliberate multi-statement unit; many DDL statements implicitly commit.

[140]

The default isolation level is REPEATABLE READ. A normal consistent read establishes a read view at the first consistent read in a transaction (or use WITH CONSISTENT SNAPSHOT where applicable). Later consistent reads reuse it. READ COMMITTED takes a fresh snapshot for each consistent read.

  • The read view tracks transaction visibility boundaries and active transaction IDs. Later transactions do not become visible merely because they commit.
  • A row’s transaction ID and undo chain allow reconstruction of an older visible version; a transaction sees its own changes.
  • Locking reads (FOR UPDATE / FOR SHARE) and DML do not simply reuse the nonlocking snapshot. Their locks and record-selection behavior depend on statement and isolation level. Mixing locking and consistent reads can expose different states.
  • Undo supports both rollback and MVCC; purge removes versions no active read view needs.
Term Meaning
Page Basic InnoDB storage/buffer unit, 16 KiB by default; configurable at instance initialization. Not the smallest OS write or individual SQL change.
Clustered key Explicit primary key; otherwise the first suitable UNIQUE NOT NULL index; otherwise an internal generated row ID.
Clustered index One per InnoDB table; leaf records contain the row data ordered by clustered key.
Secondary key Indexed columns used for alternate access paths, including columns that may overlap the primary key. Example: searching WHERE name='A'.
Secondary index Leaf records contain secondary-key columns plus the clustered key to locate the row. A covering query can avoid the extra clustered lookup. Additional indexes cost storage and write work.
