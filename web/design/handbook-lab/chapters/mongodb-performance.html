Logs, profiling and auditing are different

Facility Community 8.0 What it records / limitation
Diagnostic log Yes Startup, connections, errors, slow operations; not complete compliance audit
Database profiler Yes, on mongod Selected operation documents in system.profile; overhead and sensitive values
FTDC diagnostic data Yes Periodic diagnostic metrics and host metadata; disk/retention cost, not an event audit.[96]
Security audit facility Enterprise; Atlas availability depends on deployment Security/access event policy; separately configured and protected
Host/storage audit OS tooling File/process access, not a substitute for database authorization events

Do not tell a Community operator to turn on Enterprise auditLog options. Where compliance requires the supported audit facility, decide edition/service and review event coverage, filters, failed/successful authorization events, output protection and retention. Application access logging plus immutable external log storage can supplement Community, but does not become equivalent by renaming a log.[15][23]

Profile a bounded window

Requires enableProfiler/appropriate database administration privilege on shop; reading system.profile also needs access. Connect directly to the intended mongod; profiling is not available on mongos. Scope matters: the profiling level is per database; slow-operation threshold/sample settings affect diagnostic behavior more broadly on that process.[23]

const shop = db.getSiblingDB("shop");
const before = shop.getProfilingStatus();
printjson(before);
// Level 1 + filter, rather than recording every operation:
shop.setProfilingLevel(1, {filter: {ns: "shop.orders", millis: {$gte: 50}}});
// Run the authorized representative workload for a short, supervised window.
shop.system.profile.find({ns: "shop.orders"}, {
  ts: 1, millis: 1, planSummary: 1, keysExamined: 1, docsExamined: 1, nreturned: 1
}).sort({$natural: -1}).limit(20);
// Restore observed settings, including whether a filter previously existed:
shop.setProfilingLevel(before.was, {
  slowms: before.slowms, sampleRate: before.sampleRate,
  filter: before.filter || "unset"
});
shop.getProfilingStatus();

When a profiler filter is configured it supersedes slowms/sample-rate selection for profiling/slow-log selection as documented. Save the prior state outside the shell before enabling if a disconnect is possible. Level 2 captures all operations and can be expensive; do not leave it on by accident. system.profile is capped and rolls over, so copy required incident evidence promptly under data-access policy. Disabling profiling does not erase already collected sensitive documents.[23][84]

Explain one exact access pattern

Use the three-order fixture. The query is “recent orders for tenant t1,” not a benchmark. executionStats executes the read; it can be expensive on production. No timing or plan result below is claimed to have been measured.[20][24]

const shop = db.getSiblingDB("shop");
shop.orders.explain("queryPlanner")
  .find({tenantId: "t1"}).sort({placedAt: -1}).limit(10);
shop.orders.explain("executionStats")
  .find({tenantId: "t1"}).sort({placedAt: -1}).limit(10);
// Compare the existing fixture index explicitly, without changing global policy:
shop.orders.explain("executionStats")
  .find({tenantId: "t1"}).sort({placedAt: -1}).hint("tenant_recent").limit(10);
Mode/field Read it as
queryPlanner Winning/rejected candidate structure without running to completion
executionStats Execution statistics for the winning plan; actual work
allPlansExecution Additional candidate trial statistics; not full end-to-end runs of every plan
nReturned Documents produced; compare with work examined
totalKeysExamined Index entries scanned
totalDocsExamined Documents fetched/examined; not necessarily unique documents
COLLSCAN, IXSCAN, FETCH, SORT Collection/index access, document fetch, explicit sorting; plan layouts vary by execution engine

The tiny fixture may make a collection scan reasonable. A good representative result has bounded examined work relative to returned rows and avoids a large blocking sort; do not promise zero fetches unless the query is actually covered. explain does not populate/use the plan cache in the same way as ordinary query execution; compare real workload behavior too.[24]

For a covered projection, deliberately include all filter/sort/output fields and omit _id unless it is indexed:

shop.orders.createIndex({tenantId: 1, placedAt: -1, total: 1}, {name: "tenant_recent_total"});
shop.orders.explain("executionStats")
  .find({tenantId: "t1"}, {_id: 0, tenantId: 1, placedAt: 1, total: 1})
  .sort({placedAt: -1}).hint("tenant_recent_total").limit(10);

Creating indexes costs I/O, CPU, disk and write amplification. Check disk and replication lag, schedule builds, and compare sustained workloads before keeping both indexes. An index with tenant equality followed by descending time supports this access pattern; reversing fields can lose that useful prefix.[20]

Index decisions and reversible experiments

Index feature Use Cost / constraint
Compound Match common equality/sort/range patterns Prefix/order matters; one giant index does not serve all queries
Multikey Index array values Expansion increases work; a compound multikey index permits at most one indexed array field per document.[79]
Unique Enforce business identity Existing duplicates block build; sharded uniqueness must fit shard-key rules
Partial Index only documents meeting a filter Queries must imply the filter to use it safely.[76]
TTL Expire eligible time-based records Asynchronous deletion; not an exact scheduler or backup retention mechanism.[77]
Hidden Exclude an index from planner selection Still maintained and consumes space; unique constraints still enforced

Inspect usage/workload, then hide a redundant candidate before deleting it. The experiment below requires a supporting tenant_recent index and explicit approval to alter the second index:[20][36][42]

shop.orders.hideIndex("tenant_recent_total");
shop.orders.getIndexes();
// Observe representative application reads and writes.
shop.orders.unhideIndex("tenant_recent_total");

Hidden unique indexes still enforce uniqueness and all hidden indexes are maintained on writes.[98] Rollback is unhide, not rebuild. A hidden index cannot be tested by hinting it.[98] Drop only after a complete workload cycle establishes it is unnecessary and the exact name is recorded; dropping it is not rolled back by unhiding. Retain the creation specification if rebuilding is the recovery plan.[42]

Slow operation or overloaded host?

const s = db.getSiblingDB("admin").serverStatus();
printjson({connections: s.connections, opcounters: s.opcounters,
  locks: s.locks, wiredTigerCache: s.wiredTiger && s.wiredTiger.cache});

Use a monitoring identity, compare deltas and align timestamps with application latency. Inspect current operations for waits and query shapes. mongostat and mongotop from the separately pinned Database Tools provide repeated samples; run with authentication/TLS like other clients, not an embedded password.[10][104][51]

  1. High scan counts: verify predicate types/collation, index prefixes, selectivity and sort coverage before adding RAM.
  2. Locks/DDL waits: identify the holder and business operation; cancelling waiters may not remove the cause.
  3. Cache eviction + I/O: inspect working-set size, long transactions, index growth and storage latency together.
  4. Connection pressure: inspect driver pool counts/limits and application concurrency; raising server limits can amplify overload.
  5. Replication lag: correlate disk/write pressure and oplog window; a stale secondary is not a free read-scaling solution.
  6. No apparent DB pressure: measure application queuing, network latency, retries and downstream calls before tuning the database.

For RHEL host symptoms, correlate journalctl -u mongod, /var/log/mongodb/mongod.log, audit AVCs, storage latency and the actual process limits (systemctl show mongod, /proc/PID/limits). A login-shell ulimit does not describe the service. Preserve the RPM glibc environment and review RHEL tuned/THP settings against MongoDB 8.0 guidance instead of applying an older release’s tuning script.[62][101][110]

Keep one hypothesis/change at a time with a rollback value and representative before/after window. Never quote the fixture’s timing as a capacity result.[10][24][31]
