Replication and high availability

Replication is a durability topology

                 rs0 (one dataset)
application -> primary db1 -> oplog -> secondary db2
                         \-> oplog -> secondary db3
        election can move primary; driver discovers it

Use three data-bearing voting members across independent failure domains. Replica-set copies follow the same MongoDB dataset; they are not SQL logical-replication subscriptions or independent multi-primary writers. A one-member set enables replica-set semantics for a lab but has no redundancy. An arbiter votes but stores no data and cannot supply another durable copy; do not add one to disguise an unavailable data-bearing majority.[30][31]

The primary appends replicated changes to the node-local oplog; secondaries copy/apply them asynchronously. Initial sync builds a new member’s data/indexes and catches up from oplog. It requires enough history and resources to complete; a secondary that falls beyond retained history must resync, not skip errors until it looks current.[31][92]

Deploy a private, authenticated three-member set

New empty hosts, not an in-place production conversion. Provision the pinned packages on db1.example.net, db2.example.net, db3.example.net. These are reserved example DNS names: replace all names consistently in DNS, config, certificate SANs and connection URIs. Each must resolve/reach the others over a private network. Keep inbound firewall rules limited to members and approved clients using the RHEL firewalld matrix. Each data host uses the RPM mongod account, standard data/log paths and enforcing policy; verify those before topology initialization.[13][104]

Have a CA-signed node certificate/private key at /etc/mongodb/tls/server.pem and CA bundle at /etc/mongodb/tls/ca.pem on each host; each node’s private key/certificate is distinct. Server certificates used for inter-member TLS need appropriate client/server usage. See certificate requirements.[14][58]

Generate one shared internal-authentication key and securely distribute it to all members; do not generate a different key on each host. This is an OS-shell provisioning example, never a value to paste into notes:[13]

umask 077
openssl rand -base64 756 > rs0.key
sudo install -d -o root -g mongod -m 750 /etc/mongodb
sudo install -o mongod -g mongod -m 400 rs0.key /etc/mongodb/rs0.key
sudo restorecon -Rv /etc/mongodb
sudo -u mongod test -r /etc/mongodb/rs0.key
sudo ls -lZ /etc/mongodb/rs0.key

Remove the staging copy after verified secure distribution/escrow. On each host merge the following with the data/log configuration; substitute that host’s own name in bindIp. Never duplicate YAML net/security keys.[6][13][14]

net:
  port: 27017
  bindIp: 127.0.0.1,db1.example.net
  tls:
    mode: requireTLS
    certificateKeyFile: /etc/mongodb/tls/server.pem
    CAFile: /etc/mongodb/tls/ca.pem
    allowConnectionsWithoutCertificates: true
security:
  authorization: enabled
  keyFile: /etc/mongodb/rs0.key
replication:
  replSetName: rs0

allowConnectionsWithoutCertificates: true permits SCRAM clients without client certificates; it does not permit plaintext transport or bypass user authorization. Internal keyfile authentication authenticates members; TLS encrypts the connection.[13][14]

Start mongod.service on all three hosts only after SELinux, certificate/key access and scoped firewall checks. Check each process is confined (mongod_t) and has no unexplained AVC denials; then verify TLS/member connectivity. Enable boot start only after topology acceptance. On db1, connect through loopback for the localhost exception. Its certificate must include localhost as a SAN for this local TLS bootstrap (in addition to its private DNS name); do not bypass hostname verification:[7][14]

mongosh --host localhost --port 27017 --tls --tlsCAFile=/etc/mongodb/tls/ca.pem

rs.initiate({_id: "rs0", members: [
  {_id: 0, host: "db1.example.net:27017"},
  {_id: 1, host: "db2.example.net:27017"},
  {_id: 2, host: "db3.example.net:27017"}
]});
rs.status();

Initiate once, not on each node. Wait for the elected primary; create useradmin through the localhost exception on that primary, then authenticate and create the operation/application/backup users as in bootstrap. Users replicate with the set. If a different host becomes primary, connect locally there to finish bootstrap.[7][13]

Connect and verify the set

mongosh 'mongodb://db1.example.net:27017,db2.example.net:27017,db3.example.net:27017/shop?replicaSet=rs0&authSource=admin' \
  --username operator --tls --tlsCAFile=/etc/mongodb/tls/ca.pem

rs.conf();
rs.status();
db.getSiblingDB("admin").runCommand({hello: 1});
rs.printReplicationInfo();
rs.printSecondaryReplicationInfo();

Expected: one writable primary, healthy secondaries, matching set name, intended hostnames, acceptable lag and enough oplog time coverage. Test majority-acknowledged writes and fresh reads with a disposable business record. Never infer health only from three running OS processes.[13][31]

Drivers need a seed list and replicaSet=rs0; a fixed primary address or directConnection=true bypasses discovery behavior needed for failover. Direct connections are for controlled member diagnostics/maintenance. Read preference chooses an eligible reader; read/write concern governs visibility/acknowledgement. See consistency controls.[30][44]

Elections, majority and rollback

A member needs majority support to become/remain primary. Loss of the voting majority stops normal writable-primary service; that is protection from competing authoritative histories, not an invitation to force each side writable. Elections interrupt writes and can expose ambiguous outcomes to clients.[30]

Event Likely consequence Response
Primary unavailable; majority reachable Eligible secondary elected Driver rediscovers; monitor and retry only safe/driver-supported work
Minority partition No safe majority on that side Restore connectivity; do not force reconfigure to manufacture quorum
Write acknowledged only by old primary May roll back on rejoin Reconcile business state; prefer majority concern for required durability
Majority write timeout Outcome uncertain, not automatically absent Check stable request ID; do not duplicate charges/decrements
Member returns with divergent history Rollback/recovery may occur Preserve rollback/log evidence; review affected application records

A successful majority acknowledgement is tied to the replica-set durability assumptions; it is not a backup against deletion, all-site loss or an administrator forcing unsafe reconfiguration. Avoid mixing priority/votes/delayed members without a reviewed quorum model.[30][31]

Planned failover drill

Use an authorized staging set first; save application error/latency and member-state baselines. Verify another data-bearing member is caught up and eligible. As cluster administrator on the current primary:[30]

rs.stepDown(60);

Reconnect using the set URI. Confirm a new primary, resumed majority writes, application reconnection and no unexplained duplicate business operations. The old primary should remain/return healthy as a secondary. If stepdown refuses because no eligible secondary is ready, fix lag/health rather than force it. If election fails, inspect majority connectivity, TLS/key agreement and member configuration; restoring the failed node/network is safer than force reconfiguration.

A real disaster decision needs a named authority, confirmed surviving data, fencing of obsolete endpoints and an explicit accepted loss window. Do not run rs.initiate() on an existing set to “make a new primary.” Restored replacement sets must remain isolated until the old topology is fenced and clients are cut over exactly once.[22][30]

Replace a failed member and watch oplog headroom

Use the documented member-replacement procedure for the actual failure. A simple secondary replacement preserves the old member’s hostname/port: shut down and fence the old machine, provision a new host with the same identity, keys/TLS and configuration, and an empty dbPath owned by mongod:mongod with the intended persistent SELinux label and mount. Recheck RHEL errata, unit/environment/limits and scoped member firewall rules before starting; let it initial-sync. Never let both old and replacement hosts answer the same member address.[13][92]

When host identity must change, as administrator use rs.conf(), locate the exact member by _id, change only its host, then apply rs.reconfig(cfg) through a healthy primary as documented. Retain the old config; wait for health before any next membership change. Do not combine several voting changes or use forced reconfiguration as a routine replacement shortcut.[33]

// Inspection before selecting the member/change:
const cfg = rs.conf();
printjson(cfg.members);
rs.printReplicationInfo();
rs.printSecondaryReplicationInfo();

Track lag in time and oplog coverage, not just oplog bytes. Bursts can shrink the history window; long initial sync/maintenance needs capacity for the measured write rate. Oplog resizing/retention settings require a version-specific capacity plan, not manual collection/file deletion. If the old host returns after replacement, keep it fenced and resync it deliberately rather than admitting a stale duplicate identity.[31][33]

For horizontal partitioning use sharding, not additional independent primaries holding unsynchronized copies of shop.
