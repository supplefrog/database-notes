System variables

Command pattern Scope and limits
SHOW GLOBAL VARIABLES LIKE 'max_connections'; Global value. SHOW SESSION VARIABLES reports the current session where supported.
SET SESSION variable_name=value; Changes this connection if the variable is session-scoped/dynamic. LOCAL means SESSION, not GLOBAL.
SET GLOBAL variable_name=value; Requires variable-administration privilege; global changes to dual-scope variables usually affect newly created sessions, not existing session copies.
SET PERSIST variable_name=value; Changes the runtime global value and persists it in server-managed mysqld-auto.cnf if supported.
SET PERSIST_ONLY variable_name=value; Persists without changing the runtime value; useful for allowed startup-only settings, with appropriate privilege.
RESET PERSIST variable_name; Removes a persisted entry; does not revert its current runtime value. Restore runtime separately or restart with intended configuration.

Read the variable’s scope, dynamic status, units and privilege requirements before setting it. Do not hand-edit mysqld-auto.cnf as a routine config workflow. Save prior values, change one thing, and verify both runtime and intended restart behavior.

Accounts and authentication

An account is 'user'@'host'; use quoted explicit host identities. mysql.user includes User, Host, plugin, authentication data and static global privileges, but is not the complete representation of roles/dynamic privileges. Do not directly update grant tables or expose authentication strings.

A bounded example uses a random server-generated password instead of embedding a secret. The returned credential must be delivered through a secure channel, not copied into logs or this document:

CREATE USER 'app_reader'@'192.0.2.10' IDENTIFIED BY RANDOM PASSWORD REQUIRE SSL;
ALTER USER 'app_reader'@'192.0.2.10' ACCOUNT LOCK;
ALTER USER 'app_reader'@'192.0.2.10' ACCOUNT UNLOCK;

192.0.2.10 is an example address to replace with the actual trusted application host. Locking prevents new authentication; separately review existing sessions if revoking access urgently.

Roles and grants

CREATE ROLE 'app_read';
GRANT SELECT ON app.* TO 'app_read';
GRANT 'app_read' TO 'app_reader'@'192.0.2.10';
SET DEFAULT ROLE 'app_read' TO 'app_reader'@'192.0.2.10';
SHOW GRANTS FOR 'app_reader'@'192.0.2.10';
Operation Explanation
GRANT 'role1', 'role2' TO 'user_name'@'host'; Grants previously created roles to an account.
SET DEFAULT ROLE ... TO ... Sets default activation, subject to authority over the target account; not the same as granting the role.
SET ROLE NONE; / SET ROLE DEFAULT; Changes active roles in the current session.
SELECT CURRENT_ROLE(); Reports current active roles.
SHOW GRANTS; / SHOW GRANTS FOR CURRENT_USER; Displays grants for the current account. USING can include named granted roles in the displayed effective privileges.
GRANT SELECT(column1, column2), INSERT, UPDATE, DELETE, CREATE, DROP ON app.table_name TO 'user'@'host'; Schematic mixed column/table grant: only SELECT is column-scoped here. Grant only privileges actually required, not this entire list by habit.
GRANT ALL ON app.* TO 'user'@'host' WITH GRANT OPTION; Schema-wide privileges plus delegation; not global administrator authority. High impact: reserve for an approved schema owner, not an app reader.
REVOKE SELECT ON app.table_name FROM 'user'@'host'; Removes that explicit grant; role/schema/global paths can still give access.
DROP USER 'user1'@'host', 'user2'@'host'; Removes accounts; first inventory definers, jobs and connections. Does not drop their application tables.

CREATE USER and GRANT are separate operations in 8.4. They take effect without FLUSH PRIVILEGES.

Login paths

mysql_config_editor set --login-path=maintenance --host=localhost --user=operator --password
mysql_config_editor print --all
mysql --login-path=maintenance
mysql_config_editor remove --login-path=maintenance

The set command prompts for the password. print masks passwords, not a plaintext credentials listing. Login paths are obfuscation, not strong encryption; someone with sufficient local access can recover them. Protect the file/account and prefer a managed secret mechanism where policy requires one. Named --login-path=maintenance is not redundant. Client option precedence and [client] behavior differ from merely saving arbitrary path names.

Authorized root-password recovery

Use the documented Unix init-file method in a scheduled outage with local OS administrator access, console access, backups and an identified account host. Do not use pkill mysql or start another daemon on a live datadir.

  1. Determine the actual unit, executable, option files, datadir and service OS identity. Stop the one intended instance normally and verify it is stopped.
  2. Prepare a temporary file containing the authorized account-change SQL using a securely supplied new secret; only the administrator and required service identity may read it. Keep it out of shell history, backups, generic /tmp, and source control. The file is a secret, not a downloadable example.
  3. Start that instance under its normal OS user/configuration with the documented --init-file override. Under systemd, choose a temporary unit override appropriate to the installed unit rather than bypassing it blindly. Read the error log and confirm the intended account change.
  4. Remove the secret file and temporary startup override, perform a normal controlled restart and verify normal authenticated access. Check that no recovery options remain.

The alternative --skip-grant-tables method disables authorization and normally disables networking. Even then local users are a threat: isolate the host/socket and use the official recovery sequence (FLUSH PRIVILEGES before account-management SQL). Never leave this mode running or treat it as routine account administration. If normal startup fails, preserve the original datadir/configuration and investigate; do not reinitialize.
