Applies to MySQL Server 8.4 LTS; the production baseline is RHEL 9 x86_64 with Oracle MySQL Community RPMs from the MySQL Yum repository. Separately licensed products and other platforms are identified explicitly.[1][72]

Consensus, certification and quorum

Group Replication orders/certifies transactions and manages membership; it is not “every replica synchronously applies every commit.” Remote apply can lag. Choose group_replication_consistency behavior for read-after-write/failover needs; in 8.4 its default is BEFORE_ON_PRIMARY_FAILOVER, not a universal linearizable-read guarantee. Single-primary normally routes writes to one member; multi-primary has additional workload restrictions and certification conflicts.

Use at least three voting members in independent failure domains for tolerating one failure. A two-member group has no majority after losing either member. Three same-host instances are a functional lab, not host-failure HA. When quorum is lost, do not bootstrap another group or force membership until the old writers are fenced and the surviving authoritative history has been established.

Prepare every member

  • Use compatible supported 8.4 versions, InnoDB tables with primary keys or equivalent non-null unique keys, binary logging/ROW format, GTIDs, unique server IDs/UUIDs and the documented Group Replication requirements. Check network latency/bandwidth and clock/DNS operations.
  • Choose three controlled names such as mysql1, mysql2, mysql3; DNS or /etc/hosts must resolve consistently from every member. The source’s two host entries were a name-resolution illustration, not a fault-tolerant topology.
  • Choose one communication stack. MYSQL uses server SQL networking/security; XCOM uses a separate group-communication listener, often example port 33061. That number is a convention, not a requirement. Both distributed recovery and group communication must have their own verified TLS/account/path configuration.
  • Restrict ports to the participating members/application networks as appropriate. Never copy XCOM allowlist/port settings blindly to the MYSQL stack or assume the classic SQL port alone secures recovery.

Configuration field checklist (not a universal complete my.cnf):

Field retained from source Required decision
plugin_load_add=group_replication.so Load compatible Group Replication plugin without replacing other plugin-load entries.
plugin_load_add=mysql_clone.so Optional Clone plugin on relevant members if clone recovery is chosen; cloning can overwrite the joining instance.
group_replication_communication_stack=MYSQL Select the same intended stack throughout the group; connection/authentication and allowed local address rules depend on it.
group_replication_group_name Generate and record a dedicated group UUID, consistent across members and distinct from server UUIDs; do not reuse an unrelated copied example UUID.
group_replication_start_on_boot=OFF Controlled initial provisioning; only enable automatic joining once credentials, recovery and failure behavior are designed/tested.
group_replication_local_address Address/port valid for that stack and that member; must be reachable by peers. MYSQL stack must use an appropriate server listening address/port.
group_replication_group_seeds Reachable peer addresses for joining; include the planned group’s peers, not unrelated SQL endpoints.
group_replication_bootstrap_group=OFF Keep OFF in persistent configuration; bootstrap is a one-member, one-time operation.
group_replication_single_primary_mode ON is the usual starting choice. Multi-primary requires compatible checks/workload.
group_replication_enforce_update_everywhere_checks Enable the documented extra checks for multi-primary mode; not a switch to make conflicting application writes safe.
server_id, gtid_mode, enforce_gtid_consistency Unique server IDs and compatible ON GTID settings, established safely before group operation.

Plan a controlled restart for startup-only settings; verify effective configuration and logs rather than blindly restarting after pasting a block.

Existing-server GTID transition

A fresh lab can be initialized with GTIDs ON. Converting a live topology requires the official coordinated sequence: enable/verify GTID-consistent operations, pass through OFF_PERMISSIVE on all servers, then ON_PERMISSIVE on all, wait for anonymous transactions to finish and replicate everywhere, then move all to ON and persist the intended restart settings. Check Ongoing_anonymous_transaction_count and all channel progress as documented. The source’s two SET PERSIST lines skip prerequisites and are not a safe conversion recipe. Preserve backups/rollback and halt if any member cannot progress.

Distributed recovery and clone

A joiner needs a compatible consistent state and all missing history. Group recovery can transfer transactions incrementally or clone from a suitable donor. Clone replaces the joiner’s existing data and has version/plugin/space/restart prerequisites. Do not lower group_replication_clone_threshold to 1 as a generic fix. Choose/verify donor, back up or explicitly discard the joining instance, check compatibility and then select a documented recovery method. Restore any temporary threshold to its recorded prior value after the operation.

Recovery accounts

Provision the controlled recovery identity on required donor/member endpoints with verified TLS. Restrict host access to the actual members instead of adopting % by default. Choose secure secret delivery and intentionally decide whether account creation is locally provisioned or replicated; SET SQL_LOG_BIN=0 requires authority and must be restored to its prior state in the same session when used.

Privilege from source Why/when
REPLICATION SLAVE Distributed recovery transaction transfer.
CONNECTION_ADMIN Recovery access where the documented read-only/connection restrictions require it.
BACKUP_ADMIN Clone donor backup access when cloning is used, not an arbitrary application grant.
GROUP_REPLICATION_STREAM Required for the documented MYSQL communication-stack secure-connection case.

Use CREATE USER / GRANT rather than editing grant tables; ordinary account statements do not need FLUSH PRIVILEGES. Install credentials using the documented recovery-channel or START GROUP_REPLICATION credential interface with secure handling. Password arguments must not land in history, readable config, logs or copied examples. In-memory startup credentials need a defined restart/automatic-join strategy; merely supplying them once does not prove durable recovery readiness.

Bootstrap exactly once

  1. Start from a deliberate new empty group, or follow the separate complete-outage recovery procedure after proving which member has the authoritative most complete history. Confirm there is no reachable/live old group accepting writes.
  2. On one designated member only, set bootstrap ON, start Group Replication with the approved recovery configuration, then immediately set bootstrap OFF even if startup fails. Never persist bootstrap ON or execute this on all hosts.
  3. Inspect membership/error logs and confirm the intended group UUID/primary/state. Start other members with bootstrap OFF. Check all become ONLINE before admitting application traffic.
  4. Route clients through a topology-aware strategy such as configured Router/connection logic; certification/membership alone does not redirect existing clients or fence an external writer.

Joining member

Before joining, compare server/group identity, GTID sets, data provenance, configuration, table requirements and reachable peers. SHOW BINLOG EVENTS is a log-inspection tool, not proof of a compatible seed. If GTIDs conflict or the joiner has errant transactions, stop and investigate/reconcile or provision a clean joiner through supported backup/clone recovery. Do not run RESET BINARY LOGS AND GTIDS to hide a conflict. Clearing metadata does not undo divergent rows.

Join with bootstrap OFF and the securely provisioned recovery configuration. A failed join needs its actual error diagnosed: credentials/host match, network reachability, TLS issuer/hostname/expiry, plugin/version compatibility, required logs, clone restrictions or conflicting transactions.

Inspect membership and recovery

SELECT * FROM performance_schema.replication_group_members;
SHOW REPLICA STATUS FOR CHANNEL 'group_replication_recovery'\G

The recovery channel is not the normal group applier channel. Inspect Performance Schema applier worker/coordinator status and errors for group_replication_applier as well, plus replication_group_member_stats and server error logs. Verify the elected primary, ONLINE members, backlog/conflicts and client routing. Empty recovery activity after a completed join is not automatically a fault.

Keep three different kinds of keys separate

Credential/key Purpose
SSH host/user keys OS remote-login/file-transfer trust; Group Replication does not exchange SSH keys to authenticate database peers.
TLS certificate/private key/CA Encrypt and authenticate transport. Use per-member private keys; distribute trust anchors, not another member’s private key.
Authentication RSA public key Used by applicable password plugins when not protected by a secure transport; public_key.pem is not an SSL private key/certificate.

If an approved non-TLS authentication path requires group_replication_recovery_public_key_path, verify the donor’s RSA public key through a trusted channel and configure the actual server-readable path as documented. Prefer correctly verified TLS; do not cure TLS failures by blindly copying public_key.pem over SSH. For multiple possible donors, validate the chosen key strategy rather than assuming one donor’s key applies to all.

Change primary mode deliberately

The SQL functions below are real group operations, not per-session settings:

SELECT group_replication_switch_to_multi_primary_mode();
SELECT group_replication_switch_to_single_primary_mode();

These are alternatives, not a sequence to paste. Require a healthy/quorate compatible group, approved privileges, reviewed workload restrictions, routing changes and a maintenance plan. Multi-primary conflicts can abort transactions; applications must handle them. If selecting a particular single primary, use the documented member-UUID argument after identifying that member.

Progress instrumentation, when enabled, can be inspected with:

SELECT event_name, work_completed, work_estimated
FROM performance_schema.events_stages_current
WHERE event_name LIKE '%stage/group_rpl%';

No rows alone does not prove completion. Recheck group primary/mode/member states and application writes. Do not use a mode switch, forced membership or bootstrap as an unexplained recovery shortcut.
