Start with the operation, not the table list

The relational source has customers, orders and order_lines. A literal collection per table is possible, but it does not decide which data should be read/written atomically together. List request predicates, output fields, cardinality, update frequency, consistency requirements and growth before choosing the document boundary.[35]

Operation Frequency / invariant Model consequence
Render one order Read its lines and historical prices together Embed bounded line items in the order
List tenant’s recent orders Tenant equality, descending placement time {tenantId: 1, placedAt: -1} index
Update customer’s current contact details Many orders refer to one customer Reference a separate customer document
Preserve shipping destination at purchase Historical value must not drift Embed address snapshot on order if needed
Reserve stock and create order Both or neither when promised Conditional atomic update plus transaction if spanning documents
Customer’s entire order history Potentially unbounded Query orders by customer; never append forever to customer document

Keep the administration fixture canonical: order IDs o1001–o1003, tenant t1/t2, customer reference, UTC date, Decimal128 total and a bounded lines array. Additional model examples build on it rather than inventing another database.[35][37]

Embed a bounded aggregate; reference independent entities

// Read together and modified as one aggregate:
{
  _id: "o1001", tenantId: "t1", customerId: "c1",
  placedAt: ISODate("2026-09-01T09:00:00Z"),
  status: "new", total: Decimal128("5.00"),
  lines: [{sku: "pencil", qty: Int32(2), unitPrice: Decimal128("2.50")}]
}

The price is an order-time fact, not a pointer to today’s product price. Copying that value is intentional denormalization. Customer current email/name should usually remain on the customer. If historical customer/address facts are legally required, snapshot only the required fields and define retention/deletion obligations.[35]

Embed when Reference when
Bounded one-to-few relationship Unbounded/high-cardinality relationship
Same lifecycle and access pattern Independent updates/lifecycles
Atomic update of the aggregate matters Large or shared entities would duplicate heavily
Extra copied bytes are acceptable Growth approaches document limits or write contention

Arrays must have a growth policy, not merely an initial small size. The fixture validator caps lines at 100 as an application rule. MongoDB’s BSON document limit is 16 MiB; GridFS is an alternative for large binary content, not a reason to put unlimited order history in one customer. Measure BSON size and tail growth, not only averages.[36][37]

const shop = db.getSiblingDB("shop");
shop.orders.aggregate([
  {$project: {_id: 1, bytes: {$bsonSize: "$$ROOT"}, lines: {$size: "$lines"}}},
  {$sort: {bytes: -1}}, {$limit: 10}
]).toArray();

Preserve BSON type meaning

Relational meaning BSON/model choice Trap
Signed BIGINT identity Long("...") or stable string JavaScript Number cannot exactly represent every 64-bit integer
Money DECIMAL Decimal128("5.00") with explicit currency policy Binary floating-point rounding or string sorting
UTC instant BSON Date / ISODate(...) Date has no stored timezone; source local timestamp needs a zone decision
Date-only business value Validated ISO date string or explicitly modeled parts Midnight UTC silently changes local date semantics
Nullable value null when known-empty; missing when absent by design {field: null} also matches missing; choose $exists/type checks deliberately
SQL primary key Stable _id plus tenant/business identity policy Do not regenerate IDs on every import/retry
ENUM/status String plus validator enum Flexible schema does not enforce the enum by itself
Binary/UUID Agreed BSON binary subtype/UUID representation Legacy UUID representations differ across drivers

The shell uses BSON constructors; plain JSON cannot express all these types. Use canonical Extended JSON or a driver-aware loader for interchange. Decimal128, Long, BSON Timestamp and BSON Date are different types; oplog timestamps are not ordinary user dates.[74][87]

Validation and referential integrity

Use the full orders validator to check presence, types, enum and bounded arrays. strict/error rejects invalid writes; it does not retroactively scan/fix existing documents. Before tightening a validator, inspect old shapes, backfill deliberately, test all writers, then enforce. A rollback restores the old validator but does not restore already transformed data.[37][55]

MongoDB has no foreign key ensuring customerId exists or matches tenantId. Create/inspect customers in the disposable dataset:

const shop = db.getSiblingDB("shop");
shop.customers.insertMany([
  {_id: "c1", tenantId: "t1", name: "Mira"},
  {_id: "c2", tenantId: "t1", name: "Dev"},
  {_id: "c3", tenantId: "t2", name: "Asha"}
]);
shop.orders.aggregate([
  {$lookup: {
    from: "customers", let: {cid: "$customerId", tenant: "$tenantId"},
    pipeline: [{$match: {$expr: {$and: [
      {$eq: ["$_id", "$$cid"]}, {$eq: ["$tenantId", "$$tenant"]}
    ]}}}], as: "customer"
  }},
  {$match: {customer: {$size: 0}}},
  {$project: {_id: 1, tenantId: 1, customerId: 1}}
]).toArray();

No results is the expected invariant for this fixture, not measured output. Including the tenant prevents a same-ID/cross-tenant reference from appearing valid. Production referential rules require application/transaction policy plus periodic reconciliation; a nightly orphan report alone does not prevent invalid writes.[35][40]

Index and transaction boundaries

An embedded order update can be atomic without a multi-document transaction. A customer reference plus inventory reservation may require a transaction if the business promises an all-or-nothing change. Keep transactions short, pre-create collections/indexes, and make retries idempotent; see the stock/order transaction.[40]

Use indexes for actual predicates, not every optional field. Arrays produce multikey behavior and larger indexes; an index on lines.sku can help product-based searches but increases write cost. Tenant/date and tenant/customer/order indexes serve different patterns. After sharding, query routing and per-shard indexing remain separate: a fast shard index does not prevent scatter-gather.[20][32][36]

Schema version fields can support rolling application migrations: deploy readers accepting old/new shapes, backfill bounded batches with checkpointed IDs, deploy new writers, verify no old writers remain, then tighten validation. Do not turn off validation globally merely because one bulk import has old data. Keep business transformations reversible where possible and retain pre-transform data under policy.[35][37]

Worked relational transformation

Given source order o1001 for customer c1, and two pencils at exact decimal price 2.50, construct one order document with that line and total 5.00. Copy the source order identity; group child rows by order identity, sort line items deterministically, and preserve quantity/price types. Never compute a migration total with floating-point arithmetic just because the loader is JavaScript.[35][45]

An order snapshot and a current customer document answer different questions. Preserve the relational system as authority until bulk load, delta capture and business reconciliation pass. Translate joins/routines/constraints intentionally in the application; SQL query text is not valid MongoDB query language. Continue with migration and cutover.
