Inspect without changing data

Use the authenticated operator from bootstrap. A database becomes durable when it contains data/objects; use shop only changes shell context. A collection is a set of BSON documents, not a SQL table with implicit column types or foreign keys.[35][37]

use shop
db.getName();
db.getCollectionInfos();
db.orders.getIndexes();
db.orders.find({}, {_id: 1, tenantId: 1, status: 1}).limit(5);
db.orders.countDocuments({tenantId: "t1"});
db.runCommand({collStats: "orders", scale: 1024});
Task Command Interpretation
Database names db.adminCommand({listDatabases: 1, nameOnly: true}) Results/permission depend on account
Collection definition db.getCollectionInfos({name: "orders"}) Type, validator, collation and other options
Index definitions db.orders.getIndexes() Key order, uniqueness, partial/TTL/collation options
View definition db.getCollectionInfos({type: "view"}) Stored pipeline, not materialized data
Exact filtered count countDocuments(filter) Executes work; bound expensive production use
Fast estimate estimatedDocumentCount() Metadata estimate, not migration acceptance

To capture a bounded query, store a reviewed script inspect-orders.js containing the following and run it via mongosh --file. Shell output is not a backup; protect the file because it may contain customer data. relaxed: false requests canonical Extended JSON so BSON types remain represented.[94]

const rows = db.getSiblingDB("shop").orders.find(
  {tenantId: "t1"}, {_id: 1, total: 1, status: 1}
).sort({_id: 1}).limit(20).toArray();
print(EJSON.stringify(rows, null, 2, {relaxed: false}));

umask 077
mongosh --quiet --host 127.0.0.1 --port 27017 --username operator \
  --authenticationDatabase admin --file inspect-orders.js > orders-inspection.json

Use an interactive credential prompt; do not redirect a secret into a URI or script. This loopback command is for the initial authenticated standalone. After enabling requireTLS, use the approved CA and certificate-matching hostname as in TLS connections; for replicas/routers use their topology URI. Do not relax transport settings to keep an old loopback example working.

Create a BSON-aware fixture

Data mutation in a disposable shop database. Stop if orders already exists: inspect it rather than dropping it. The examples share these three orders. Stable string IDs make idempotency and tenant routing explicit; prices use Decimal128, quantities use BSON int, and dates are UTC BSON dates.[35][37][54]

const shop = db.getSiblingDB("shop");
if (shop.getCollectionInfos({name: "orders"}).length) {
  throw new Error("orders already exists: inspect it; do not reset it");
}
shop.createCollection("orders", {
  validator: {$jsonSchema: {
    bsonType: "object",
    required: ["_id", "tenantId", "customerId", "placedAt", "status", "total", "lines"],
    properties: {
      _id: {bsonType: "string"},
      tenantId: {bsonType: "string"},
      customerId: {bsonType: "string"},
      placedAt: {bsonType: "date"},
      status: {enum: ["new", "paid", "cancelled"]},
      total: {bsonType: "decimal", minimum: Decimal128("0")},
      lines: {bsonType: "array", minItems: 1, maxItems: 100,
        items: {bsonType: "object", required: ["sku", "qty", "unitPrice"],
          properties: {
            sku: {bsonType: "string"},
            qty: {bsonType: "int", minimum: 1},
            unitPrice: {bsonType: "decimal", minimum: Decimal128("0")}
          }}}
    }
  }},
  validationLevel: "strict", validationAction: "error"
});
shop.orders.insertMany([
  {_id: "o1001", tenantId: "t1", customerId: "c1",
   placedAt: ISODate("2026-09-01T09:00:00Z"), status: "new", total: Decimal128("5.00"),
   lines: [{sku: "pencil", qty: Int32(2), unitPrice: Decimal128("2.50")}]},
  {_id: "o1002", tenantId: "t1", customerId: "c2",
   placedAt: ISODate("2026-09-02T09:00:00Z"), status: "paid", total: Decimal128("9.00"),
   lines: [{sku: "notebook", qty: Int32(1), unitPrice: Decimal128("9.00")}]},
  {_id: "o1003", tenantId: "t2", customerId: "c3",
   placedAt: ISODate("2026-09-03T09:00:00Z"), status: "new", total: Decimal128("2.50"),
   lines: [{sku: "pencil", qty: Int32(1), unitPrice: Decimal128("2.50")}]}
]);
shop.orders.createIndex({tenantId: 1, placedAt: -1}, {name: "tenant_recent"});
shop.orders.countDocuments({});
shop.orders.find({_id: "o1001"}).toArray();

Acceptance: the three IDs exist once, values retain their BSON types, and tenant_recent exists. A document with total: "5.00" should be rejected by validation; do not weaken the validator to import a string accidentally. Duplicate-key errors on rerun are useful evidence that the stable IDs already exist, not a reason to clear the database. If an ordered insert fails midway, inspect which IDs landed before retrying.[37][54]

CRUD, views and schema changes

const shop = db.getSiblingDB("shop");
shop.orders.find({tenantId: "t1", status: "new"}, {_id: 1, total: 1})
  .sort({placedAt: -1}).limit(10);
shop.orders.updateOne(
  {_id: "o1001", tenantId: "t1", status: "new"},
  {$set: {status: "paid"}}
);
shop.createView("paid_orders", "orders", [
  {$match: {status: "paid"}},
  {$project: {_id: 1, tenantId: 1, total: 1}}
]);
shop.paid_orders.find().limit(10);

updateOne changes only specified fields with $set; replaceOne replaces the document body and can remove omitted fields. Include the tenant and old status to avoid an unintended transition. Ordinary views are read-only pipelines over source data; their underlying indexes determine performance.[80]

Use collMod for validator changes. Inspect and save the entire current validator first; supplying a new validator replaces it, not merges it. For a staged rollout, make old data conform, enable strict/error validation, and test rejected and accepted writes. validationAction: "warn" accepts invalid data and is not a final integrity control.[37][55]

shop.getCollectionInfos({name: "orders"});
shop.runCommand({collMod: "orders", validationLevel: "strict", validationAction: "error"});

MongoDB does not supply SQL foreign keys, SQL stored procedures/triggers, sequences or per-session temporary tables as interchangeable features. Enforce cross-document references and sequencing in application design; change streams are asynchronous notifications, not a synchronous constraint trigger. Do not use server-side JavaScript as a stored-procedure replacement: relevant server-side JavaScript features are deprecated in 8.0.[29][35]

For deletion, preview the exact predicate and count, obtain approval and retain a backup. deleteMany({}), collection drop() and database dropDatabase() are destructive, not “reset settings.” A safer fixture cleanup uses the explicit known IDs only in a disposable database, after confirming no dependent exercise needs them; even that has no automatic undo.[54]

Users, roles and authentication databases

Authenticate as useradmin on admin to administer users. A user created in shop authenticates against shop even when granted privileges elsewhere. The same username in different authentication databases denotes different identities.[99]

use shop
db.createRole({
  role: "orderWriter",
  privileges: [{resource: {db: "shop", collection: "orders"},
    actions: ["find", "insert", "update"]}],
  roles: []
});
db.createUser({user: "shopapp", pwd: passwordPrompt(),
  roles: [{role: "orderWriter", db: "shop"}]});
db.getUser("shopapp", {showPrivileges: true});
db.getRole("orderWriter", {showPrivileges: true});
Identity Authentication DB Privileges
shopapp shop Find/insert/update orders only; no delete, DDL or user management
operator admin Cluster administration plus readWrite/dbAdmin on shop for exercises
monitor admin clusterMonitor; add only required per-DB visibility
backup admin backup; protect broad read access
restore admin restore; additional reviewed privilege needed for oplog replay
useradmin admin User/role administrator; escalation-capable, not app access

Tenant isolation is not enforced by this collection role: the application must constrain tenant predicates, or use a stronger tenancy design. Test denied operations from a fresh shopapp session as well as permitted reads/writes.[18][85]

// useradmin, context shop: credential rotation and role revocation examples
db.changeUserPassword("shopapp", passwordPrompt());
db.revokeRolesFromUser("shopapp", [{role: "orderWriter", db: "shop"}]);
// Restore approved access if revocation was a drill:
db.grantRolesToUser("shopapp", [{role: "orderWriter", db: "shop"}]);

Coordinate password rotation with application connection pools; test a new connection before retiring the previous deployment secret. For incident revocation, restrict network access and invalidate/close affected sessions as part of the response; changing credentials alone is not proof every old operation stopped. Keep a separate emergency administrator, not an undocumented bypass.[17][18]

Operations and sessions

Read-only inspection first; clusterMonitor supplies broad visibility. $currentOp is preferred over deprecated db.currentOp() in 8.0. Match namespace/client/comment and inspect returned operation IDs; do not kill by an example ID copied from notes.[19][51]

const admin = db.getSiblingDB("admin");
admin.aggregate([
  {$currentOp: {allUsers: true, idleConnections: false}},
  {$match: {active: true, ns: "shop.orders", secs_running: {$gte: 5}}},
  {$project: {opid: 1, ns: 1, secs_running: 1, client: 1,
              command: 1, waitingForLock: 1, lsid: 1}}
]).toArray();

Prefer application cancellation and maxTimeMS on bounded reads. db.killOp(observedOpId) asks the server to interrupt a particular operation; it is not a Linux process kill. Run only against the confirmed target, with killop privileges when killing another user’s work. In a sharded cluster use the documented router-aware operation identifier/path; do not strip shard information from an ID.[51][53]

killSessions takes observed session identifiers and can terminate related work/cursors/transactions. It is broader than one operation and distinct from ending your own shell session with endSession(). Prepared transactions are an exception: killSessions ignores their sessions rather than undoing a prepared distributed transaction.[17] Review ownership, topology and privileges first. After cancellation, inspect operations and application outcome; a write already committed is not undone.[17][53]

Runtime settings versus startup configuration

const admin = db.getSiblingDB("admin");
const prior = admin.runCommand({getParameter: 1, logLevel: 1});
if (prior.ok !== 1) throw new Error("could not capture prior logLevel");
printjson(prior); // Also save securely outside this session.
try {
  admin.runCommand({setParameter: 1, logLevel: 1});
  // Capture a short, supervised diagnostic window here.
} finally {
  admin.runCommand({setParameter: 1, logLevel: prior.logLevel});
}
admin.runCommand({getParameter: 1, logLevel: 1});

Use an account authorized for setParameter; restore and verify the observed prior value rather than assuming zero. If the shell disconnects, reconnect and restore the externally saved value. Verbose logging adds overhead and can expose data. setParameter is node-scoped/runtime for supported parameters, not a broadcast to all members and not persistence through restart. Put an approved persistent value in YAML under its documented setting and schedule a restart; daemon-reload does not reload MongoDB YAML.[6][16]
