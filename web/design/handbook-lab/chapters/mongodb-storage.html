Cache, checkpoints and journal

WiredTiger uses an internal cache plus the OS filesystem cache. On-disk compression and cached document representation differ; database size is not a reliable RAM requirement. The documented default cache is the larger of 50% of (RAM - 1 GB) or 0.256 GB. Multiple instances/container limits require an explicit memory budget, not that default multiplied per process.[10]

Mechanism Protects/provides Does not provide
Cache Working data, dirty pages, fast access Durable acknowledgement on its own
Checkpoint Consistent on-disk recovery point, normally every 60 seconds A separate retained backup
Journal Redo of modifications between checkpoints Oplog history or arbitrary PITR
Oplog Replication operations in bounded node-local history Indefinite archive or protection from user deletion
History store Older versions needed for snapshot visibility User-controlled historical restore points

Crash recovery uses a valid checkpoint and journal. Removing journal/history files to free space breaks the storage contract. Find growth in data, indexes, history retention, oplog or logs before acting; retain evidence and restore from a known-good copy if corruption is suspected.[10][31]

// Read-only; clusterMonitor
const s = db.getSiblingDB("admin").serverStatus();
printjson(s.wiredTiger.cache);
printjson(s.connections);
printjson(s.locks);

Use successive samples: dirty bytes, eviction activity and read I/O rising together are more informative than cache occupancy alone. A full cache is normal; sustained application-thread eviction or disk saturation deserves investigation. Long-running snapshots/transactions retain history and can increase pressure. Do not tune an internal WiredTiger option from an unrelated version’s blog post.[10][40]

On the RHEL production host, prefer XFS and verify the actual mounted filesystem, capacity and latency. MongoDB 8.0 has different memory/Transparent Huge Pages guidance from older MongoDB releases: do not inherit a blanket old-version THP-disable script or generic database sysctl profile. Review the 8.0 production notes and coordinate tuning with RHEL tuned, cgroups and the service memory budget; record effective settings after reboot.[62]

Atomicity and concurrency

One document update is atomic, including its embedded fields/arrays. updateMany is not one atomic transaction across all matching documents. WiredTiger provides document-level concurrency with optimistic conflict handling; DDL and metadata operations can still require stronger locks. MVCC snapshots are internal visibility machinery, not a promise that a sequence of unrelated reads shares one snapshot.[10][40][72]

For a bounded stock decrement, include the invariant in the filter. This sample expects the shop.inventory document created below and needs readWrite on shop:

const shop = db.getSiblingDB("shop");
shop.inventory.insertOne({_id: "pencil", available: Int32(20)});
const r = shop.inventory.updateOne(
  {_id: "pencil", available: {$gte: 2}},
  {$inc: {available: -2}},
  {writeConcern: {w: "majority", j: true, wtimeout: 5000}}
);
printjson(r);

matchedCount: 1 is the expected successful branch, not captured output. Zero means missing item or insufficient stock; it is not permission to retry without the stock condition. An acknowledgement timeout does not prove the write failed: reconcile the business request before issuing a non-idempotent decrement again.[75]

Read preference, read concern, write concern

Control Example Meaning / trap
Read preference primary, secondaryPreferred Where a read may run, not its isolation/durability
Read concern local Data visible on that member; can include writes later rolled back
Read concern majority Majority-committed data; not necessarily the newest wall-clock write
Read concern snapshot Point-in-time view where supported; use for cross-document transaction invariants
Write concern {w: 1} Primary acknowledgement, not majority protection
Write concern {w: "majority", j: true} Majority acknowledgement plus requested journal durability
Write timeout wtimeout: 5000 Bounds waiting for acknowledgement; not server-side undo
Causal session causalConsistency: true Orders causally related operations; use majority reads and writes for documented guarantees

Do not infer effective defaults from the word “replica set”; topology and cluster default settings matter. Secondary reads can be stale. For read-your-own-writes across eligible nodes, use one causally consistent session and the documented majority concerns; separate sessions do not automatically exchange causal history.[30][44][75]

const session = db.getMongo().startSession({causalConsistency: true});
try {
  const orders = session.getDatabase("shop").orders;
  orders.updateOne({_id: "o1001"}, {$set: {status: "paid"}},
    {writeConcern: {w: "majority", wtimeout: 5000}});
  printjson(orders.find({_id: "o1001"}).readConcern("majority").toArray());
} finally {
  session.endSession();
}

Use this only after loading the fixture; it mutates order status. Restore the fixture’s business state deliberately, not with an unqualified delete.

A two-collection transaction

Multi-document transactions need a replica set or sharded cluster, not a standalone. Create the target collections/indexes before the example: load the three-order fixture and create inventory using the earlier stock example in this same deployment. Confirm pencil has at least two available units and o2001 is absent; do not reset stock on a rerun. Use the replica-set connection, and grant data privileges on both orders and inventory.[40]

const session = db.getMongo().startSession();
const shop = session.getDatabase("shop");
try {
  session.startTransaction({
    readConcern: {level: "snapshot"},
    writeConcern: {w: "majority", wtimeout: 5000},
    readPreference: "primary"
  });
  const stock = shop.inventory.updateOne(
    {_id: "pencil", available: {$gte: 2}}, {$inc: {available: -2}}
  );
  if (stock.matchedCount !== 1) throw new Error("stock unavailable");
  shop.orders.insertOne({
    _id: "o2001", tenantId: "t1", customerId: "c1",
    placedAt: ISODate("2026-09-01T10:00:00Z"), status: "new",
    total: Decimal128("5.00"),
    lines: [{sku: "pencil", qty: Int32(2), unitPrice: Decimal128("2.50")}]
  });
  session.commitTransaction();
} catch (e) {
  try { session.abortTransaction(); } catch (_) { /* may already be ended */ }
  throw e;
} finally {
  session.endSession();
}

This shell walkthrough illustrates boundaries, not a production retry loop. On TransientTransactionError, retry the whole transaction using the driver’s transaction API; on UnknownTransactionCommitResult, resolve/retry the commit as documented rather than resubmitting arbitrary external side effects. A duplicate o2001 on rerun should abort; do not erase it to make the example appear successful. Keep payment/email calls outside retryable transaction callbacks.[78]

After an unambiguous commit, inspect order and stock in a fresh majority read. After an unambiguous abort, neither mutation should persist. If commit outcome is uncertain, look up the stable order/business request ID before retrying. Transactions add cost and do not make an unbounded document model sensible; prefer one atomic aggregate where the access pattern permits it.[35][40]
