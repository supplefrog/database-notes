Applies to MySQL Server 8.4 LTS; the production baseline is RHEL 9 x86_64 with Oracle MySQL Community RPMs from the MySQL Yum repository. Separately licensed products and other platforms are identified explicitly.[1][72]

TLS and encryption solve different problems

TLS protects connections; InnoDB encryption protects selected stored data when the corresponding keys are available. Neither replaces least privilege, host security, patching, backups or audit/restore tests. Server, replication, administrative and client connections may use different TLS settings.

  • TLS certificate and transport procedure: trust/hostname verification, separate key permissions, planned rotation and rollback. The old SSL.sh is retained there only as historical text, with the world-readable-key bug explained.
  • Keyring and encryption procedure: component availability, early loading, key custody, explicitly enabled data/log encryption and restore testing. The old TDE.sh only attempted to load an Enterprise encrypted-file keyring; it did not implement complete TDE.

For 8.4 Community, evaluate component_keyring_file with its documented threat model; the encrypted-file keyring component is Enterprise. Local file keyrings are not, by themselves, a regulatory-compliance key-management solution. Backup keys separately and verify recovery on an isolated server before claiming data is recoverable.

SSL.sh

Historical source example for reading, not a tested procedure or executable download.

Applies to MySQL Server 8.4 LTS; the production baseline is RHEL 9 x86_64 with Oracle MySQL Community RPMs from the MySQL Yum repository. Separately licensed products and other platforms are identified explicitly.[1][72]

Replace the old script with a controlled TLS deployment

Target: MySQL 8.4 LTS on the selected EL9 RPM platform; use the distribution’s supported OpenSSL build and your organization’s CA/PKI workflow. The OpenSSL 3.x reference explains request/SAN syntax, but no versionless certificate-generation script is recommended. The historical source is reproduced below as text only; do not execute it.

Prerequisites and certificate identities

Inventory every endpoint/client (classic, X Protocol, admin interface and replication separately), DNS names/IPs actually used, current account TLS requirements, CA trust, protocol/cipher policy and expiry/rotation policy. Back up current config/certificates securely, keep an authenticated administrative connection and console/rollback access, and rehearse on an isolated instance.

Have the CA issue the server certificate for its real identity with appropriate DNS/IP subjectAltName entries and key usage. A certificate for an IP will not automatically verify an unrelated DNS hostname. Modern CA policy, not the source’s fixed ten-year validity or empty APP_NAME/IP, determines lifetime. The CA private key belongs in protected CA custody, not the MySQL datadir. Generate/store server and optional client private keys separately; do not deploy every .pem produced in a working directory.

Validate chain, identity, expiry and certificate/key match using the CA’s tooling and the selected OpenSSL documentation before modifying the server. For REQUIRE X509 or subject/issuer-constrained accounts, each client additionally needs its own suitable certificate and private key. REQUIRE SSL alone requires encrypted transport, not necessarily a client certificate.

File permissions: the concrete security fix

After installing explicitly selected files into the approved server-readable directory, set permissions by role:

File Example EL9 ownership/mode Custody
server-key.pem mysql:mysql, 0600 (or a narrowly scoped equivalent needed by the service) Server private key; never world-readable.
server-cert.pem root-owned, 0644 with service read access Public certificate; integrity still matters.
ca.pem root-owned, 0644 with service read access Public trust chain, not the CA signing key.
Client private key Owned by the specific client OS identity, 0600 On the client host; not shared among replicas by default.
CA private key Not installed on the DB server Protected CA system/backup with separate access control.

Ensure parent directories and SELinux labels permit the intended reads. Use exact paths, not chmod 644 *.pem: that wildcard overwrites restrictive key modes and was the source’s blocking defect. Check ACLs as well as numeric mode. If that script was ever used operationally, treat exposed private keys as potentially compromised and plan revocation/reissue rather than merely changing mode afterward.

Server/client configuration

Edit the correct existing [mysqld] group in a reviewed option-file copy. [server] is also a server-read group, but the old script only searched for that heading and missed the supplied file’s [mysqld]. Do not delete every matching TLS line across all groups or duplicate contradictory settings.

[mysqld]
ssl_ca=/var/lib/mysql/tls/ca.pem
ssl_cert=/var/lib/mysql/tls/server-cert.pem
ssl_key=/var/lib/mysql/tls/server-key.pem
require_secure_transport=ON

These are example approved file locations to provision/label first. Check permitted local transports and all legacy clients before enforcing require_secure_transport. This setting by itself does not force every client to authenticate the server identity. Do not pin one TLS 1.3 ciphersuite from a copied script without validating client compatibility and organizational policy; TLS 1.2/1.3 cipher settings differ.

A classic-protocol client verification example, with actual host/account/CA inputs:

mysql --host=db.example.com --user=operator --password \
  --ssl-mode=VERIFY_IDENTITY --ssl-ca=/etc/mysql/trust/ca.pem

Within that session, inspect SHOW SESSION STATUS LIKE 'Ssl_cipher'; and Ssl_version; empty cipher indicates no TLS for that session. A cipher alone does not prove hostname verification: deliberately test that an untrusted CA/wrong hostname is rejected in a controlled test. Inspect server startup/TLS diagnostics and account requirements, and test application plus replication clients before accepting the change.

Deploy, rotate and roll back

Place validated cert/key files in their final paths before a restart/reload. Avoid stopping first then using mv *.pem from an arbitrary current directory. Use a deliberate maintenance restart for initial setup; for rotation, the documented ALTER INSTANCE RELOAD TLS interface can update supported server TLS contexts without restarting, with version/channel behavior checked first. Existing connections may retain their old TLS sessions; test new connections.

Retain previous usable certificate/configuration until validation is complete, subject to revocation/security rules. On failure, restore only the known prior files/settings and reload/restart the intended context; do not disable verification globally or expose plaintext just to get an application online. Rotate client trust in a staged overlap window where needed, monitor expiry and test backup/recovery of required keys. Never keep an exposed/revoked key solely as a convenient rollback.

RHEL placement and SELinux verification

The server example uses /var/lib/mysql/tls, inside the standard data tree, so its server-read files can use the existing mysqld_db_t data-tree policy instead of leaving a novel /etc/mysql/tls path unprovisioned. Provision it as a restricted directory (for example root-owned, group mysql, mode 0750); deploy only the selected server key, server certificate and public CA chain with the file-specific permissions above. Apply restorecon -Rv /var/lib/mysql/tls and inspect ls -ldZ / ls -lZ before starting. Confirm effective policy on this installed RHEL system; for a relocated datadir use its equivalence mapping and update the TLS paths deliberately.

Replication-side SOURCE_SSL_CA, SOURCE_SSL_CERT and SOURCE_SSL_KEY are read by mysqld on the replica; provision and label them there too. Ordinary client’s --ssl-ca is read by the client OS identity and is a separate path/access contract. The CA private key is never copied into either directory. Do not solve a certificate/key read denial by giving all users read permission. Keep a backup exclusion/inclusion inventory: a physical datadir copy may now include these private keys, so encrypt/restrict that backup and retain controlled recovery access.

Historical source — do not deploy

The following is the complete sanitized original, preserved for comparison. Its exact defects and replacement decisions are explained above. This text is not a supported executable/configuration recipe.

#!/bin/bash
set -euo pipefail

APP_NAME=""
IP=""
DAYS=3650

DATA_DIR="/data/mysql"
MYCNF="/etc/my.cnf"

# =====================
# Generate certificates
# =====================
{
openssl genrsa -out ca-key.pem 2048
openssl req -new -x509 -nodes -key ca-key.pem -out ca.pem -subj "/CN=MySQL_${APP_NAME}_CA" -sha256 -days ${DAYS}

openssl genrsa -out server-key.pem 2048
openssl req -new -key server-key.pem -out server.csr -subj "/CN=${IP}"
echo "subjectAltName=IP:${IP}" > san.cnf
openssl x509 -req -in server.csr -CA ca.pem -CAkey ca-key.pem -CAcreateserial -out server-cert.pem -extfile san.cnf -sha256 -days ${DAYS}

openssl genrsa -out client-key.pem 2048
openssl req -new -key client-key.pem -out client.csr -subj "/CN=replica-client"
openssl x509 -req -in client.csr -CA ca.pem -CAkey ca-key.pem -CAcreateserial -out client-cert.pem -sha256 -days ${DAYS}

chown mysql:mysql *.pem
chmod 600 *-key.pem
chmod 644 *.pem
}

# =====================
# Edit my.cnf
# =====================
{
CA="${DATA_DIR}/ca.pem"
CERT="${DATA_DIR}/server-cert.pem"
KEY="${DATA_DIR}/server-key.pem"

# Remove ALL cert-related or TLS-related lines anywhere
sed -i '/ssl-ca=\|ssl-cert=\|ssl-key=\|tls_ciphersuites=\|require_secure_transport/d' "${MYCNF}"

# Append ordered block under [client] if it exists
if grep -q '^\[client\]' "${MYCNF}"; then
  sed -i "/^\[client\]/a ssl-ca=${CA}\n" "${MYCNF}"
fi

# Append ordered block under [server] if it exists
if grep -q '^\[server\]' "${MYCNF}"; then
  sed -i "/^\[server\]/a ssl-ca=${CA}\nssl-cert=${CERT}\nssl-key=${KEY}\ntls_ciphersuites=TLS_AES_256_GCM_SHA384\n#require_secure_transport\n" "${MYCNF}"
fi
}

systemctl stop mysqld
mv *.pem $DATA_DIR
systemctl start mysqld

TDE.sh

Historical source example for reading, not a tested procedure or executable download.

Applies to MySQL Server 8.4 LTS; the production baseline is RHEL 9 x86_64 with Oracle MySQL Community RPMs from the MySQL Yum repository. Separately licensed products and other platforms are identified explicitly.[1][72]

A keyring is not complete transparent data encryption

Target: MySQL 8.4 LTS. The source names component_keyring_encrypted_file, an Enterprise Edition component, not a universally available Community plugin. Community has component_keyring_file; external key-management implementations have separate platform/edition/service dependencies. Both local file-based components have limited threat models and are not stand-alone regulatory-compliance solutions.

Do not run the historical script below. It stops a service, overwrites hardcoded files, embeds a configuration password and omits key recovery, permissions and encryption enablement. No literal credential survives in the preserved snapshot.

Select and establish the keyring

  1. Inventory existing encrypted tablespaces/logs and the already active keyring. Never replace/reinitialize a keyring that holds keys needed by existing data. Confirm edition, selected component library, exact server/plugin paths and backup-tool compatibility.
  2. Read the component’s version-specific manifest/configuration rules. A global mysqld.my belongs alongside the actual mysqld executable; local manifests may be read from the instance datadir when enabled. The source’s /sbin/mysqld.my and /lib64/mysql/plugin/... are not portable paths. Components needed to open encrypted InnoDB data must load early through the documented manifest mechanism, not a late generic plugin recipe.
  3. Preserve existing manifest entries rather than overwriting the file. Determine whether global versus local component configuration is appropriate for multiple instances. Each instance needs independent custody/access to the intended key store, not an accidental shared keyring path.
  4. For the encrypted-file component, provision path, the configuration password, and read_only as documented. Supply the secret through a controlled secret-management/deployment process; it is not safe simply because it sits inside JSON. Restrict the config and keyring files/directories to required OS identities, apply ownership/SELinux policy and ensure the keyring path is not publicly readable or casually backed up with its unlocking secret beside it.
  5. Start/restart only in a maintenance window after a tested rollback/backup plan. Inspect server errors and performance_schema.keyring_component_status; verify the selected component/path/status. A returned status row proves neither that all tables are encrypted nor that backup recovery works.

Explicitly enable and verify each encryption scope

Scope Action/check
New InnoDB file-per-table/general tablespaces Review supported ENCRYPTION='Y' DDL and default_table_encryption / privilege controls. Defaults govern creation and do not retroactively encrypt every old table.
Existing tables For a compatible file-per-table table, ALTER TABLE app.table_name ENCRYPTION='Y'; is a deliberate storage operation with time/space/lock implications. Shared/general tablespace encryption is changed at its appropriate tablespace scope, not with an arbitrary per-table operation. Back up and rehearse first.
mysql system tablespace Separate supported system-tablespace encryption control/DDL; not covered merely by setting an application schema default.
Redo / undo Review and explicitly enable innodb_redo_log_encrypt / innodb_undo_log_encrypt where required, with recovery/keyring prerequisites. Observe transition behavior; do not infer all preexisting bytes change instantly.
Binary / relay logs binlog_encryption is a separate feature. Retain keys and use the supported server-mediated reading/recovery path for encrypted logs.
Temporary storage, general/slow/error/audit logs, exports Not automatically protected by the above table settings. Evaluate each documented coverage boundary and disk/log/backup encryption separately.
Backups Database encryption and backup-image encryption differ. Confirm the backup product can capture/restore encrypted tables and key material for this exact component/version.

Inspect the relevant Information Schema InnoDB tablespace encryption metadata and actual configuration after each change. Test reads/writes and restart. Do not declare “TDE complete” because only the component was loaded or a default changed.

Key lifecycle, restore and rollback

Back up the data and every key/keyring state needed by that backup under separate access controls, including component configuration and the securely recoverable unlocking secret. Document who can recover them during a host/CA/KMS outage; encrypt/protect backups off-host and retain key history as long as dependent data/log backups exist.

ALTER INSTANCE ROTATE INNODB MASTER KEY rotates the InnoDB master key under its documented privileges and prerequisites; it is not a rotation of every unrelated log/audit/backup encryption key. Test rotation, keyring backup update, restart and reading older retained backups. Do not delete an old key because a new key was created.

The acceptance test is an isolated restore to compatible binaries/component configuration using only the retained backup and recovery key material: start, read encrypted objects, validate application data and replay the required logs. Also test the expected controlled failure when keys are unavailable, without damaging the only copies.

Rollback is not unloading/removing the keyring while data still needs it. Keep the working component/keyring available; reverse a failed configuration deployment only to a configuration that can still read the required keys. If changing encryption policy, use supported decrypt/reencrypt/migration steps with backups and revalidation. Lose the necessary keys and the encrypted data may be unrecoverable.

Community file keyring on the selected RHEL host

For a new, single instance with no existing keyring or encrypted data, Community’s component_keyring_file is a concrete alternative to the historical Enterprise-only encrypted-file script. First inspect @@plugin_dir, the actual RPM mysqld executable path and all existing manifests. Only one keyring implementation may be enabled; changing one for existing encrypted data requires a supported key migration, not the following new-instance setup.

For the selected /usr/sbin/mysqld, the global manifest is /usr/sbin/mysqld.my:

{"components":"file://component_keyring_file"}

Place component_keyring_file.cnf beside its actual component library in the queried plugin directory, not an assumed /lib64 path:

{"path":"/var/lib/mysql-keyring/component_keyring_file.keys","read_only":false}

The keyring data path must not point into the MySQL datadir. Provision the approved /var/lib/mysql-keyring independently of /var/lib/mysql, owned by the service identity with mode 0700 and no unnecessary ACL access. Keep manifest/configuration root-controlled and server-readable but not server-writable (for example root:mysql 0640, with traversable parent directories); restrict key data to the required service identity. The component’s local key file is not encrypted merely because its filename contains “keyring”.

Inspect the installed policy and expected labels first. For this mutable MySQL-owned key data directory, a reviewed mysqld_db_t file-context mapping plus restorecon is the data-access policy pattern; do not label the manifest, component library and all configuration as writable database data. Verify actual process/file contexts and any AVC during the controlled restart. If policy denies access, diagnose the specific path/type/permission rather than widening all file modes or disabling enforcement.

With multiple instances sharing the executable/plugin directory, do not deploy the preceding global-only key-path configuration: it would make them share one key file. Use the documented global read_local_manifest:true and read_local_config:true routing, place each local manifest/configuration in its corresponding datadir, and select a distinct external key-store path per instance. Provision and test every instance affected by the shared global files before restarting any of them. Retain the original working files for rollback.

After the planned restart, inspect SELECT * FROM performance_schema.keyring_component_status;, error logs and the actual key-store permissions/labels; Active means component initialization, not encrypted tables or recoverable backups. Explicitly enable only the intended encryption scopes described above. A backup of the datadir alone omits this external key directory: include its version-consistent key material, manifests/configuration and recovery access in a separately protected backup set and prove an isolated encrypted-data restore before relying on the configuration.
