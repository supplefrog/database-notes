Applies to MySQL Server 8.4 LTS; the production baseline is RHEL 9 x86_64 with Oracle MySQL Community RPMs from the MySQL Yum repository. Separately licensed products and other platforms are identified explicitly.[1][72]

Upgrade the exact source/target pair

Target: MySQL Server 8.4 LTS. Record the full source patch, distribution, architecture, OS, plugins, client drivers, replication topology and desired 8.4 target patch. A table that says 8.0.x → 8.4 or 8.4 → 9.x is not a support matrix. Use the official upgrade-path table and the selected release notes/prerequisites before choosing packages.

Source-era path from the old notes Correct disposition
Older than 5.7 → 5.7 Historical intermediate migration, not an 8.4 direct in-place path. Plan supported intermediate steps or reviewed logical transformation for the actual source.
5.7 → 8.0.15 Historical pre-auto-upgrade behavior used mysql_upgrade; it is not a recommendation to deploy that old patch now.
5.7 → 8.0.16+ 8.0.16 introduced server-performed upgrade tasks. Reach a source version eligible for the next hop; do not jump 5.7 directly to 8.4.
8.0 → 8.4 LTS Supported adjacent-series class (the manual gives 8.0.37 → 8.4.x as an example), subject to exact versions, removed features, readiness checks and release notes. Update to an eligible maintained source patch first where required.
8.4 → a later Innovation/LTS Outside this deployment target. Only follow a specifically documented supported path; “all 9.x” is false. A required LTS cannot be skipped.
Within 8.4 LTS maintenance update; still review release notes, plugin/tool compatibility and rollback support for the exact pair.

Rehearsal and checker

  1. Back up all data, binlogs, key material, effective configuration, grants/routines and package inventory. Rehearse restoring them to an isolated old-version instance; merely saving old packages does not undo a dictionary upgrade.
  2. Use a MySQL Shell build whose checker understands the chosen target, and supply the exact targetVersion. The 8.4 API supports this option; omitting it checks against the Shell release, which may not be the intended target. configPath can include checks of a local copy of the source option file. The checker’s documented account needs RELOAD, PROCESS and SELECT; use temporary controlled access, not a permanently privileged application account.
  3. Connect without an embedded password and call util.checkForServerUpgrade(connectionData, {targetVersion: approvedTargetVersion, configPath: sourceConfigPath}) in Shell JavaScript. Those names represent explicitly supplied values. Save the report; resolve errors and understand warnings. Passing the checker is necessary evidence, not an application/replication/backup test.
  4. Rehearse the exact package/binary upgrade and restart on the restored copy. Check changed authentication defaults, removed variables/plugins, charset/collation, SQL behavior, optimizer changes and app drivers. Rehearse topology sequencing, including replicas and Router where used.
  5. During the approved production window, stop writes as required, take the final consistent backup/boundary, apply only the reviewed packages from the intended 8.4 channel, and start with monitored logs. Do not use a blanket yum localupdate over an arbitrary directory.
  6. Validate server version, tables/routines/accounts, application results, performance, backups and all replicas before cutover is accepted.

Server upgrade mode

mysqld --upgrade= Meaning
AUTO Default: performs dictionary/server upgrade steps as needed.
MINIMAL Limits upgrade to required dictionary, Performance Schema and INFORMATION_SCHEMA work; skips other server-upgrade work. Not proof that user/system objects have passed all checks.
FORCE Forces server-upgrade checks/work even when normally considered current; not a magic repair for arbitrary corruption.
NONE Suppresses upgrade work; startup fails if a required dictionary upgrade is needed. Not a way to run new binaries against an incompatible old dictionary.

Rollback is a restore/cutover decision

Do not start old binaries on a newly upgraded datadir unless the exact downgrade is expressly supported. The 8.4 LTS policy permits some within-series in-place downgrades; cross-series and feature-specific restrictions are separate. Safest rehearsed fallback is the untouched old instance/backup plus a plan for writes accepted after cutover. A logical export may require unsupported-feature/type/SQL transformations and is not universally loadable into an older version. Test rollback and its data-loss window before upgrading.

RHEL package and topology boundary

Use the same Oracle repository origin, selected 8.4 channel and approved package transaction; inventory server, client, Shell, Router, backup tool, plugins and SELinux policy compatibility. A Red Hat AppStream module-switch command is not this upgrade method. Review every active mysqld@... unit as well as mysqld.service: package replacement changes their shared binaries, so plan all affected instances even when they have separate datadirs. Back up drop-ins, /etc/my.cnf includes and /etc/sysconfig/mysql; compare RPM configuration artifacts rather than overwriting working local settings.

For a supported asynchronous rolling upgrade, upgrade/test replicas before the writer where the exact-version replication matrix allows old-source to new-replica traffic. Stop if any required channel, plugin or client version is unsupported; new-source to old-replica traffic must not be assumed. For Group Replication, use its exact mixed-version/primary restrictions and preserve quorum while upgrading one member at a time. Do not bootstrap during an ordinary rolling update. Keep a separately restored old-version fallback, and record the point after which new writes make it stale. These are topology acceptance gates, not a universal execution sequence for unspecified source/target versions.
