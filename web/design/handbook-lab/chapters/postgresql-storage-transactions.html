Map the cluster before touching files

A PostgreSQL cluster is one initialized data directory served by one server instance, containing multiple databases. It does not by itself mean an HA group. Roles and tablespaces are cluster-wide; a schema is a namespace inside a database. Unlike MySQL’s common usage, database and schema are not synonyms.[6][21][22]

For the RHEL/PGDG target, main config, HBA and data are together under PGDATA unless explicitly relocated. The service takes PGDATA from its systemd environment. Do not invent a separate distribution cluster registry or external config tree.[6][100]

/usr/pgsql-18/bin/                  versioned server and client executables
/usr/pgsql-18/lib/                  major-specific extension libraries
/usr/pgsql-18/share/extension/      extension control/SQL files
/usr/lib/systemd/system/postgresql-18.service   vendor unit (do not edit)
/etc/systemd/system/postgresql-18.service.d/    local drop-ins
/var/lib/pgsql/18/data/             default PGDATA
    postgresql.conf                main settings / reviewed includes
    pg_hba.conf                    ordered connection authentication
    pg_ident.conf                  OS/certificate-to-role maps
    postgresql.auto.conf           ALTER SYSTEM overrides
    PG_VERSION                     major, not full minor
    base/<database-OID>/            per-database relation files
    global/                        cluster-wide catalogs/control
    pg_wal/                        write-ahead log, not disposable logs
    pg_xact/                       transaction status
    pg_multixact/                  shared row-lock state
    pg_tblspc/                     links to external tablespaces
    log/                           collector output (configured here)
/run/postgresql/                   explicit socket directory; tmpfiles-managed

Use the server’s answers as authority, not a remembered package path:

SHOW data_directory;
SHOW config_file;
SHOW hba_file;
SHOW ident_file;
SELECT system_identifier FROM pg_control_system();
SELECT oid, datname FROM pg_database ORDER BY datname;
SELECT pg_relation_filepath('pg_catalog.pg_class');

Control information and some paths require elevated privileges. Record system identifier, major version, host, port and tablespace map with every physical backup. A relation OID is not necessarily its current filenode; rewrites and reindexing can change files without changing the SQL object’s identity. Never repair a table by renaming files or editing catalogs.[6][23]

Durable writes and crash recovery

A dirty page in shared buffers is not yet a durable data-file write. WAL records describing the change must reach durable storage before the corresponding changed data page. With normal synchronous commit, the commit waits for local WAL flush; the checkpointer later establishes a redo starting point so crash recovery need not scan all historical WAL.[7][34]

Component/setting Purpose Operational consequence
shared_buffers Shared database page cache Startup setting; leave memory for OS cache, sessions and maintenance.[63]
wal_buffers In-memory staging for WAL Not retained backup history.
fsync = on Request durable writes Turning it off risks unrecoverable corruption after OS/power failure.[34]
full_page_writes = on Protect against torn page writes during recovery Keep on; also a rewind prerequisite.[34][44]
synchronous_commit = on Wait for commit durability at configured level off can lose acknowledged recent transactions after crash, even without corruption; not an optimization to apply blindly.[34]
checkpoint_timeout, max_wal_size Time/volume pressure for checkpoints More frequent checkpoints increase write load; max_wal_size is a soft limit, not a disk-space cap.[34]
WAL archive / replication slot Retain changes for recovery or consumers Failures can fill disk independently of checkpoint limits.[33][39]

Crash recovery replays WAL automatically on restart. It does not repair deleted files, restore a dropped table or reverse valid but unwanted transactions. Those require backups and PITR. Leave pg_wal under server control; deleting files there to make room can destroy the recovery path.

Heap, indexes and visibility

Ordinary tables use heap storage; their primary-key index is a separate structure, not an InnoDB-style clustered row store. An index entry leads to a heap tuple whose visibility must normally be checked. The visibility map allows an index-only scan to avoid some heap visits; having all selected columns in an index alone does not promise zero heap fetches.[6][10][76]

Structure Use Cost/limit
Heap relation Row versions, pages with free space Updates/deletes leave old versions until safe cleanup.
B-tree Equality, range and ordered access Extra writes/WAL/storage; column order and selectivity matter.
GIN Inverted access for suitable array, JSONB and text-search operators Write/maintenance cost; requires matching operators/classes.
BRIN Summaries of ranges of physical pages Useful for correlated large data; lossy checks may visit many rows.
TOAST Out-of-line/compressed large values Include TOAST in size/maintenance investigations.
Free-space / visibility map Reusable page space / visibility information Maintained by normal operations and vacuum, not hand-edited.

Index methods and operator classes are choices for measured access patterns, not interchangeable speed switches.[28][75]

SELECT pg_size_pretty(pg_table_size('notes.orders')) AS table_with_toast,
       pg_size_pretty(pg_indexes_size('notes.orders')) AS indexes,
       pg_size_pretty(pg_total_relation_size('notes.orders')) AS total;

This inspection assumes the adminlab fixture. Growth is not proof of bloat: compare live row counts, row widths and workload before proposing a rewrite.

Transactions, snapshots and locks

MVCC lets readers use snapshots while writers create new row versions. It does not eliminate locks. Updates to the same row serialize; DDL can block readers and writers. Keep transactions short, acquire locks in a consistent order and retry the whole transaction after deadlock or serialization failure—not just the last statement.[8][9]

Isolation Snapshot behavior Application obligation
Read Committed (default) New snapshot for each statement Recheck assumptions across statements; an earlier read is not a reservation.
Repeatable Read Stable transaction snapshot Concurrent update conflicts can abort; retry from the beginning.
Serializable Detects anomalies inconsistent with serial execution Handle SQLSTATE 40001 and bounded retry with backoff.
Read Uncommitted Behaves as Read Committed in PostgreSQL No dirty-read mode.[8]

Example: reserve a known row while changing it. Run only against the fixture, and replace the proposed update with the real business invariant before production use.

BEGIN;
SET LOCAL lock_timeout = '2s';
SET LOCAL statement_timeout = '10s';
SELECT order_id, status FROM notes.orders WHERE order_id = 1 FOR UPDATE;
UPDATE notes.orders SET status = 'paid'
WHERE order_id = 1 AND status = 'new';
COMMIT;

A zero-row update can mean the row already changed; it is not automatically success. A lock timeout aborts the statement and leaves this transaction needing ROLLBACK. ROLLBACK undoes transactional row changes, but sequence allocations are not gapless and are not rolled back.[60] Do not hold the lock while waiting for a user or remote API.

A two-session lock investigation is explicit: session A opens a transaction and locks the row; session B attempts the update with the short timeout; inspect pg_blocking_pids() before rolling back A. Do not reproduce this on an unknown production row. Use wait diagnostics, not random process termination.

Temporary objects and external storage

CREATE TEMP TABLE creates a session-local object; ON COMMIT DROP makes its lifecycle transaction-local. Autovacuum cannot maintain another session’s temporary table, so analyze it after a substantial load if subsequent plans depend on its distribution. Unlogged tables are different: persistent objects whose contents are not crash-safe or physically replicated; they are not a substitute for durable application tables.[10][70]

Run this example as the database owner or administrator. The fixture intentionally revokes public database privileges and grants notes_app no TEMPORARY privilege; do not widen runtime permissions just to run this maintenance example.[19]

BEGIN;
CREATE TEMP TABLE order_batch (order_id bigint PRIMARY KEY) ON COMMIT DROP;
INSERT INTO order_batch VALUES (1), (2);
ANALYZE order_batch;
SELECT o.* FROM notes.orders AS o JOIN order_batch USING (order_id);
COMMIT;

A tablespace assigns objects to an existing empty, persistent directory owned by the PostgreSQL OS account. On RHEL, mount it persistently, add RequiresMountsFor=/srv/postgresql/fastspace to the owning unit, and check parent traversal. Before SQL creation, inspect existing local labels, then use sudo semanage fcontext -a -t postgresql_db_t '/srv/postgresql/fastspace(/.*)?' and sudo restorecon -Rv /srv/postgresql/fastspace; verify ownership/mode 0700 and matchpathcon -V. Do not replace an existing conflicting mapping blindly or disable enforcing mode.[102][104] Creating one requires superuser; using it requires CREATE on that tablespace. It is part of the same cluster, not an independent backup or portable collection of tables.[22]

-- Prerequisite: /srv/postgresql/fastspace exists, empty, owned by postgres.
CREATE TABLESPACE fastspace LOCATION '/srv/postgresql/fastspace';
GRANT CREATE ON TABLESPACE fastspace TO notes_owner;
SELECT spcname, pg_tablespace_location(oid) FROM pg_tablespace;

Moving notes.orders with ALTER TABLE notes.orders SET TABLESPACE fastspace takes a strong lock, consumes copy space and does not move its separate indexes automatically.[71] Schedule and verify every object; reverse the move to the original tablespace if needed. Drop a tablespace only once all databases’ objects have been moved out. A missing mount can make the entire cluster unusable. Base-backup/restore plans must include every tablespace, and same-host drills must remap them rather than reuse live paths.[22][32]
