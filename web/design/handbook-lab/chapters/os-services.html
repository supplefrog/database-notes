Systemd service types

Type= describes the startup protocol, not a guarantee that an application is healthy. These five types are relevant to RHEL 9; the upstream systemd 252 manual provides the reference semantics. Consult the installed man systemd.service for the exact packaged version and backports.[12]

Type When startup is considered complete Main point
simple After systemd forks the service process, before successful executable invocation is confirmed Run the main service in the foreground; follow-up jobs can begin before the executable is ready
exec After successful execution of the service binary (execve) Detects invocation failures such as a missing executable; it does not wait for application readiness
notify After a valid READY=1 notification The program must implement the notification protocol; setting this type alone cannot add readiness support
forking After the original process exits as part of daemonization Intended for traditional forking daemons. Use a reliable PIDFile= where appropriate; identifying the main process by guessing can be unreliable
oneshot After the start command(s) finish successfully Suitable for finite setup work. With RemainAfterExit=yes, systemd can regard the unit as active after the commands exit; otherwise it normally becomes inactive

Service processes are tracked as a group; do not reduce systemd tracking to “the orphan happened to be adopted by PID 1.” Choose the type matching the program’s actual behavior. After= expresses ordering, while requirement dependencies such as Requires= have different semantics.[99] An exec service that has started can still fail during its own initialization.[12]

For boot targets, see init system; for resource policy, see limits and cgroups.

RHEL service changes: inspect, override, verify

RHEL’s packaged unit and its vendor-defined OS identity are the starting point. A familiar unit name does not establish package origin or prove that another distributor’s helper script exists. Use read-only inspection on the actual host; sshd.service below is an inspection example, not an instruction to restart remote access:

systemctl cat sshd.service
systemctl show sshd.service -p FragmentPath -p DropInPaths -p User -p Group
systemctl status sshd.service
journalctl -u sshd.service -b

systemctl cat shows the unit and drop-ins; show exposes manager properties, while the journal records startup/runtime messages. An empty User= for a system service does not mean no OS identity: the service may begin with the manager’s default root identity and drop privileges internally.[48][55]

For a separately approved service change, preserve the installed configuration and existing drop-ins, then use systemctl edit UNIT (replace UNIT) for a narrow override in /etc/systemd/system/. Do not overwrite /usr/lib/systemd/system/ or shadow the complete vendor unit merely to change one limit. Use the installed systemd-analyze verify on the actual unit path; after editing, systemctl daemon-reload reloads unit definitions, not the application’s own configuration. Plan a service reload/restart only when that service supports the required operation and its maintenance/recovery conditions are met.[48][99]

For a service depending on a custom data mount, a [Unit] drop-in can use RequiresMountsFor=/srv/service-data for the approved actual path. This adds mount requirements/ordering, not a test that the correct volume, files or encryption keys are present. Check mount identity and service data before start. After=network-online.target is also not a guarantee that a remote database or DNS endpoint is healthy.[99]

After the planned change, verify the intended unit, effective properties, application readiness, logs, listeners and a fresh client connection; distinguish enabled (boot policy) from active (current state). Test persistence/restart during the maintenance window. If it fails, restore only the changed drop-in/application settings, reload the manager and recover the intended service; do not remove unrelated overrides or repeatedly reset a failed unit without resolving its cause.[48]
