Backup and point-in-time recovery

Choose a recovery contract

A replica set copies mistakes as faithfully as good writes. Set RPO (maximum accepted lost work) and RTO (time to restore useful service), then measure them with restores. A backup job finishing is not proof of either.[21][22]

Method Appropriate use Consistency/recovery boundary
mongodump without oplog Small logical export during a controlled write pause With writes running, collections need not represent one instant
Full replica-set dump + --oplog Consistent logical restore of one replica set Captures dump-window operations, not future continuous PITR
Coherent filesystem snapshot Fast physical recovery Whole data/journal state, correct engine/version and topology required
Cold whole-directory copy Planned standalone outage Clean shutdown, complete directory; copying a running directory is unsafe
Atlas continuous backup / Ops Manager Managed/coordinated backup products Service/subscription-specific; not bundled Community commands
JSON/CSV export Interchange Omits important metadata/types/options; not backup replacement

Record source binary/FCV, Tools version, topology, times, namespaces, concerns, backup checksums, encryption/key IDs and restore instructions. Encrypt backups off-host, restrict deletion, retain independent generations, and keep decryption keys available outside the failed host. Retention deletion starts only after verifying the replacement generation and policy; never delete oplog/journal files by hand.[2][3][21]

Logical dump and isolated restore

Read-heavy source operation; destructive potential on destination. Use Database Tools 100.17.0 from a trusted worker; the dump/restore flags here are present in the official 100.17.0 tagged sources.[69][70] This first route targets a standalone or a deliberately quiesced replica set’s shop database. Pause all writers and schema changes for the whole dump; document the business checkpoint. backup is the source identity; the destination uses its own restore identity.[2][3][60]

umask 077
sudo install -d -o "$(id -un)" -g "$(id -gn)" -m 700 /srv/backups/mongodb
mongodump --host 127.0.0.1 --port 27017 --username backup \
  --authenticationDatabase admin --db shop \
  --archive=/srv/backups/mongodb/shop-before-change.archive.gz --gzip

Use a new filename per generation. Require a successful exit status, retain stderr/logs, checksum the completed artifact and copy it off-host before treating it as protected. Resume writes only after source state and the checkpoint are recorded. This database-only archive does not automatically provide the whole instance’s users/roles.[2]

Create the isolated authenticated instance at 27018, with empty target application namespaces and the same server major/FCV as the source. The documented general restore compatibility is same major or same FCV; the conservative drill here uses the same 8.0.29 binary and recorded FCV. Do not use restore as an undocumented cross-major upgrade.[2][3]

mongorestore --host 127.0.0.1 --port 27018 --username restore \
  --authenticationDatabase admin \
  --archive=/srv/backups/mongodb/shop-before-change.archive.gz --gzip \
  --nsInclude='shop.*' --nsFrom='shop.*' --nsTo='shop_restore.*' \
  --stopOnError

No --drop: this route restores into a new namespace. Verify first that shop_restore is absent; otherwise choose another isolated target. If the dump contains system.profile metadata and the destination has no profiling collection, also grant the destination loader dbAdmin on shop_restore for its creation, then revoke that extra role after the drill. The ordinary restore role alone is not sufficient for this case; profile documents themselves are not restored.[60][85] A failed restore can leave partial data. Do not retry over it and assume duplicate errors are harmless; preserve logs, discard only the explicitly identified disposable target, and rerun into a clean target.[3]

Tool option Scope / caution
--archive=FILE, --gzip Single archive plus compression; supply matching restore options
--db, --collection Limits dump scope; incompatible with full consistent oplog route
--dumpDbUsersAndRoles Explicit database user/role export; security-sensitive
--nsInclude Restore namespace selection; quote wildcards from the shell
--nsFrom, --nsTo Namespace rewrite; not allowed with oplog replay
--stopOnError Stop on write errors; does not roll back already restored documents
--drop Drops collections present in backup, not unrelated destination collections
--config=FILE Tools sensitive-options YAML alternative; restrict permissions

If restoring admin with --drop, users are replaced and authentication can fail midway unless the required existing/backup credentials work. Never use that flag casually on an operational server. Restored view pipelines and cross-namespace references must be checked after namespace rewriting, not assumed to follow application naming changes.[2][3]

Capture/replay a replica-set dump window

Use this route for a full single replica set, not mongos or a whole sharded cluster. Confirm oplog history spans the dump, sufficient disk, stable topology and no prohibited DDL/user/role/default-concern changes during the dump. An oplog rollover or prohibited operation makes the attempt unusable; inspect the tool exit/log rather than preserving a partial dump as “success.”[2][31]

The host names/CA come from the secured replica set. On the backup worker:

mongodump --uri='mongodb://db1.example.net:27017,db2.example.net:27017,db3.example.net:27017/?replicaSet=rs0&authSource=admin' \
  --username backup --ssl --sslCAFile=/etc/mongodb/tls/ca.pem \
  --oplog --out=/srv/backups/mongodb/rs0-full-001

Do not add --db, --collection, or query filters. Ordinary dump metadata recreates indexes/views; the root oplog.bson carries captured changes. Freeze schema and privilege changes during this window even though ordinary application writes may continue. A full dump includes sensitive user/role definitions; protect it accordingly.[2]

Destination-only privilege escalation for recovery. Use a fresh isolated 27018 instance, not the populated target of the preceding exercise. Bootstrap its administrator with the unique name drill_useradmin instead of useradmin, and create drill_restore with the ordinary restore role. Confirm neither name occurs in the source backup; select different names if they do. Do not create the other source-named bootstrap accounts on this destination. Authenticated as drill_useradmin, add the temporary replay role below. Oplog replay requires broader access than the ordinary restore role:[60][85]

use admin
db.createRole({role: "oplogReplayOnlyForDrill", privileges: [
  {resource: {anyResource: true}, actions: ["anyAction"]}
], roles: []});
db.grantRolesToUser("drill_restore", [{role: "oplogReplayOnlyForDrill", db: "admin"}]);

Restore the entire dump into this otherwise empty isolated deployment. Its bootstrap users must not conflict with source users carrying different credentials: establish the credential/role restoration plan before running, and never experiment against production admin.[3][60]

mongorestore --host 127.0.0.1 --port 27018 --username drill_restore \
  --authenticationDatabase admin --dir=/srv/backups/mongodb/rs0-full-001 \
  --oplogReplay --stopOnError

No namespace filter/rewrite with --oplogReplay. Retain source recovery credentials securely for post-restore administration; verify whether the restore identity/role changed, then revoke/remove the temporary replay privilege using the effective administrator. The distinct destination recovery identities above avoid name collisions, but still require a post-restore access review. Revoke the temporary role from drill_restore, remove the temporary role, and disable/remove the recovery accounts only after proving an approved source administrator can authenticate on the restored target. Do not remove your sole working administrator.[3][60]

--oplogLimit is not a universal “restore to any timestamp” switch. The dump captures only its own window, not earlier consistent baselines or later writes; arbitrary truncation can produce inconsistent data. Continuous PITR needs a verified base plus uninterrupted, correctly ordered retained history and a supported recovery process. Do not build it by copying random oplog BSON and claiming parity with a managed backup service.[3]

Physical snapshot and cold restore

A physical backup contains storage-engine state. Keep all data and journal files coherent. For online snapshots, use an atomic storage snapshot across the required volumes; if data and journal are separated, lock/suspend writes as documented. Snapshot copy-on-write space must survive until the full backup copy completes. A snapshot on the same failed disk is not offsite protection.[21]

A simple self-hosted cold standalone route avoids storage-vendor snapshot syntax. Have sudo access, a write pause, a clean backup destination and a supported filesystem. Stop the source cleanly, verify termination, then copy the whole directory:

sudo systemctl stop mongod
sudo systemctl is-active mongod
sudo install -d -o root -g root -m 700 /srv/backups/mongodb
sudo mkdir -m 700 /srv/backups/mongodb/cold-001
sudo cp -a /var/lib/mongo/. /srv/backups/mongodb/cold-001/
sudo systemctl start mongod

Do not proceed from is-active alone if a separate manually launched process can own the path. Record successful copy/ownership and source restart checks, then encrypt/checksum/copy the artifact off-host. Record numeric UID/GID, mount identity, SELinux local rules and policy revision alongside config/unit/TLS key identifiers (not private key contents). On an isolated recovery host, stop mongod-restore, move its disposable previous directory aside, create an empty owned /srv/mongodb/restore, and copy the full backup there. Keep the original backup read-only; start only a working copy with the matching storage options, bound to loopback at 27018.[21][22]

The restore-service policy gate applies to physical restores too. Copying preserved labels/numeric owners from the source does not prove destination correctness. On the stopped disposable target only, set the restored tree to that host’s mongod:mongod, apply its persistent dbPath mapping with restorecon, and verify the mount, DAC, effective labels and confined startup. Do not recursively relabel the retained immutable backup or expose restored replica identities to production.[100][110]

# Target only; the complete backup has already been copied and validated.
sudo chown -R mongod:mongod /srv/mongodb/restore
sudo restorecon -Rv /srv/mongodb/restore
sudo ls -ldZ /srv/mongodb/restore
sudo systemctl start mongod-restore
sudo ps -eZ | grep mongod
sudo ausearch -m AVC,USER_AVC -ts recent

For a replica-set physical backup, node-local replication identity comes with the files. Do not start a restored member on the production network. To form a new set from it:[22]

  1. Work on the isolated copied directory; start it as a standalone, preserving storage/TLS/auth settings but without production replica-set membership. Authenticate using restored administrative credentials.
  2. On this isolated copy only, confirm host/path/port, then remove old node-local replication metadata:
// DESTRUCTIVE: isolated restored copy only, never a live member
// Requires authorized administrative access to local.
db.getSiblingDB("local").dropDatabase();
  1. Shut down cleanly. Add a new replication.replSetName, internal key and isolated host addresses; restart, initiate a single-member recovery set, then add empty secondaries for initial sync.
  2. Validate the restored data and newly built topology before cutover. Never clone the same stale membership into several running nodes and hope election makes it safe.

The local removal is not a corruption repair or routine replica-member replacement. On Enterprise encrypted storage with AES256-GCM, cold-restore key rollover has additional mandatory requirements; this Community/OS-encrypted baseline does not cover that feature by pretending the same copy is sufficient.[11][22]

Sharded backup means coordinated backup

Stopping the balancer alone does not stop application writes. Exact cluster-wide consistency requires no in-flight operations and coordinated quiescence of shards and config-server metadata. Different independent per-shard dumps/snapshots can cut a cross-shard transaction or migration at different points.[26]

For the documented 8.0 filesystem route, schedule an outage/window, block new writers and DDL/resharding, wait for in-flight work, and use the appropriate maintenance identities:

  1. On mongos, sh.stopBalancer(); verify sh.getBalancerState() is false and no balancing round/migration remains.
  2. Run db.getSiblingDB("admin").fsyncLock() on mongos and separately on the config-server replica-set primary. The router lock covers shard writes; config metadata must also be locked. Confirm lock results and the documented $currentOp lock diagnostics on both endpoints.
  3. Snapshot the config-server primary and every shard primary, including each node’s coherent data/journal volumes. Record one topology-wide backup manifest; do not omit the config backup.
  4. In guaranteed cleanup, issue db.getSiblingDB("admin").fsyncUnlock() on both locked endpoints, verify unlocked state, then restore the prior balancer state and admit traffic.
  5. If any snapshot/lock fails, mark the whole set incomplete, unlock what was locked and repeat from a clean window. Do not label the surviving shard files a consistent cluster backup.[26]

fsyncLock disrupts writes; retain an independent operator connection and a time-bounded recovery plan. Storage-provider snapshot commands depend on the actual volume layout and are not invented here. Restoring a sharded physical backup must rebuild the matching topology/config metadata in isolation; do not apply the single-replica-set local recipe blindly to a whole cluster. Ops Manager/Atlas provide separately licensed/managed coordinated alternatives; they are options, not Community commands.[22][26][60]

Managed continuous backup is a separate service

Atlas Cloud Backup is a configured service feature, unavailable on Free clusters. Its snapshot storage uses the cloud provider; cross-region copies, retention and restoration permissions remain explicit customer decisions. A cluster existing in Atlas does not prove a recoverable backup policy exists.[81]

Atlas point-in-time restore requires Continuous Cloud Backup on an eligible dedicated cluster and a timestamp within the retained restore window; scheduled snapshots alone do not establish that capability.[93][97] Select the source time and compatible destination, rehearse application cutover, and validate the restored business checkpoint. Sharded restores require topology-aware handling, not independent selection of convenient shard timestamps.[90][93]

Ops Manager coordinates snapshot capture and oplog collection using deployed agents and its backup storage. It is an independently installed/operated backup product, not an additional flag on Community mongodump. Confirm deployment-version support, subscription/entitlements, agent reachability, storage capacity and recovery credentials before choosing it. Neither service removes the need to test restores or protect deletion authority.[83]

Restore acceptance

Use operator with readWrite/dbAdmin on the restored database, not just the write-oriented restore account. On 27018, grant these destination-only roles as needed via useradmin and revoke after the drill.[18][59]

const restored = db.getSiblingDB("shop_restore");
restored.getCollectionInfos();
restored.orders.getIndexes();
restored.orders.countDocuments({});
restored.orders.aggregate([
  {$group: {_id: "$tenantId", orders: {$sum: 1}, amount: {$sum: "$total"}}},
  {$sort: {_id: 1}}
]).toArray();
restored.runCommand({validate: "orders", full: true});

For full oplog/physical restores the database is shop, not shop_restore. validate can be expensive and affect concurrency; run the full check on the isolated copy. Acceptance includes no tool errors, engine validation, expected BSON types, validators, indexes/uniqueness, views, users/roles, checkpoint-matched business totals, representative application reads/writes and measured restore time. Compare to the backup checkpoint, not a source that continued changing.[3][59]

Keep the source authoritative until acceptance. A failed drill leaves the source untouched; repair backup policy rather than deleting the only known-good copy. Once a restored system accepts new writes, rollback requires reconciliation, not simply redirecting clients to an older snapshot.
