Inventory semantics before moving rows

A MySQL SQL dump is not a PostgreSQL restore script. Convert the model, SQL behavior and application contract before the outage, then move data under a documented snapshot/change boundary. PostgreSQL logical replication cannot consume MySQL’s binary log directly; cross-engine CDC needs a separately selected connector whose source version, privileges, initial snapshot and offset semantics are verified.

Record source server/tool versions, storage engines, SQL modes, charsets/collations, time zones, table sizes, PK/FK/unique constraints, views, triggers, routines, generated columns, events and application queries. Include nontransactional source tables and external side effects when deciding whether a consistent export is possible. The target remains community PostgreSQL 18 on RHEL/PGDG; no migration tool or managed service is silently assumed. Provision that RPM/service/TLS/firewalld/SELinux baseline before loading. Use /usr/pgsql-18/bin/psql with the explicit /run/postgresql socket/5432 for local peer administration; target extensions need their RHEL-major-specific RPMs on all recovery/HA hosts. Client \copy below reads the client filesystem, so grant that client account access rather than relabeling exports as server-writable data.[100][105][13]

Source concept PostgreSQL target / conversion decision Validate before loading
MySQL database used as namespace PostgreSQL database plus named schema Cross-database SQL must be redesigned; schema is inside one database.[21]
Backtick/mixed-case identifiers Prefer lowercase unquoted names; double quotes preserve exact case Rewrite application SQL and collisions; do not just replace quoting characters in arbitrary SQL.[78]
Signed integer types smallint, integer, bigint by actual range Overflow and negative-value constraints.
Unsigned integer / unsigned bigint Wider signed type, or numeric(20,0) where bigint cannot hold the range Add nonnegative/range checks; do not silently wrap or truncate.[79]
Auto-increment GENERATED ... AS IDENTITY plus explicit PK/unique constraint Imported IDs, sequence next value, application generated-key API.[48]
Decimal currency numeric(precision, scale) Rounding, scale and maximum aggregate values; not floating point.[79]
Tiny integer used as boolean boolean only after proving the actual value domain Values other than intended true/false/null need explicit mapping.
Datetime / timestamp timestamp for wall-clock facts; timestamptz for instants Source session zone, DST ambiguity, invalid/zero dates and precision.[80]
Text/charset/collation Usually UTF-8 plus chosen libc/ICU/builtin collation Case/accent comparisons, trailing-space behavior, ordering and unique collisions.[49]
JSON json or jsonb by required semantics/operators Formatting/key-order/duplicate-key expectations; index design.[81]
Binary/blob bytea, or an explicitly designed large-object/external store Byte-for-byte comparison, encoding and backup lifecycle.[47]
Enum/set Enum, check-constrained text or normalized relation Allowed values, ordering and future schema evolution.

The table is a conversion checklist, not a universal mechanical mapping. Inspect actual values and source-version semantics; target data types and operators are defined by the PostgreSQL 18 manual.[47]

Convert schema, routines and access paths

Use a no-login owner and separate runtime roles as in administration. Keep a checked-in conversion manifest mapping each source object to its target name, type, default, constraint and application change. Avoid importing source administrators or broad grants.

Object/behavior Conversion work
Defaults/generated columns Rewrite expressions and volatile/time-zone behavior; PostgreSQL 18 defaults generated columns to virtual, so specify STORED when required by the design.[4][70]
Views/procedures/functions Rewrite SQL dialect and security semantics; PL/pgSQL is not source-compatible stored-routine syntax.
Triggers PostgreSQL uses trigger functions; preserve timing, row/statement scope and privileges explicitly.[50]
Scheduled events Choose an external scheduler or separately reviewed extension; not an automatic core event-scheduler import.
Upsert / duplicate handling Rewrite to INSERT ... ON CONFLICT with a deliberate arbiter: DO UPDATE requires a supported unique constraint/index, not an exclusion constraint. Do not assume identical affected-row semantics.[82]
Indexes Recreate constraints first; redesign useful B-tree/expression/partial/GIN indexes for actual PostgreSQL predicates.[28]
Prefix/collation-sensitive unique index Model the intended uniqueness explicitly and detect collisions before enforcement.
Sequences They are not gapless and not rolled back; test generated-key handling and post-import alignment.[60]

Changing collation can change equality and sort behavior, not just display order. Run duplicate checks under the target comparison before creating a unique index. Do not merely refresh a recorded collation version after an OS/library upgrade; rebuild affected indexes first.[49][87]

Test application transaction boundaries, error SQLSTATE handling/retries, pagination stability, boolean/date serialization, parameter placeholders, identifier quoting, connection pooling and permissions. A schema that loads successfully can still implement different business rules.

Load through a text staging table

This bounded example assumes a quiesced, consistent CSV export of one source orders table has already been produced and validated by the source owner. It is not a MySQL export or CDC tool recipe. The file contract is UTF-8 RFC-style CSV with header, comma delimiter, double-quote escaping, \N for null, dot decimal, and timestamps already normalized to explicit UTC offsets. If the export uses different escaping/null conventions, convert it explicitly rather than guessing.[46]

Example file shape (illustrative input, not captured production output):

id,customer_id,total,status,created_at
1,42,12.50,new,2026-01-01T10:00:00+00:00
2,17,8.00,paid,2026-01-02T09:30:00+00:00
3,42,0.00,cancelled,2026-01-03T12:00:00+00:00

Create a new migrationlab database and migration_owner no-login owner using controlled local peer administration. Stop on name collisions; do not reuse a database containing application data. As postgres in psql, outside a transaction for CREATE DATABASE:[13][59]

\set ON_ERROR_STOP on
CREATE ROLE migration_owner NOLOGIN;
CREATE DATABASE migrationlab OWNER migration_owner;
REVOKE ALL ON DATABASE migrationlab FROM PUBLIC;
\connect migrationlab
REVOKE CREATE ON SCHEMA public FROM PUBLIC;
SET ROLE migration_owner;

Continue in that same owner session. The client OS account must be allowed to read /secure/orders.csv. No application login receives access until mapping and validation are accepted.

\set ON_ERROR_STOP on
CREATE SCHEMA staging;
CREATE SCHEMA sales;
CREATE TABLE staging.orders_raw (
  id text, customer_id text, total text, status text, created_at text
);
\copy staging.orders_raw FROM '/secure/orders.csv' WITH (FORMAT csv, HEADER true, NULL '\N', ENCODING 'UTF8')

-- Inspect rejects; resolve them, do not discard them silently.
SELECT * FROM staging.orders_raw
WHERE id IS NULL OR id !~ '^[0-9]+$'
   OR customer_id IS NULL OR customer_id !~ '^[0-9]+$'
   OR total IS NULL OR total !~ '^[0-9]+([.][0-9]{1,2})?$'
   OR status IS NULL OR status NOT IN ('new','paid','cancelled')
   OR created_at IS NULL OR created_at LIKE '0000-%'
   OR created_at !~ '[+]00:00$';
SELECT id, count(*) FROM staging.orders_raw GROUP BY id HAVING count(*) > 1;

The reject query is a preliminary screen, not a complete date/range validator. Casts and constraints below are the decisive fail-fast gate. Text duplicates such as 1 versus 01 can still collide numerically; the primary key catches them. If actual source IDs can exceed signed bigint, change the target design before importing, not after an overflow.

BEGIN;
CREATE TABLE sales.orders (
  order_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY CHECK (order_id > 0),
  customer_id integer NOT NULL CHECK (customer_id > 0),
  amount numeric(12,2) NOT NULL CHECK (amount >= 0),
  status text NOT NULL CHECK (status IN ('new','paid','cancelled')),
  created_at timestamptz NOT NULL
);
INSERT INTO sales.orders (order_id, customer_id, amount, status, created_at)
OVERRIDING SYSTEM VALUE
SELECT id::bigint, customer_id::integer, total::numeric(12,2),
       status, created_at::timestamptz
FROM staging.orders_raw;
COMMIT;

-- No writers may connect until this and the validation pass.
SELECT setval(pg_get_serial_sequence('sales.orders','order_id'),
              COALESCE((SELECT max(order_id) FROM sales.orders), 1),
              EXISTS (SELECT 1 FROM sales.orders));
ANALYZE sales.orders;

Resolve every reject before the insert, including scale violations: casting to a constrained numeric type can round, so a successful cast is not proof of no source precision loss.[79] OVERRIDING SYSTEM VALUE permits the reviewed source IDs in an always-generated identity column.[82] If the transaction fails, inspect the failing row/error and correct the mapping; do not turn constraints off to make it pass. setval’s final boolean distinguishes empty-table next value from a used maximum; sequence state is not transactionally rolled back, so run it while writers are fenced and repeat validation afterward.[48][60]

For a larger load, choose parallelism and deferred index construction deliberately; retain primary-key/business validation and enough disk/WAL/archive headroom. Client \copy avoids granting server filesystem access. Server COPY uses server paths/privileges. Do not leave staging exports or reject files readable after the migration.[13][46]

Validate at a common boundary

SELECT count(*) AS rows, min(order_id), max(order_id), sum(amount)
FROM sales.orders;
SELECT status, count(*), sum(amount) FROM sales.orders GROUP BY status ORDER BY status;
SELECT count(*) FROM sales.orders WHERE customer_id <= 0 OR amount < 0;
SELECT conname, convalidated FROM pg_constraint
WHERE conrelid = 'sales.orders'::regclass;

Compare these with the source at the exported snapshot or final CDC watermark. Equal counts do not prove equal rows: compare ordered primary-key ranges and canonical per-row/per-batch digests or exports. Define identical null, decimal, Unicode, time-zone and binary serialization on both engines before hashing; database-native hash functions over different string formats are not comparable.

Include orphan/FK checks, duplicate detection under target collation, bounds/null distributions, money totals, time-zone edge cases and representative joins. Test target grants and expected denials, routine/trigger side effects, generated IDs and application read/write workflows in an isolated environment. Inspect plans after ANALYZE; do not require identical MySQL and PostgreSQL plans, only equivalent results and the agreed performance objective.[27][46][49]

Keep a per-table reconciliation report: source snapshot/watermark, target count, comparison definition, rejected rows, owner decision and final acceptance. No rows are “close enough” without an explicit business decision. Masked rehearsals must preserve the data distributions relevant to uniqueness and plan tests.

Cut over once, with a rollback boundary

Phase Required proof before continuing
Rehearsal Complete conversion, restore/reload timings, application/permission tests and repeatable reconciliation.
Initial copy Consistent source snapshot and its CDC start position, or a documented full write outage.
Catch-up Connector reports durable applied position, no unresolved conflicts/rejects, DDL changes coordinated.
Write fence Source application writers/jobs disabled; remaining transactions completed; final source position recorded.
Final sync All changes through the fence applied; sequence state/routines/privileges validated; totals/checks pass.
Switch One write authority, endpoint/driver/pool updated, controlled smoke write/readback succeeds.
Observe Error/latency/business checks pass, backups and recovery monitoring active, old source kept read-only.

For a small system, a full outage plus consistent export/import may be safer than an unproven CDC stack. For low downtime, choose a connector with documented MySQL-version/binlog/snapshot requirements and PostgreSQL delivery semantics; test duplicates, restart/replay, deletes, schema changes and offset retention. This is a product-selection boundary, not a missing command to fake with PostgreSQL’s native subscription syntax.

Before target writes are accepted, rollback can leave the source authoritative and discard/rebuild the target. After target writes, the old MySQL source is stale. Returning traffic requires tested reverse movement/reconciliation or an explicitly accepted loss window. Dual-writing both databases is not a free rollback mechanism: ordering, retries, partial success and conflict handling require application design.

Retain source backups, normalized export definitions, conversion scripts, source/CDC positions and validation reports through the agreed rollback period. After acceptance, remove migration-only privileges/connector secrets, securely retire staging data and prove a PostgreSQL restore. The migration is not finished merely because the final row loaded.
